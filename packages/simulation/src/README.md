# simulation/src

## Purpose

- `backend/backend.ts`: the `./backend` entry, `simulationReplacements(app)`: the harness, harnesses, HTTP client layer and plugins an engine in simulation is built with. Driven (`CONCIV_DRIVE` set), it resolves the manifest and opens the backend control socket in the caller's scope. `startSimulation(app, configProvider)` runs it on a scope of its own with the node file system and returns the replacements with their `close`, the `StartSimulation` that `@conciv/backend` and `@internal/engine-kit` give `createBackend`.
- `backend/simulated-provider.ts`: the driver-answered model provider and the backend control socket's router: one invocation per model turn, waiting until the driver answers it by id.
- `backend/simulated-harness.ts`: a harness whose chat streams the simulated provider's answer as chat events; the refused harness of an undriven simulation.
- `backend/simulated-ui.ts`: `widgetDrivePlugin`, the `conciv.simulation.ui` plugin of a driven engine: it listens on the manifest's `ui` endpoint with `control-server.ts`, answers the `ui` handshake as opencode's TUI server does, and forwards each supported `ui.*` call to the widget as a `call` event, waiting for the widget's `result` (capture, recording, mouse and resize are refused). Invariant: the driver dials the engine, never the widget, as in opencode.
- `backend/simulated-tools.ts`: the tools a driver registers, offered to the engine as the `conciv.simulation.tools` plugin.
- `backend/scripted-harness.ts`: the scripted harness definition (models, commands, terminal, past sessions, context meter), one copy for the simulation and `@internal/engine-kit`'s harness engine.
- `backend/network.ts`: the fixed network table.
- `control-server.ts`: the WebSocket control server both endpoint roles run on: handshake dispatch (role, version, capabilities), one message at a time, the outbound byte cap.
- `manifest.ts`: the Drive manifest.
- `driver.ts`: the `./driver` entry and its answer helpers.
- `frontend.ts`: the `./frontend` entry, the ui driver: `connectUi(endpoint, signal)` dials the engine's `ui` endpoint and handshakes; `byRole`, `clickByRole`, `typeInto` act through it.

- `scripted-harness.ts`: the harness the engine runs. A given adapter keeps everything but its chat, which answers each model request with the next reply the test gave through `engine.reply`, records what each model request was given as plain data (its system prompts, messages, each tool's name, description and JSON Schema input, never the tool's functions, plus the configured model, effort and model options), and holds it while a gate is set; without one, the quick adapter with id `engine` does the same, takes the system prompt (`systemPrompt: 'flag'`), and also lists a fixed model list, the `model` and `deploy` slash commands and a plain bash terminal; one scripted harness with its own models is `harnesses: [{id: 'engine', models}]`. `harnesses` makes several such adapters, each with its own id, models and commands: the first is the engine's harness, the rest are passed to `makeApp` as `harnesses`, and all answer from the one reply queue and `requests()` log. The engine refuses, before it starts, a repeated harness id, an empty `harnesses`, and `harnesses` with `harness`. An entry's `sessions` gives it a `history` and a `resume` built from that data (see the package README).
- `test-llm.ts`: the reply shapes and helpers of opencode's test model, on `ChatEvent` chunks, and the shape of one recorded model request. It is also the `./test-llm` entry, which imports nothing from core and no node builtin, so browser mode can load it.
