# harness-testkit/src

## Purpose

`harness-engine.ts` is the package entry, with `createHarnessEngine(config, start)`. `config` is parsed by the product's `ConcivConfigSchema` and goes to core's `start` as its `options`, the way the dev server's config file does, so `plugins`, `permission`, `permissions`, `policies`, `systemPrompt`, `sessionId`, `hubAccess` and the rest take the product's own defaults when left out (`resolveConfig`). Three fields are the kit's to set and are refused before anything starts, with a message naming the field: `stateRoot`, `homeDir`, `devEndpointDir`. `config.harness` picks which of the scripted harnesses is the engine's (refused when no harness has that id); without it the first. `config.port` becomes `start`'s `port: {exact}`, as the unplugin's boot does; without it the port is free. `sessionId` goes through `resolveConfig`, which refuses an id that is not a conciv id, and the engine opens on that session instead of creating one. `start` holds what is not product config: `harness` (a real adapter), `harnesses`, `directory`, `timeouts` (`firstChunkTimeoutMs`, `firstStartTimeoutMs`, `eventHeartbeatIntervalMs`, `stopGraceMs`, `pageReplyTimeoutMs`, `queuedActionTimeoutMs`, passed to `start`), `env` (laid over the isolated environment the engine reads its configuration from; the file watcher is off, `CONCIV_DISABLE_FILEWATCHER`, unless `fs: {filewatcher: true}`, opencode's option name) and `clock`. After start, the test changes what the engine sees through calls on it: `reply(...responses)` appends to the reply queue; `write(path, content)` writes a file inside the project folder (refused outside it, and refused on a `directory` fixture, which is committed on disk); `setting(...)` writes a setting through the settings rpc; `stale(staleness)` is the engine's stale-code report from then on and `version(version)` the version in its `x-conciv-version` header, on every route and on a refused request. The kit hands `start` a function for each, read on every request; until the test calls it, it answers `undefined`, and the product falls back to its own check and the core package version. `directory` runs the engine on an existing fixture folder (resolved against the working directory) as its `cwd`, while its state, home and temp folder stay in the kit's own temp root, the only thing removed on stop. `root` is the project folder's real path: the fixture, or the temp root, where `engine.write` puts files. As the dev server does, `start` writes `server.json` and the Claude connect file in the state folder of the temp root, and registers the engine in the home database of its own home, retiring the row on stop; so the CLI finds the engine from `root` when there is no fixture, and through that home (`CONCIV_HOME`) otherwise. The dev endpoint folder is inside that home, so nothing is written outside the temp root. A known limit: with a `directory` fixture, `server.json` and the home stay in the kit's temp root, not in the fixture folder, so the CLI run from `root` without that home does not find the engine. `opened` is what the engine opened in the editor, in the order opened, with undefined fields left out: `start`'s editor opener records instead of launching, so a missing line is line 1 and the same file, line and column asked again within 4 s is opened once, as in the product. `event(type)` subscribes to the engine's event stream for that type and resolves once the subscription is live (after the stream's first `server.connected`), so a wait made before an action cannot miss it; its `arrived` resolves with the first such event as `{type, data}`, and rejects with "the engine stopped before a <type> event arrived" when the engine stops first. A wait nobody awaits raises no unhandled rejection. `event('server.connected')` is refused at once with a plain message: the engine sends that frame only once, as the first frame of each subscription, which is how `event` knows the subscription is live, so no later one can arrive. `rpc.call(rpcId, method, input?)` calls a plugin's own rpc over `plugin.call`; `rpc.failure` answers the plugin rpc failure as `{type, message, data?}` (zod-parsed from the error, as the product client does), rejects when the call answers, and rethrows any other error. `loginCode()` issues a browser login code through `auth.issueCode` with the engine's own token (the token path client, as `conciv link` does), and `revokeBrowsers()` revokes every trusted browser in the engine's state folder (`revokeBrowsers(stateDir, 'all')` from `@conciv/protocol/engine-trust`). `restart()` stops and boots the engine on the same project folder, state, home, token and port: it refuses the open event waits, aborts the kit's open turns, then releases a held gate, stops the engine, and starts it again with the same access token, the exact port and the first session's id as its configured session (a taken port fails the start). Writes and settings already made stay; the reply queue, `requests()` and `opened()` carry on. If the new start fails, `start` undoes what it did, the project root stays for `stop`, and `restart` rejects. `stop` is one function over whichever engine is running, so a restarted engine is still stopped. `clock: 'test'` runs the engine on Effect's test clock, as opencode's `it.effect` does: the reads and sleeps on Effect's `Clock` move only when the test moves them, raw `Date.now()` and timers stay real, and time starts at 0; without it the engine is on the real clock. `start.port: 'connect'` starts the engine on the first free connect port, 4732 to 4741 (`@conciv/protocol/connect-ports`), through core `start`'s `port: {exact}`, trying the next port when one is taken (`EADDRINUSE`), as `packages/try/src/connect.ts` does; with all ten taken it rejects with `no free port between 4732 and 4741: <last error>`, and `start` has undone each failed try, so no engine is left behind; given with `config.port` it is refused before anything starts. `start.token` is the connect port's pairing token, core `start`'s `accessToken`, which refuses a token that is not a UUID; it is refused without `port: 'connect'`, and not given, core `start` makes one. Either way it is `address.token`. Ten connect ports are shared by every test and every `npx @conciv/try` on the machine.

- `clock.ts`: the engine's `clock`. With `clock: 'test'` the kit builds `TestClock.layer()` on its own scope, hands its context to `start` as `clock`, keeps it across `restart` and closes it at `stop`. `advance(until)` repeats opencode's step (one real 1 ms macrotask, then `TestClock.adjust('500 millis')`) until `until` settles, and returns or rethrows its outcome; after 15 s of real time it rejects with "the engine clock was advanced for 15s and the awaited call never settled". `drain()` is four steps and one settle. `tick()` is one step, for browser mode only. On an engine on the real clock all three reject with "this engine runs on the real clock: make it with clock: 'test'". Its step is one settle and one `TestClock.adjust`; the loop around it is `clock-steps.ts`'s.
- `clock-steps.ts`: the clock loop, once, for the node clock and browser mode: `advanceUntil(until, step)` repeats the caller's step until `until` settles, with the 15 s limit and its message; `drainWith(step)` is four steps and one settle; `refuseRealClock` rejects with the real-clock message. It is also the `./clock` entry, which imports nothing from core, nothing from effect and no node builtin, so browser mode can load it; the browser side's step is one `concivClockTick` command.

- `scripted-harness.ts`: the harness the engine runs. A given adapter keeps everything but its chat, which answers each model request with the next reply the test gave through `engine.reply`, records what each model request was given as plain data (its system prompts, messages, each tool's name, description and JSON Schema input, never the tool's functions, plus the configured model, effort and model options), and holds it while a gate is set; without one, the quick adapter with id `engine` does the same, takes the system prompt (`systemPrompt: 'flag'`), and also lists a fixed model list, the `model` and `deploy` slash commands and a plain bash terminal; one scripted harness with its own models is `harnesses: [{id: 'engine', models}]`. `harnesses` makes several such adapters, each with its own id, models and commands: the first is the engine's harness, the rest are passed to `makeApp` as `harnesses`, and all answer from the one reply queue and `requests()` log. The engine refuses, before it starts, a repeated harness id, an empty `harnesses`, and `harnesses` with `harness`. An entry's `sessions` gives it a `history` and a `resume` built from that data (see the package README).
- `test-llm.ts`: the reply shapes and helpers of opencode's test model, on `ChatEvent` chunks, and the shape of one recorded model request. It is also the `./test-llm` entry, which imports nothing from core and no node builtin, so browser mode can load it.
- `call-tool.ts`: a session's tool call on `/api/mcp`: a tool the engine lists by its own name (a direct tool) is called by that name, any other through `execute_typescript`; a reply of one text part is parsed as JSON, a reply of several parts comes back as its content list.
- `outside.ts`: `engine.outside({client?, tab?})`, an outside agent's call the way the conciv hub makes it: an rpc client with `conciv-origin: hub` and `conciv-client: <client>` (`terminal` when not given), the tab as the call's `sessionId`. `describe`, `discover(toolNames)` and `call(name, input?)` are `code.describe`, `code.discover` and `code.execute` (`return await external_<name>(input)`), their replies built by the hub's own `codeDiscoverReply` and `codeExecuteReply`; an error the engine answers resolves as the hub's error reply, `{content: [{type: 'text', text: message}], isError: true}`, and any other error rejects. A call with no tab is an outside run, which the engine answers with its no-tab error for a tab's tool. `hubAccess` (`'open'` or `'project'`) goes into the engine's config; not given, the product's `'open'`. A connected agent is not covered: only the agent's own CLI writes its connection row.
- `cli.ts`: `cli(args, {cwd?, env?, engine?})` runs the built `@conciv/cli` bin (resolved as `@conciv/cli/bin`, a peer) with `node` in a fresh temp home, with `isolated-env.ts`'s environment and `env` laid over it, from `cwd` (default: that home), and resolves with its `stdout`, `stderr` and `exitCode` (a child killed by a signal answers 128 plus the signal's number); a non-zero exit resolves. The CLI looks for its engine in `CONCIV_PORT`, then a `.conciv/server.json` in its folder or a parent, then its home database, then port 5173. So: `engine` (anything with the engine's `address`) sets `CONCIV_PORT` and `CONCIV_TOKEN` from that address, the way to reach an engine on a `directory` fixture, whose `server.json` is not in that folder; with no `engine`, no `cwd` and no `CONCIV_PORT` in `env`, `CONCIV_PORT` is a port the kit has just opened and closed on `127.0.0.1`, so the CLI answers its own "No conciv dev server on 127.0.0.1:<port>." and never reaches a real dev server on 5173; with a `cwd` and nothing else no port is set, so the CLI finds a no-fixture engine from `engine.root`. A `cwd` with no `server.json` above it still falls through to 5173. `env` is laid over all of it. Re-exported by `@conciv/plugin-testkit` only, never the browser entry.
- `isolated-env.ts`: the environment the engine reads: the developer's own with provider keys, secrets, every `CONCIV_*` variable and the agent-shell variables (`CLAUDECODE`, `CODEX_THREAD_ID`, `GEMINI_CLI`, `OPENCODE`, which the CLI reads to tag a call with its agent) taken out, and `HOME`, the XDG folders and `TMPDIR` set inside the engine's state folder, as opencode's test runner does; `PATH` is kept.
- `run-tests.ts`: the `./run-tests` entry behind the `conciv-test` bin. It runs the package's own `vitest run` with the caller's arguments in a fresh home folder, with `isolated-env.ts`'s environment plus `PLAYWRIGHT_BROWSERS_PATH` set to the folder Playwright would use with the real environment (so browser mode finds the installed browsers), forwards SIGINT and SIGTERM, removes the folder when vitest exits, and exits with vitest's code.
- `until.ts`: the private wait `approve` uses until the session has a pending ask.

## Invariants

- `send` resolves when the turn's run finishes, fails or is stopped. A RUN_FINISHED whose finish reason (top level, or `metadata.tanstack.finishReason` where @tanstack/ai puts it on a model call's RUN_FINISHED) is `tool_calls` ends one model call, not the run, as the TanStack chat client reads it.
- `requests` is a copy of the model requests recorded so far, in arrival order, recorded before a gate holds them. Each is plain data: the system prompts as strings, the messages, each tool with its name, description and JSON Schema input, the model and effort the harness was configured with (or `null`), and the model options; after `send` resolves or a gate's `started` settles, it holds that request.
- A session's `stop` sends the chat stop rpc, as a session-scoped client the way the widget's Stop does, for the session's active run and every run the kit started on it; it resolves when the engine answers, and the run's `send` then resolves.
- `approve` waits up to 5000 ms for a pending ask, then answers every pending ask once.
- A tool call gives up after 60000 ms; a tool error rejects with its text, which `failure` returns.
- A `cli` call gives up after 60000 ms: the child is killed and the call rejects with "the conciv CLI gave no result within 60000ms". Its temp home is removed after the child has closed, on every path.
- `stop` ends open turns, stops the engine (`start`'s stop: the dev endpoint, the home database row, the server, the app) and removes the project root; every step runs even when an earlier one fails, and the failures are rethrown as one `AggregateError`. A failed start undoes what it did the same way.
