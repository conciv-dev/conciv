# harness-testkit/src

## Purpose

`harness-engine.ts` is the package entry, with `createHarnessEngine`. It writes `files` into a fresh project root, starts core with `makeApp` (only `plugins`, `permission` and `permissions` are read from `config`), reads its configuration from the isolated environment with `env` laid over it (the file watcher is off, `CONCIV_DISABLE_FILEWATCHER`, unless `fs: {filewatcher: true}`, opencode's option name), serves it, writes `settings` through the settings rpc and opens the first session. `policies` and `systemPrompt` go into the configuration as given (defaults: no policies, an empty system prompt, `'project'` hub access); `sessionId` goes through core's `resolveConfig`, which refuses an id that is not a conciv id, and the engine opens on that session instead of creating one. `timeouts` (`firstChunkTimeoutMs`, `firstStartTimeoutMs`, `eventHeartbeatIntervalMs`, `stopGraceMs`, `pageReplyTimeoutMs`, `queuedActionTimeoutMs`) are spread into `makeApp`. `staleness`, when given, is the engine's stale-code report (`makeApp`'s `staleness: () => value`); without it the product's own check stays. `app` (`{version?}`) goes to `makeApp` as given: `app.version` is the version the engine reports in its `x-conciv-version` header, on every route and on a refused request; without it the core package version. `directory` runs the engine on an existing fixture folder (resolved against the working directory) as its `cwd`, while its state, home and temp folder stay in the kit's own temp root, the only thing removed on stop; it cannot be given with `files`. `root` is the project folder's real path: the fixture, or the temp root that holds `files`. `opened` is what the engine was asked to open in the editor, in the order asked, with undefined fields left out (the engine's `openInEditor` records instead of launching). `event(type)` subscribes to the engine's event stream for that type and resolves once the subscription is live (after the stream's first `server.connected`), so a wait made before an action cannot miss it; its `arrived` resolves with the first such event as `{type, data}`, and rejects with "the engine stopped before a <type> event arrived" when the engine stops first. A wait nobody awaits raises no unhandled rejection. `rpc.call(rpcId, method, input?)` calls a plugin's own rpc over `plugin.call`; `rpc.failure` answers the plugin rpc failure as `{type, message, data?}` (zod-parsed from the error, as the product client does), rejects when the call answers, and rethrows any other error. `loginCode()` issues a browser login code through `auth.issueCode` with the engine's own token (the token path client, as `conciv link` does), and `revokeBrowsers()` revokes every trusted browser in the engine's state folder (`revokeBrowsers(stateDir, 'all')` from `@conciv/protocol/engine-trust`). `restart()` stops and boots the engine on the same project folder, state, home, token and port: it refuses the open event waits, aborts the kit's open turns, then releases a held gate, closes the server, disposes the app, makes a new app with the same `agentToken` and the first session's id as its configured session, and listens on the same port (a taken port fails with a plain message). `files` and `settings` are not applied again; the reply queue, `requests()` and `opened()` carry on. If the new app or the listen fails, the new app is disposed, the project root stays for `stop`, and `restart` rejects. `stop` is one function over whichever app and server are running, so a restarted engine is still stopped.

- `scripted-harness.ts`: the harness the engine runs. A given adapter keeps everything but its chat, which answers each model request with the next of `replies`, records what each model request was given as plain data (its system prompts, messages, each tool's name, description and JSON Schema input, never the tool's functions, plus the configured model, effort and model options), and holds it while a gate is set; without one, the quick adapter with id `engine` does the same, takes the system prompt (`systemPrompt: 'flag'`), and also lists the `models` and `commands` it is given (by default a fixed model list and the `model` and `deploy` slash commands) and a plain bash terminal. `harnesses` makes several such adapters, each with its own id, models and commands: the first is the engine's harness, the rest are passed to `makeApp` as `harnesses`, and all answer from the one `replies` queue and `requests()` log. The engine refuses, before it starts, a repeated harness id, an empty `harnesses`, `harnesses` with `harness`, `models` or `commands`, and `models` or `commands` with a `harness` adapter.
- `test-llm.ts`: the reply shapes and helpers of opencode's test model, on `ChatEvent` chunks, and the shape of one recorded model request. It is also the `./test-llm` entry, which imports nothing from core and no node builtin, so browser mode can load it.
- `call-tool.ts`: a session's tool call on `/api/mcp`: a tool the engine lists by its own name (a direct tool) is called by that name, any other through `execute_typescript`; a reply of one text part is parsed as JSON, a reply of several parts comes back as its content list.
- `cli.ts`: `cli(args, {cwd?, env?})` runs the built `@conciv/cli` bin (resolved as `@conciv/cli/bin`, a peer) with `node` in a fresh temp home, with `isolated-env.ts`'s environment and `env` laid over it, from `cwd` (default: that home), and resolves with its `stdout`, `stderr` and `exitCode` (a child killed by a signal answers 128 plus the signal's number); a non-zero exit resolves. To reach a test's engine, pass `CONCIV_PORT` and `CONCIV_TOKEN` in `env`. Re-exported by `@conciv/plugin-testkit/node` only, never the browser entry.
- `isolated-env.ts`: the environment the engine reads: the developer's own with provider keys, secrets, every `CONCIV_*` variable and the agent-shell variables (`CLAUDECODE`, `CODEX_THREAD_ID`, `GEMINI_CLI`, `OPENCODE`, which the CLI reads to tag a call with its agent) taken out, and `HOME`, the XDG folders and `TMPDIR` set inside the engine's state folder, as opencode's test runner does; `PATH` is kept.
- `run-tests.ts`: the `./run-tests` entry behind the `conciv-test` bin. It runs the package's own `vitest run` with the caller's arguments in a fresh home folder, with `isolated-env.ts`'s environment plus `PLAYWRIGHT_BROWSERS_PATH` set to the folder Playwright would use with the real environment (so browser mode finds the installed browsers), forwards SIGINT and SIGTERM, removes the folder when vitest exits, and exits with vitest's code.
- `until.ts`: the private wait `approve` uses until the session has a pending ask.

## Invariants

- `send` resolves when the turn's run finishes, fails or is stopped.
- `requests` is a copy of the model requests recorded so far, in arrival order, recorded before a gate holds them. Each is plain data: the system prompts as strings, the messages, each tool with its name, description and JSON Schema input, the model and effort the harness was configured with (or `null`), and the model options; after `send` resolves or a gate's `started` settles, it holds that request.
- A session's `stop` sends the chat stop rpc, as a session-scoped client the way the widget's Stop does, for the session's active run and every run the kit started on it; it resolves when the engine answers, and the run's `send` then resolves.
- `approve` waits up to 5000 ms for a pending ask, then answers every pending ask once.
- A tool call gives up after 60000 ms; a tool error rejects with its text, which `failure` returns.
- A `cli` call gives up after 60000 ms: the child is killed and the call rejects with "the conciv CLI gave no result within 60000ms". Its temp home is removed after the child has closed, on every path.
- `stop` ends open turns, closes the server, disposes the app and removes the project root; every step runs even when an earlier one fails, and the failures are rethrown as one `AggregateError`. A failed start undoes what it did the same way.
