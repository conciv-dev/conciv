# @conciv/plugin source

The SDK is a port of opencode's plugin package (opencode at commit `a1aa513`; every opencode path below is relative
to its `packages/` folder). Names and shapes are opencode's except for the lines under "Differences from opencode".
The source keeps opencode's JSDoc only where a block carries at least one tag (`@param`, `@returns`, `@example`,
`@remarks` ...) above a declaration or member: those blocks stay whole, prose-only doc blocks are not kept
(`conciv/no-comments` with `keepDocComments`). A member marked as not implemented (below) carries only its `@remarks`
line.

## Entries

A plugin has up to three parts: an engine part (runs inside the conciv engine, adds tools, skills and RPC handlers),
an RPC contract shared by both sides, and a browser part (runs in the conciv widget, adds panels, slots, commands
and stores).

### `@conciv/plugin` (`promise/index.ts`)

The engine part. `Plugin.define({id, setup})` returns its argument typed; `setup(ctx)` may be async and may return
a cleanup. `ctx` is `Plugin.Context`: the `tool`, `skill`, `session`, `rpc`, `storage`, `permission`, `model`,
`agent`, `event`, `plugin`, `location`, `options` and `servers` domains. The entry also exports
the `Agent`, `Tool`, `Skill`, `Model`, `Location` and `Rpc` namespaces and, by name, every exported type of the
engine-side files: the domain, editor, hook, caller and handler types (`ToolContext`, `SessionIdle`, `RpcClient` ...),
the client's request and response types (`SessionInfo`, `PluginInfo` ...), `ConcivClient`, `ConcivEvent`, `ServerRef`, the client builder `Conciv` (`Conciv.make`),
and what an engine host builds a plugin's context from (`Registration`, `Transform`, `Hooks`, `Rule`, `Ruleset`). Tool and
RPC schemas are an Effect Schema, any Standard Schema (zod, Valibot, ArkType ...) or a raw JSON Schema object, as
opencode's; store schemas are Standard Schema only. A stored value that fails its store schema keeps every valid field; each failing field takes the store's
initial value (see "App part" below for where this differs from opencode).

```ts
import {z} from 'zod'
import {Plugin} from '@conciv/plugin'
import {Tanstack} from './rpc.js'

export default Plugin.define({
  id: 'tanstack',
  async setup(ctx) {
    await ctx.tool.transform((tools) => {
      tools.add({
        name: 'tanstack_routes',
        description: 'Count the app routes',
        input: z.object({}),
        output: z.object({count: z.number()}),
        execute: async () => ({output: {count: 1}}),
      })
    })
    const registration = await ctx.rpc.register(Tanstack, {routes: async () => ({routes: ['/']})})
    return () => registration.dispose()
  },
})
```

### `@conciv/plugin/effect` (`effect/index.ts`)

The engine part on Effect, opencode's `@opencode/plugin/effect`. `Plugin.define({id, effect})` returns its argument
typed; `effect(ctx)` returns an `Effect` that runs in the plugin's scope, so what it registers is removed when the
scope closes. `ctx` has the same domains as the Promise `Plugin.Context`, each returning `Effect` or `Stream`;
`servers` keeps its Promise types for now. The entry also exports the storage types and the
`Agent`, `Location`, `Model`, `Provider`, `Rpc` and `Skill` namespaces. The subpaths `./effect/plugin`,
`./effect/permission`, `./effect/rpc`, `./effect/session` and `./effect/tool` carry the domain types the engine host
imports. `@conciv/plugin/promise/adapter` holds `fromPromise`, which turns a Promise plugin into the Effect plugin the
host runs, and `./schema/<name>` each Effect Schema file. `effect` is a dependency of the SDK.

### `@conciv/plugin/rpc` (`rpc.ts`)

The `Rpc` namespace alone, for the contract module both parts import. `Rpc.define({id, methods, events})` returns
its argument typed and throws when an error name starts with `rpc.` (reserved). Method and event schemas are any
Standard Schema or a raw JSON Schema object (an event's with `type: 'object'`).

Rpc methods never ask. An operation that must ask is a tool, and gets no rpc method: the server plugin's restart
is the `server_restart` tool only.

```ts
import {z} from 'zod'
import {Rpc} from '@conciv/plugin/rpc'

export const Tanstack = Rpc.define({
  id: 'tanstack',
  methods: {routes: {input: z.object({}), output: z.object({routes: z.array(z.string())})}},
  events: {buildError: {schema: z.object({message: z.string()})}},
})
```

### `@conciv/plugin/experimental` (`experimental/index.ts`)

The browser part. `Plugin.define({stores, setup})` has no id (the host gives it the engine part's id as `ctx.id`);
`setup` is synchronous and runs under the plugin's Solid owner. `ctx.add(Registry, item)` adds to a registry
(`Panel`, `Slot`, `Command`, `ComposerPill`, `LinkHandler`, `SettingsPage`, `Server`, `CodeBlock`, `CodeBlockAction`), and
everything added is withdrawn when the plugin reloads or stops. Also exported: `Store` (`global`, `project`,
`session`), `Registry`, `Contract`, the host API types, `createKeyed`, `createLatest`, `createVisitState`,
`usePlugin`, `bindPlugin`, `usePanel` and `useDrawer`. `ctx.client.rpc(Definition)` calls the plugin's own engine
part; `ctx.servers.get(id)?.client.rpc(Definition)` calls another engine. On the engine side `ctx.servers` lists every
running conciv engine on the machine, this one included (`builtin`). A plugin in one engine can call plugins in every
other running engine on the machine without a prompt.

The browser part needs `Promise.try`: Chrome and Edge 128, Firefox 134, Safari and iOS Safari 18.2 (Node 23.0.0 for tooling that evaluates it), source MDN browser-compat-data (`javascript.builtins.Promise.try`).

```tsx
import {z} from 'zod'
import {createLatest, Panel, Plugin, Slot, Store} from '@conciv/plugin/experimental'
import {Tanstack} from './rpc.js'

export default Plugin.define({
  stores: {prefs: Store.global(z.object({open: z.boolean()}), {open: false})},
  setup(ctx) {
    const routes = createLatest(
      () => ctx.id,
      (_id, signal) => ctx.client.rpc(Tanstack).routes({}, {signal}),
    )
    ctx.add(Slot, {at: 'session.status', render: () => <span>{routes.latest?.routes.length ?? 0} routes</span>})
    ctx.add(Panel, {id: 'routes', region: 'pane', list: () => [{id: 'routes', title: 'Routes'}], render: () => <p />})
  },
})
```

### `@conciv/plugin/experimental/vite` (`experimental/vite.ts`)

`experimental(options?)` returns the Vite plugins that build a browser part into a CommonJS entry,
`dist/plugin-experimental.cjs` from `src/plugin-experimental.tsx` by default, with Vite's manifest beside it
(`dist/plugin-experimental.cjs.manifest.json`). An `import()` in the part gives an on-demand chunk: the app loads the
entry with the chunks it requires at start, and each `import()`ed chunk the first time it runs, over the engine
socket. The build fails on an import of a `@conciv/*` or `solid-js/*` module the conciv app does not provide to
plugins.

### `@conciv/plugin/experimental/page` (`experimental/page.ts`)

What the built-in page plugin offers other plugins' browser parts, shaped as opencode's `gui/browser.ts` (interface and
const of one name): the `Page` contract (`symbolicate`, `toast`, `capture` with `exclude` and `plugins`, snapdom's own `SnapdomPlugin` type, so `@zumer/snapdom` is a dependency, and `pick`, which lets the user pick an element in grab's quiet comment mode and resolves the whole `Grab`, attaching nothing, or `null` when the user cancels; a second `pick` cancels the one in flight), the `ReactTree` contract
(`page.react`: `rootFibers`, `dehydrate`, `describe`, `locate`, `frames`), the `PageOperation` registry (`page.operation`: a
named `run(input, signal)` a plugin adds for the page plugin to run as one of its operations), with `PageToastTone`, `PageCapture`, `DehydrateOptions`, `ReactFiber` and `ReactComponentInfo`.

### `@conciv/plugin/experimental/grab` (`experimental/grab.ts`)

The `GrabPicker` registry (`grab.picker`, opencode's `FileViewer` way for one plugin to supply another's
operation) and the element grab types. The registry is the only way a picker is supplied; the page plugin adds its own.

### `@conciv/plugin/host` (`host.ts`)

For the engine-side host only: `resolve(target)` finds a plugin's `server`, `rpc` and `experimental` entry files,
`load(entrypoint)` imports one, `packageId(target)` names it. Import it as a namespace:
`import * as Host from '@conciv/plugin/host'`.

### `@conciv/plugin/experimental/host` (`experimental/host.ts`)

For the browser-side host only: `compose` merges built-in and installed entries, `pluginEnabled` and
`pluginIdAvailable` decide which run, `evaluatePluginBundle` runs a prebuilt bundle with the host's `require`,
`pluginSharedModules` and `pluginWindowModules` list what that `require` provides, `inertModule` and
`mainOnlyModule` stand in for Node built-ins, `Installed` and `shipsPluginExperimental` describe installed plugins,
and `Scope` plus the Solid contexts (`PluginContext`, `LifetimeContext`, `PanelContext`, `DrawerContext`,
`liveAccessor`) are what the host mounts a plugin with.

## Differences from opencode

### Files and exports

- One opencode file is one conciv file, same name and folder. opencode's `plugin/src` is `src` (`gui/` is `experimental/`); the files conciv ports from opencode's `schema`, `client` and `util` packages sit in `src/schema/`, `src/client/` and `src/util/` (conciv has no such packages): `schema/` holds the Effect Schema files the SDK and the engine host use, each published as `./schema/<name>`; `client/` holds `shared-events.ts`, `effect/rpc.ts` (`RpcApi`, `RpcClient`, source's `@opencode/client/effect/api` members the entry uses) and `promise/` (`index`, `api`, `rpc`, `generated/types`, `generated/client`); `util/` holds `runtime-import.ts` and `runtime/import.node.ts`. `effect/` holds eleven of the source's 23 entry files, the ones for the domains conciv declares (list in "Effect entry" below). The src root keeps opencode's root files: the entries `rpc.ts` and `host.ts`, and `app.ts`, `options.ts`, `permission.ts`, `storage.ts`, whose types `.` exports by name.
- Not ported files: `schema/src/token-usage.ts` (`TokenUsage` is the generated client's `TokenUsageInfo`); opencode's other `schema`, `client` and `util` files are not used by the plugin package.
- `promise/index.ts` mirrors `plugin/src/promise/index.ts`: `PluginOptions`, the storage types and the `Plugin` namespace; of the schema namespaces it re-exports only those conciv declares (`Agent`, `Location`, `Model`, `Rpc`, `Skill`), plus `Tool`, which opencode authors import from `@opencode/schema/tool` (conciv has no schema package).
- `promise/index.ts` also exports by name every exported type of the engine-side files that no namespace carries: `promise/*.ts`, `client/promise/*.ts` (with `generated/`), `client/shared-events.ts` and the root `app.ts`, `options.ts`, `permission.ts`, `storage.ts`. opencode authors import these from `@opencode/plugin/promise/*` (its `./*` export) and `@opencode/client`; conciv has no `./*` subpaths. `promise/tool.ts`'s `Info` (the Promise tool, whose `execute` takes `ToolContext`) is `Info` at the root; the names `promise/tool.ts` re-exports from `schema/tool.ts` stay `Tool.*`.
- `promise/index.ts` exports `Registration`, `Transform` and `Hooks` (`promise/registration.ts`) and `Rule` and `Ruleset` (`schema/permission.ts`) by name: the engine host builds a plugin's context from them. `ToolHooks` stays private to `promise/tool.ts`, as in source.
- `schema/tool.ts` is source's, with Effect's `progress` and `cancel` on `Context`; `promise/tool.ts` adds the Promise `ToolContext` (without `progress` and `cancel`, as source, plus `signal` and a Promise `progress`) and its `Info`.
- `./rpc` (`rpc.ts`) is opencode's schema namespace only: `RpcApi`, `RpcArguments`, `RpcCallContext`, `RpcCallOptions`, `RpcClient`, `RpcDomain`, `RpcEventPayload`, `RpcHandlers` and `RpcRegistration` are on `.`.
- `schema/rpc.ts` does not re-export itself as `Rpc` (source does, and fallow reports that as a cycle): `promise/index.ts` and `rpc.ts`, the `./rpc` entry mirroring `plugin/src/rpc.ts`, export the namespace.
- `schema/bundler.ts` is conciv's own (opencode has no dev server): the one declaration of a dev server diagnostic and of `BundlerBridge`, the dev server seam the engine reads (`defineBundlerBridge` throws without an id), and the `bundler.diagnostic` server event the engine publishes for each diagnostic of the attached dev server. `bundler.status` says whether one is attached; the bundler is fixed for the engine's life, so the host starts each plugin event subscription that asks for `bundler.status` with the current one, as opencode's event route starts each subscription with `server.connected`. Like `schema/rpc.ts` it does not re-export itself; callers import it as a namespace.
- `client/promise/api.ts` holds `ExperimentalGenerateApi` only: source's other `*Api` types alias its generated HTTP client, which conciv does not have; the domain types inline those signatures.
- `client/promise/generated/types.ts` holds the request and response types of the client API that the domains use; `generated/client.ts` holds `RequestOptions` only.
- `promise/servers.ts` (`ServerRef`, `Servers`, for `Plugin.Context.servers`) is conciv-only.
- `experimental/core.ts` declares its own `Json` and `PluginOptions`, as source `gui/core.ts` does. `client/promise/generated/types.ts` reads `Json` from it, which makes a type-only import cycle (`experimental/core.ts`, `client/promise/index.ts`, `client/promise/rpc.ts`, `client/promise/generated/types.ts`); source avoids it with the generated client's own mutable `JsonValue`.
- `Plugin.Context.servers` is conciv's (opencode's `plugin/src/promise/plugin.ts` has no `servers`), so `ServerRef` and `Servers` live in the engine file `promise/servers.ts`, which imports nothing from `experimental/`; `experimental/host-apis.ts` re-exports them. The engine side's list is core's `provideServersSource` (`packages/core/src/runtime/servers-source.ts`): the conciv home database's engine rows after a health check, refreshed when that database changes and every 10 s (opencode's `SERVER_HEALTH_POLL_MS`), built on a plugin's first read of `servers`. The declarations of `.`, `./rpc` and `./host` import neither `solid-js` nor `vite`.
- Schema values are source's Effect Schema: `AssertInput` (root `permission.ts`) is source's struct, and `Tool.Error` is an Effect Schema with `isToolError = Schema.is(Error)`; the Promise `permission.assert` takes `AssertInput`'s encoded form, as source. The one zod check left is the private one of the `PLUGIN_RPC` and `PLUGIN_RPC_INTERNAL` errors in `makeRpc`.
- `AssertInput` has one field the source does not (named difference, ruling): `fallback?: 'ask'`, on the Effect and the Promise `permission.assert` alike. It is the tool's own ask, a default just above the agent's built-in rules: the engine adds, for each resource of the call on its own, the rule `{action, resource: <that resource>, effect: 'ask'}` after the agent's rules only when the agent's answer for that action and resource is an allow from a rule whose action is `*` (the built-in allow-all of `Agent.Info.default`). Any rule that names the action (an agent rule a plugin or config pushes, a session rule, a saved "always allow" answer) beats it in either direction, a deny from anywhere still denies, an agent that does not exist still denies everything, and a plugin's `permission.hook('evaluate')` deny, which runs after every rule, still wins. The server plugin's `server_restart` passes `fallback: 'ask'` and pushes no agent rule, so the ask cannot go missing while plugins reload. A blanket rule `{action: '*', effect: 'allow'}` does not switch the tool's own ask off, because it cannot be told apart from the built-in allow-all; a user switches it off by naming the action, as in `{action: 'server_restart', resource: '*', effect: 'allow'}`. Before, it pushed `{action: 'server_restart', resource: '*', effect: 'ask'}` onto every agent from the `post` phase, last among the agent rules, so an agent rule for `server_restart` pushed by any other plugin never switched the ask off and an agent deny asked instead of denying; now that rule is obeyed (a gain, not a regression).
- `makeRpc(raw, events)` (`client/promise/rpc.ts`, exported by name from `.`) takes the source's two arguments: `raw` is the contract client (`RpcClient`, `@conciv/contract`) in place of opencode's generated HTTP client, and `events` is the client's shared event stream (`client.event`). A call goes to `raw.plugin.call` where the source calls `raw.rpc.call`: it sends `{rpcId, method, input}` with `{signal}` (no `location`, no `headers`) and returns what the procedure answers (oRPC has no `{output}` wrapper). A failure is recognised as the contract's defined `PLUGIN_RPC` (400, source's `RpcError`) or `PLUGIN_RPC_INTERNAL` (500, source's `RpcInternalError`) error by one private zod check, in place of `isRpcError` / `isRpcInternalError`, and rejects with its `{type, message, data?}` as source does. A subscription reads the shared stream with no types and keeps the events whose `type` is `rpc.<id>.<name>`, as the source. The event generator and the `on` loop are named inner functions in place of source's two IIFEs; the input cast is dropped (the wire input is `unknown`); the two remaining casts keep source's, without its `SAFETY` comments and oxlint directives. `on` logs a handler that throws and keeps delivering (source's `on` ends on it); it has no reconnect loop of its own, as the source: it ends with the shared stream.
- `client/promise/client.ts` is the source's `make` (`client/src/promise/client.ts:12`): `SharedEvents.make((signal, onActivity) => received(raw, signal, onActivity))`. `received` is the one adapter the source does not need: oRPC's `raw.event.subscribe` answers a Promise of an iterator and takes no `onActivity`, so an async generator awaits it, calls `onActivity` for every frame and yields each frame but `server.heartbeat` (the websocket peer's stand-in for the source's SSE keepalive comment, `packages/core/src/api/rpc/README.md`), narrowed to `ConcivEvent` by a type guard on that heartbeat check. Each subscribe goes with `context: {retry: 0}`, so the transport never retries the stream itself. The shared stream ends when the engine's stream ends or fails, as the source's: a reader that wants the stream back subscribes again (the source's readers do the same).
- `client/solid/connection.ts` (exported from `./experimental/host`) is the source's `client/src/solid/connection.ts`, ported as is: `createClientConnection(client, options)` holds one reader of the shared stream and reopens it (connect timeout 2 s, idle watchdog `defaultIdleTimeout` 45 s, 1 s reconnect delay, `reconnect` option, `pageLifecycle`, connection history), and reads back `status()`, `attempt()` and `error()` from a Solid store. The widget's engine ref (`apps/conciv/src/runtime/plugin/host-apis.tsx`) makes one and passes the engine's trust wait as `reconnect`: after a drop it waits until the browser is trusted again (`browserRpcConnection(...).trust`) and returns the same client.
- `.fallowrc.json` `ignoreExports` exempts the namespace member names repeated across `packages/plugin/src` modules (opencode's names) from fallow's duplicate-export check.
- `conciv/banned-vocabulary` is off for `packages/plugin/src/**` because opencode's names are kept exactly: it rejects `Composer.attach` (`experimental/host-apis.ts`, opencode `plugin/src/gui/host-apis.ts:639`).

### Effect entry (`effect/`, `promise/adapter.ts`)

- `effect/` holds `agent`, `event`, `model`, `permission`, `plugin`, `registration`, `rpc`, `session`, `skill`, `storage`, `tool` and `index`. Not ported: `aisdk`, `artifact`, `command`, `integration`, `mcp`, `provider`, `reference`, `shell`, `vcs`, `websearch`, `worktree` (domains conciv does not declare).
- `@opencode/client/effect/api` is not ported: each `*Api<unknown>` a domain extends is inlined as the members conciv implements, or comes from `client/effect/rpc.ts`. So `agent` has no `reload`; `model` is `list` and `default` only (no `ModelEditor`, `transform`, `reload`); `skill` inlines `list`; `permission` inlines `list`, `get`, `reply`; `event` builds its output from the server events plus an `rpc.*` event.
- `plugin.ts` `Context` has only the declared domains (no `aisdk`, `command`, `credential`, `integration`, `mcp`, `generate`, `provider`, `reference`, `shell`, `vcs`, `websearch`, `worktree`, `experimental.terminal`, `experimental.artifact`) and adds conciv's `servers` with its Promise types. `session.ts` keeps the `prompt`, `context`, `compaction` and `experimental.idle` hooks (source has 15) and types its domain from the Promise client types. `storage.ts` adds `directory`. `index.ts` re-exports the schema namespaces conciv has: `Agent`, `Location`, `Model`, `Provider`, `Rpc`, `Skill`.
- `promise/adapter.ts` keeps the source's way of encoding events, one union of the server events and a generic `rpc.*` event, with conciv's rpc event fields (`created`; `location` an optional `Location.Ref`, where source's is a required `Location.PublicRef`), while the Effect `EventDomain` in `effect/event.ts` types an rpc event's `location` as `Location.PublicRef`, so for rpc events the type and the wire differ.
- OPEN: Widget first load grows 267 KB gzip; the way to get it back is subpath imports in the SDK schema files so effect's root loads lazily (measured path, not built). First load is 1,887,640 bytes gzip before and 2,161,184 after.

### Finding a plugin's parts (`host.ts`, `experimental/host.ts`)

- `host.ts` ports `plugin/src/host.ts`; it does not re-export itself as `Host` (the `schema/rpc.ts` rule above): callers import it as a namespace, `import * as Host from '@conciv/plugin/host'`.
- `Entrypoints` has `server`, `rpc` and `experimental` (source `gui`); no `tui`. Bundle file names are `plugin-experimental.*` and the package export is `./plugin-experimental`.
- The app part is a prebuilt `.cjs` or `.js` file only, for a named package and a local directory alike, built with `@conciv/plugin/experimental/vite`. TypeScript is never an app part entry.
- A local plugin's own TypeScript loads as opencode's does on Node (`@conciv/plugin-host` `plugin/source.node.ts`): Node's own type stripping loads its `.ts`, `.mts` and `.cts` files, so syntax that needs a transform (enums, namespaces with runtime code, parameter properties, import aliases) and `.tsx` files do not load: the plugin fails to load, and the engine log carries Node's error. Once Node's resolver fails, a relative import resolves by Bun's documented order for a local ESM `import` (https://bun.sh/docs/runtime/modules), less the `.tsx` and `.jsx` forms Node cannot load: `./x.js` to `x.ts`, `./x.mjs` to `x.mts`, then the path with `.mts`, `.ts`, `.mjs`, `.js`, `.cts`, `.cjs`, `.json` appended (an extensionless `./helper` too), then a folder's `index` with the same extensions. As on Bun, `./x.cjs` never maps to `x.cts`. Imports inside `node_modules` and the engine's own modules resolve as Node does.
- `resolveModule` and `importModule` are `util/runtime/import.node.ts` (the Node runtime), re-exported by `util/runtime-import.ts`; the Bun and workerd runtimes and the runtime switch are dropped. No package export reaches them.
- An absolute specifier (a local directory's conventional file) resolves by a file lookup with the same extension list instead of Node's resolver: Node refuses every file under a `package.json` that does not parse, so source's Node runtime fails source's own "package.json that does not parse" case (its tests run on Bun, whose resolver finds the file).
- A resolved specifier must be a regular file; anything else is a miss, so the next candidate is tried (a package without `exports` that has a `server/` directory gives its root `index.js` as `server`). Source runs on Bun, where the resolver finds the file; on Node, which conciv runs on, the same code returns the directory and loading fails later (opencode `util/src/runtime/import.node.ts:32`).
- The manifest is read with zod (`name`, `exports`, both unknown); a `package.json` that is not a JSON object counts as missing. Error codes are read with zod instead of `"code" in error`; `host.ts` and `util/runtime/import.node.ts` each keep their own guard, as source inlines one in each.
- The source's `//` comments are dropped; `packageID` is `packageId`.
- `experimental/host.ts` ports `Entry` (`windowEntry` only; no `mainEntry`; `stores` is `Declarations.stores`, no `BuiltinStoreDeclaration`), `compose`, `EnableState`, `pluginEnabled`, `pluginIdAvailable` (reserved namespace `conciv`), `Installed` (no `tui`, no `unsupported`) and `shipsPluginGui` as `shipsPluginExperimental`, reading `features.experimental`. It re-exports `Scope`, `pluginSharedModules`, `pluginWindowModules` and `PluginModule` from `modules.ts` and, as source does, `DrawerContext`, `LifetimeContext`, `liveAccessor`, `PanelContext` and `PluginContext` from `internal.ts`. `runsOn` is absent (no `os`); `BridgePluginExperimental` and `BridgePluginExperimentals` are ported as plain data (the plugin browser parts to run: id, revision, code, options, and the reserved ids), which the browser host's plugin-experimental machine reads and conciv's widget gets from its engine; `Bridge`, `BridgeLayout`, `BridgeMessage` and `BridgeMenubarItem` are absent (Electron bridge, no desktop main process). The file's header comment is dropped.
- The app's hot reload (`apps/conciv/src/runtime/plugin/hmr.tsx`, source `app/src/runtime/plugin/hmr.tsx`) logs a built-in's `windowEntry` import that rejects, `[plugin] <id>`, where source leaves the rejection unhandled.
- The engine serves a plugin's `./plugin-experimental` as the text it read when it loaded the plugin, under the revision hashed from that text (`@conciv/plugin-host` `core/plugin/module.ts`, `core/plugin.ts`), where source reads the file again on each fetch (`core/src/plugin.ts:58`) under the revision it hashed at load (`core/src/plugin/module.ts:142`), so a fetch between an edit and its reload got the new code under the old revision. An edited bundle reaches the app once its reload has hashed its new revision.

### Evaluating a bundle (`experimental/host.ts`, `experimental/modules.ts`)

- `PluginBundle` has `definition` and `setup` (no `main`); `definition` carries `stores`, `beforeRegister` and `enforce` (no `os`, no `i18n`).
- Added: `Declarations.beforeRegister(options)` and `enforce` (`pre` | `post`), Vite-style and not in the source. The host calls every known plugin's `beforeRegister` once, synchronously, in enforce order (every `pre`, then those without, then every `post`) when it starts, before any setup; a plugin it learns of later (an engine bundle) has its `beforeRegister` called before its own setup. A built-in's runs at the top of the app's mount, so a page-wide hook (the page plugin's React bridge) exists as early as the app can run. A throw is logged and the plugin still loads.
- `PluginBundle` also has `exports`, the bundle's `module.exports`: conciv loads a plugin's lazy chunks on demand and a chunk may require the entry (Vite writes `require("./plugin-experimental.cjs")` when the lazy part imports a value the entry exports), so the app hands a chunk the entry's exports; the source ships one file and never needs them.
- `BridgePluginExperimental` also has `file`, the entry's file name (`plugin.experimental` answers it), for the same reason: the app maps a chunk's `require("./<file>")` to the entry's exports; the source ships one file.
- `PluginBundleHost` has `require` only: `process` (`'window' | 'main'`) is absent, since it only tells the two processes apart and nothing reads it in the evaluator.
- `evaluatePluginBundle` returns every field of the default export but `setup` as the definition.

### Session

- `session.hook` is `ModelHooks<SessionHooks>` with `ModelHookOptions` (`providerId`), as the source.
- `SessionHooks` has `prompt`, `context`, `compaction` and `experimental.idle` only; `fork`, `generate`, `title`, `experimental.model.resolve`, `model.request`, `http.request`, `http.response`, `experimental.ws.handshake`, `experimental.ws.send`, `experimental.ws.receive` and `retry` are not ours, with their event types.
- `experimental.idle` runs when a run completes and no session inbox input is waiting (waiting input, such as a finished page queue's `session.synthetic` notice, wakes the session, whose completion runs it instead); it does not run after a stopped or failed run, as in opencode; a failing hook is shown to the user as an error after the completed answer (the run stays completed and its answer stays), the plugin is not disabled, the later `experimental.idle` callbacks of that trigger are skipped, the next run triggers again; no second hook exists (ruling: whiteboard drafts from such a turn stay drafts). A hook that waits on its own session (`ctx.session.wait({sessionId})`) waits until that session is stopped or the engine closes, as in opencode: the run it is the end of is still running; Stop (and `ctx.session.interrupt`) then interrupts the hook and answers that it stopped something, and an interrupted hook is not a failure (the run stays completed with no error).
- `prompt` (`SessionPrompt`, opencode `plugin/src/promise/session.ts:14-20`) runs as the source's (`core/src/session/prompt.ts:40-54`): once per new user message (a resent message whose id is already stored does not run it again), after `Plugin.awaitActivation`, before the message is stored and before the agent is called; hooks run in registration order, one after the other, on one event. When the hooks leave the event equal in value to the one they were given (compared deep, by value, against a copy taken before the first hook; no hook registered counts as unchanged), the user message is stored and sent exactly as it arrived, part for part, part metadata included; this is a difference from the source, which always stores the event's form. When a hook changed it, the event they leave is rebuilt into the stored user message: one text part with `prompt.text` (the message's text parts joined with newlines), then one part per file; part metadata is not carried over, and files are `data:` URIs only. Its `PromptInput` types (`PromptInput`, `PromptInputFileAttachment`, `PromptInputSkillAttachment`, `PromptAgentAttachment`, `PromptFileSource`) are opencode's `schema/src/prompt-input.ts` and `schema/src/prompt.ts` written as plain TypeScript and already mutable (source: `Types.DeepMutable<PromptInput.Prompt>`). `messageId` is a `string`: conciv's message ids are the client's, without opencode's `msg_` prefix. Stopping the turn while a hook still runs ends it with nothing stored, as the source's interrupted preparation.
- Members of `prompt`'s event conciv does not fill: `prompt.files[].name`, `source`, `description` and `mention` (a composer attachment reaches the engine as a bare `image` or `document` part with a `data:` URI, its file name stays in the browser), `prompt.agents` and `prompt.skills` (the composer names neither on the wire: a message carries only text, image and document parts), and `delivery`, which is always `'queue'` (the widget sends a message after the running turn ends; a value a hook sets is not read). `metadata` is filled: it is the user message's metadata as the client sent it (absent when it sent none; a message sent with notes carries opencode's `displayText`, `comments` and `attachments` keys at its top level), and when a hook changed the event, the `metadata` it leaves is stored on the user message, as the source does (`core/src/session/prompt.ts:51` and `:87`).
- A file a hook adds must be a `data:<mime>;base64,<payload>` URI: an image mime becomes an `image` part, any other a `document` part, checked against the chat part schema. Any other URI (`file:`, `media:`) fails the prompt with `Unsupported attachment URI`: conciv has no `materializeAttachment` (`core/src/session/prompt.ts:93-146`), so no file reading, size cap, mime sniffing or image resizing.
- `context` and `compaction` (`SessionContext`, `SessionCompaction`, opencode `plugin/src/promise/session.ts:25-55`) run as the source's (`core/src/session/model-request.ts:262-300` and `:444-449`): before every model request of a turn (TanStack AI's `beforeModel` config phase, once per model call of `chat()`), after `Plugin.awaitActivation`, hooks in registration order on one event; `compaction` for a compact turn, `context` for every other turn. The event is the request the turn hands the adapter: `system` (one `SystemPart` per system prompt: the configured system prompt, the plugin instructions and the code-mode preface), `messages` (the provider messages, TanStack AI's `ModelMessage`, through `@conciv/protocol/chat-message-types`), `options` (the harness's `modelOptions`, a fresh copy per request), `tools` (each offered tool's `description` and JSON Schema `input`, keyed by name), `model` (the adapter's model, the harness id as `providerId`, the session's effort as `variant`) and `agent`. What the hooks leave is what the adapter gets: the system prompts, the provider messages (the stored conversation is not changed), the `modelOptions`, and the tools, matched to the offered tool by identity, then by name, as the source; a definition that matches neither is dropped, a moved definition renames its tool, an edited `description` or `input` replaces the tool's (an unchanged `input` keeps the tool's own schema and its validation), and a removed tool is neither offered nor run (the agent loop runs only the tools of the request). Each request starts again from the turn's own values, so edits do not pile up across the model calls of one turn. A stop interrupts the hooks as `prompt`'s: an Effect hook is interrupted, a Promise hook is abandoned and runs on until it settles, the harness is not called, and the run ends stopped, not failed. `SystemPart` is opencode's `ai/src/schema/messages.ts:22-28` as a plain interface without `cache` and without the `SystemPart.make` static: a plugin pushes `{type: 'text', text}`; a part's `metadata` does not reach the request. `options` is `Record<string, unknown>` (source: generation fields and provider keys); the hook option `providerId` is not read. `SessionCompaction.result` is the source's (`plugin/src/promise/session.ts:42-53`, read at `core/src/session/compaction.ts:635` `fromHook`): a compaction hook that sets it replaces the compaction model request; the harness is not called, `summary` is stored as the compaction's assistant text (the run's one message, stamped as the compaction), and `tokens` (`TokenUsageInfo`) are recorded as the run's usage, as the source bills them. The engine carries the result in that model call's own config and the wrapped adapter answers it (`packages/ai/src/server/model-request.ts` `answeredAdapter`). Not ported from the result: `native` (a provider replacement window; conciv's CLIs keep their own transcripts) and `metadata` (the stored message keeps only TanStack's and conciv's stamps, so it would be dropped). For the CLI harnesses (Claude Code, Codex, OpenCode, the ACP ones) the request is one CLI run, which runs its own agent loop: the hooks run once per run, not before the CLI's own model calls; `system` reaches the CLI as its appended system prompt (Claude Code) or as text before the prompt (the others); `tools` are the TanStack tools the adapter bridges to the CLI over MCP, so a removed tool is not listed to the CLI; `messages` reach the CLI as its prompt, and a resumed CLI session is sent only from the last user message; `options` reach the adapter as `modelOptions`, which each adapter reads by its own keys (`permissionMode`, `sessionId`, ...) and ignores otherwise.
- `SessionIdle.background` is always empty: conciv keeps no background jobs; the CLI owns that work.
- `session.create` fails with `Session.AgentNotFoundError` for an agent other than `build`, and with `Session.NotFoundError` for a model the session's harness does not list (or lists disabled, or without the given `variant`), as `switchAgent` and `switchModel` do; nothing is created. The source accepts both unchecked (`core/src/session/session.ts:290-310`) and fails at run time, which conciv has no place to do. The errors' `sessionId` is the supplied `id`, or the id the call minted for the new session.
- `session.create`'s `id` is `string | undefined` (a `null` id is rejected, as the source). The Promise adapter decodes the `id` only, with the host's Session id schema, and passes the rest of the input through untouched, so a bad id fails the call before the session key's `create` runs; the source decodes its whole payload (`plugin/src/promise/adapter.ts:635` with `protocol/src/groups/session.ts:169`), and conciv has no schema for the rest. An `id` naming a live session returns that session unchanged, as the source (`core/src/session.ts:291-293`). An `id` naming a deleted session is refused with `Session.NotFoundError` (the same error `session.get` answers for it), and the deleted session is left as it was, so it can still be restored; an `id` naming no session at all creates a new session under that id. This differs from the source: it deletes the row outright when a session is removed (`core/src/session/projector.ts:963-966`), so its `create` with that id finds nothing and makes a fresh session (`core/src/session.ts:290-293`); conciv keeps the deleted session.
- The other session calls (`list`, `get`, `remove`, `switchAgent`, `switchModel`, `compact`, `interrupt`, `update`, `wait`, `instructions.entry.list`, `put`, `remove`) validate their input at the Promise adapter as opencode's endpoints do (`protocol/src/groups/session.ts`): the session id with the host's Session id schema, and each field the call reads with the source's schema (`list` `limit` a positive whole number, `search` a string, `archived` a boolean; `switchAgent` `agent`; `switchModel` `model` a model reference; `compact` `id` a message id; `interrupt` `resume` a boolean; `update` `title` a string, `metadata` JSON values by key, `permissions` a permission ruleset, `archived` a boolean; an instruction entry's `key` and JSON `value`). A bad value fails the call with a `SchemaError` before the session key runs; keys a call does not declare pass through untouched (the source drops them). Not validated, because conciv has no schema for them: `list`'s `order`, `parentId` (the source's id-or-null union) and `cursor` (the source's `SessionsCursor`; conciv's cursor is its own JSON, which the key refuses with `Session.InvalidListCursorError`), and `compact`'s `delivery` (the source's `SessionInbox.Delivery`); the key reads none of them except `cursor`. The SDK types stay as the source's: a `limit` that is not a positive whole number and a compact `id` that does not start with `msg_` are typed `number` and `string` but refused.
- `SessionDomain` has no `move` (not ours: one directory per engine).
- The session list input has no `directory`, `project` or `subpath`, and the session create input no `location` (one project per engine).
- `interrupt`'s `resume` is accepted and does nothing more than the stop: conciv has no steering inbox, so `resume` has nothing to wake.

### Model

- The dialog stack (`apps/conciv/src/runtime/plugin/dialog-stack.tsx`, `dialog-stack-machine.ts`) is opencode's `ui/src/context/dialog.tsx` and `dialog-machine.ts`. It lives in the app, not the kit: the kit is flat and its `dialog.tsx` is the Dialog component, its test-file budget is full, and it takes no app plumbing.
- conciv did not port opencode's code mode interpreter (TanStack's code mode runs programs), so `toolExpression` (`packages/plugin-host/src/codemode/tool-runtime.ts`) answers `external_x_y` where opencode answers `tools.x.y`: in TanStack's code mode a tool is a global function and there is no `tools` object.
- A discovered plugin's mtime leaves its browser bundle out (`packages/plugin-host/src/core/config/plugin/source.ts`), so a bundle edit reloads the browser part only. The source's `core/src/config/plugin/source.ts:180-191` includes it, although `core/src/plugin.ts:44-45` and the docs (`gui/index.mdx:225`) say a changed bundle restarts nothing.
