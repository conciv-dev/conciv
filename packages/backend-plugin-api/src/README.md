# @conciv/backend-plugin-api source

The engine side of a port of opencode's plugin package (opencode at commit `a1aa513`; every opencode path below is
relative to its `packages/` folder). The browser side is `@conciv/frontend-plugin-api`. Names and shapes are
opencode's except for the lines under "Differences from opencode". The source keeps opencode's JSDoc only where a
block carries at least one tag (`@param`, `@returns`, `@example`, `@remarks` ...) above a declaration or member: those
blocks stay whole, prose-only doc blocks are not kept (`conciv/no-comments` with `keepDocComments`). A member marked as
not implemented (below) carries only its `@remarks` line.

## Entries

A plugin has up to three parts: an engine part (runs inside the conciv engine, adds tools, skills and RPC handlers),
an RPC contract shared by both sides, and a browser part (runs in the conciv widget, written against
`@conciv/frontend-plugin-api`). This package holds the engine part and the contract.

### `@conciv/backend-plugin-api` (`promise/promise.ts`)

The engine part. `Plugin.define({id, setup})` returns its argument typed; `setup(ctx)` may be async and may return
a cleanup. `ctx` is `Plugin.Context`: the `tool`, `skill`, `session`, `rpc`, `storage`, `permission`, `model`,
`agent`, `event`, `plugin`, `location`, `options` and `servers` domains. The entry also exports
the `Agent`, `Tool`, `Skill`, `Model`, `Location` and `Rpc` namespaces and, by name, every exported type of the
engine-side files: the domain, editor, hook, caller and handler types (`ToolContext`, `SessionIdle`, `RpcClient` ...),
the client's request and response types (`SessionInfo`, `PluginInfo` ...), `ConcivClient`, `ConcivEvent`, `ServerRef`, the client builder `Conciv` (`Conciv.make`),
and what an engine host builds a plugin's context from (`Registration`, `Transform`, `Hooks`, `Rule`, `Ruleset`). Tool and
RPC schemas are an Effect Schema, any Standard Schema (zod, Valibot, ArkType ...) or a raw JSON Schema object, as
opencode's; store schemas are Standard Schema only. A stored value that fails its store schema keeps every valid field; each failing field takes the store's
initial value (see "App part" below for where this differs from opencode).

```ts
import {z} from 'zod'
import {Plugin} from '@conciv/backend-plugin-api'
import {Tanstack} from './rpc.js'

export default Plugin.define({
  id: 'tanstack',
  async setup(ctx) {
    await ctx.tool.transform((tools) => {
      tools.add({
        name: 'tanstack_routes',
        description: 'Count the app routes',
        input: z.object({}),
        output: z.object({count: z.number()}),
        execute: async () => ({output: {count: 1}}),
      })
    })
    const registration = await ctx.rpc.register(Tanstack, {routes: async () => ({routes: ['/']})})
    return () => registration.dispose()
  },
})
```

### `@conciv/backend-plugin-api/effect` (`effect/effect.ts`)

The engine part on Effect, opencode's `@opencode/plugin/effect`. `Plugin.define({id, effect})` returns its argument
typed; `effect(ctx)` returns an `Effect` that runs in the plugin's scope, so what it registers is removed when the
scope closes. `ctx` has the same domains as the Promise `Plugin.Context`, each returning `Effect` or `Stream`;
`servers` keeps its Promise types for now. The entry also exports the storage types and the
`Agent`, `Location`, `Model`, `Provider`, `Rpc` and `Skill` namespaces. The subpaths `./effect/plugin`,
`./effect/permission`, `./effect/rpc`, `./effect/session` and `./effect/tool` carry the domain types the engine host
imports. `@conciv/backend-plugin-api/promise/adapter` holds `fromPromise`, which turns a Promise plugin into the Effect plugin
the host runs. The Effect Schema files are `@conciv/protocol`'s `./schema/<name>`. `effect` is a dependency of the SDK.

### `@conciv/backend-plugin-api/rpc` (`rpc.ts`)

The `Rpc` namespace alone, for the contract module both parts import. `Rpc.define({id, methods, events})` returns
its argument typed and throws when an error name starts with `rpc.` (reserved). Method and event schemas are any
Standard Schema or a raw JSON Schema object (an event's with `type: 'object'`).

Rpc methods never ask. An operation that must ask is a tool, and gets no rpc method: the server plugin's restart
is the `server_restart` tool only.

```ts
import {z} from 'zod'
import {Rpc} from '@conciv/backend-plugin-api/rpc'

export const Tanstack = Rpc.define({
  id: 'tanstack',
  methods: {routes: {input: z.object({}), output: z.object({routes: z.array(z.string())})}},
  events: {buildError: {schema: z.object({message: z.string()})}},
})
```

### `@conciv/backend-plugin-api/host` (`host.ts`)

For the engine-side host only: `resolve(target)` finds a plugin's `server`, `rpc` and `experimental` entry files,
`load(entrypoint)` imports one, `packageId(target)` names it. Import it as a namespace:
`import * as Host from '@conciv/backend-plugin-api/host'`.

## Differences from opencode

### Files and exports

- One opencode file is one conciv file, same name and folder. opencode's `plugin/src` is `src` (its `gui/` is `@conciv/frontend-plugin-api`); the files conciv ports from opencode's `client` and `util` packages sit in `src/client/` and `src/util/`, and its `schema` files are `@conciv/protocol`'s `src/schema/` (conciv has no such packages): `client/` holds `shared-events.ts`, `effect/rpc.ts` (`RpcApi`, `RpcClient`, source's `@opencode/client/effect/api` members the entry uses) and `promise/` (`promise`, `api`, `client`, `rpc`, `generated/types`, `generated/client`); `util/` holds `runtime-import.ts` and `runtime/import.node.ts`. `effect/` holds the source's entry files for the domains conciv declares (list in "Effect entry" below). The src root keeps opencode's root files: the entries `rpc.ts` and `host.ts`, and `app.ts`, `permission.ts`, `storage.ts`, whose types `.` exports by name; `PluginOptions` is `@conciv/protocol/options`.
- Not ported files: `schema/src/token-usage.ts` (`TokenUsage` is the generated client's `TokenUsageInfo`); opencode's other `schema`, `client` and `util` files are not used by the plugin package.
- `promise/promise.ts` mirrors `plugin/src/promise/index.ts`: `PluginOptions`, the storage types and the `Plugin` namespace; of the schema namespaces it re-exports only those conciv declares (`Agent`, `Location`, `Model`, `Rpc`, `Skill`), plus `Tool`, which opencode authors import from `@opencode/schema/tool` (conciv has no schema package).
- `promise/promise.ts` also exports by name every exported type of the engine-side files that no namespace carries: `promise/*.ts`, `client/promise/*.ts` (with `generated/`), `client/shared-events.ts` and the root `app.ts`, `permission.ts`, `storage.ts`. opencode authors import these from `@opencode/plugin/promise/*` (its `./*` export) and `@opencode/client`; conciv has no `./*` subpaths. `promise/tool.ts`'s `Info` (the Promise tool, whose `execute` takes `ToolContext`) is `Info` at the root; the names `promise/tool.ts` re-exports from `@conciv/protocol` `schema/tool.ts` stay `Tool.*`.
- `promise/promise.ts` exports `Registration`, `Transform` and `Hooks` (`promise/registration.ts`) and `Rule` and `Ruleset` (`@conciv/protocol` `schema/permission.ts`) by name: the engine host builds a plugin's context from them. `ToolHooks` stays private to `promise/tool.ts`, as in source.
- `@conciv/protocol` `schema/tool.ts` is source's, with Effect's `progress` and `cancel` on `Context`; `promise/tool.ts` adds the Promise `ToolContext` (without `progress` and `cancel`, as source, plus `signal` and a Promise `progress`) and its `Info`.
- `./rpc` (`rpc.ts`) is opencode's schema namespace only: `RpcApi`, `RpcArguments`, `RpcCallContext`, `RpcCallOptions`, `RpcClient`, `RpcDomain`, `RpcEventPayload`, `RpcHandlers` and `RpcRegistration` are on `.`.
- `@conciv/protocol` `schema/rpc.ts` does not re-export itself as `Rpc` (source does, and fallow reports that as a cycle): `promise/promise.ts` and `rpc.ts`, the `./rpc` entry mirroring `plugin/src/rpc.ts`, export the namespace.
- `@conciv/protocol` `schema/bundler.ts` is conciv's own (opencode has no dev server): the one declaration of a dev server diagnostic and of `BundlerBridge`, the dev server seam the engine reads (`defineBundlerBridge` throws without an id), and the `bundler.diagnostic` server event the engine publishes for each diagnostic of the attached dev server. `bundler.status` says whether one is attached; the bundler is fixed for the engine's life, so the host starts each plugin event subscription that asks for `bundler.status` with the current one, as opencode's event route starts each subscription with `server.connected`. Like `@conciv/protocol` `schema/rpc.ts` it does not re-export itself; callers import it as a namespace.
- `client/promise/api.ts` holds `ExperimentalGenerateApi` only: source's other `*Api` types alias its generated HTTP client, which conciv does not have; the domain types inline those signatures.
- `client/promise/generated/types.ts` holds the request and response types of the client API that the domains use; `generated/client.ts` holds `RequestOptions` only.
- `promise/servers.ts` (`ServerRef`, `Servers`, for `Plugin.Context.servers`) is conciv-only.
- `Plugin.Context.servers` is conciv's (opencode's `plugin/src/promise/plugin.ts` has no `servers`), so `ServerRef` and `Servers` live in the engine file `promise/servers.ts`; `@conciv/frontend-plugin-api` (`host-apis.ts`) re-exports them. The engine side's list is core's `provideServersSource` (`packages/backend-defaults/src/engine/runtime/servers-source.ts`): the conciv home database's engine rows after a health check, refreshed when that database changes and every 10 s (opencode's `SERVER_HEALTH_POLL_MS`), built on a plugin's first read of `servers`. The declarations of `.`, `./rpc` and `./host` import neither `solid-js` nor `vite`.
- Schema values are source's Effect Schema: `AssertInput` (root `permission.ts`) is source's struct, and `Tool.Error` is an Effect Schema with `isToolError = Schema.is(Error)`; the Promise `permission.assert` takes `AssertInput`'s encoded form, as source. The one zod check left is the private one of the `PLUGIN_RPC` and `PLUGIN_RPC_INTERNAL` errors in `makeRpc`.
- `AssertInput` has one field the source does not (named difference, ruling): `fallback?: 'ask'`, on the Effect and the Promise `permission.assert` alike. It is the tool's own ask, a default just above the agent's built-in rules: the engine adds, for each resource of the call on its own, the rule `{action, resource: <that resource>, effect: 'ask'}` after the agent's rules only when the agent's answer for that action and resource is an allow from a rule whose action is `*` (the built-in allow-all of `Agent.Info.default`). Any rule that names the action (an agent rule a plugin or config pushes, a session rule, a saved "always allow" answer) beats it in either direction, a deny from anywhere still denies, an agent that does not exist still denies everything, and a plugin's `permission.hook('evaluate')` deny, which runs after every rule, still wins. The server plugin's `server_restart` passes `fallback: 'ask'` and pushes no agent rule, so the ask cannot go missing while plugins reload. A blanket rule `{action: '*', effect: 'allow'}` does not switch the tool's own ask off, because it cannot be told apart from the built-in allow-all; a user switches it off by naming the action, as in `{action: 'server_restart', resource: '*', effect: 'allow'}`. Before, it pushed `{action: 'server_restart', resource: '*', effect: 'ask'}` onto every agent from the `post` phase, last among the agent rules, so an agent rule for `server_restart` pushed by any other plugin never switched the ask off and an agent deny asked instead of denying; now that rule is obeyed (a gain, not a regression).
- `makeRpc(raw, events)` (`client/promise/rpc.ts`, exported by name from `.`) takes the source's two arguments: `raw` is the contract client (`RpcClient`, `@conciv/protocol`) in place of opencode's generated HTTP client, and `events` is the client's shared event stream (`client.event`). A call goes to `raw.plugin.call` where the source calls `raw.rpc.call`: it sends `{rpcId, method, input}` with `{signal}` (no `location`, no `headers`) and returns what the procedure answers (oRPC has no `{output}` wrapper). A failure is recognised as the contract's defined `PLUGIN_RPC` (400, source's `RpcError`) or `PLUGIN_RPC_INTERNAL` (500, source's `RpcInternalError`) error by one private zod check, in place of `isRpcError` / `isRpcInternalError`, and rejects with its `{type, message, data?}` as source does. A subscription reads the shared stream with no types and keeps the events whose `type` is `rpc.<id>.<name>`, as the source. The event generator and the `on` loop are named inner functions in place of source's two IIFEs; the input cast is dropped (the wire input is `unknown`); the two remaining casts keep source's, without its `SAFETY` comments and oxlint directives. `on` logs a handler that throws and keeps delivering (source's `on` ends on it); it has no reconnect loop of its own: the feed under the shared stream (`client/promise/client.ts`) reopens it.
- `client/promise/client.ts` feeds the shared stream through a loop, conciv's own placement: `received` reads `raw.event.subscribe`, each attempt opened with `context: {retry: 0}` so the transport never retries the stream itself (the source's stream is one SSE fetch that throws on a lost read, `client/src/promise/generated/client.ts:437`, or ends with the body, :463), and when that stream ends or fails (the socket closed, an `ORPCError`, a server feed overflow) or the subscribe is refused, it logs at info, as the source (`connection.ts:162` `options.log?.info`), with the reason as the second argument, waits 1 s flat (no backoff, no jitter, no cap, as `connection.ts:181`) and subscribes again, until the shared stream's signal aborts (the last subscriber left); each new subscription starts with `server.connected`, which `client/shared-events.ts` hands to every subscriber, their cue to resync. The loop is opencode's `runStream` (`client/src/solid/connection.ts:147-183`, `reconnectDelay = 1_000` at :33, `wait` at :267-277), but in the source only the app's own reader comes back (`runStream` is a looping reader above SharedEvents, :97, and source `client/src/promise/client.ts:12` feeds SharedEvents straight from `raw.event.subscribe`); conciv's readers of the shared stream are plugins (`rpc(...).events.on`, a direct `client.event.subscribe` reader) and the widget's plugin list (`bundle-source.ts`), which have no such layer, so the stream itself is reopened under all of them. `client/shared-events.ts` is the source's, unchanged: a subscriber that falls 4096 events behind is failed, as the source, and stays failed. Not ported from `connection.ts`: the connect timeout and the attempt counter. Each subscribe waits for the socket's next open or close before it is sent (the connection driver in `packages/client/src/engine-connection.ts`, which settles every call against its machine in `engine-connection-machine.ts`); the transport's own unlimited retry of a streaming call (the driver's `retryDelay`, which waits for the socket to reopen) is switched off for the event stream by `retry: 0`, so a socket close reaches `received`. conciv's one socket carries every call, so a 2 s bound on the first frame would show a slow engine as a lost one; the watchdog's 45 s from the start of the attempt bounds that wait instead. The connection status is the source's (`connection.ts:5` `ClientConnectionStatus`, `'connected' | 'connecting' | 'reconnecting'`, starting at `'connecting'`, :44-48) with the source's transitions, kept beside `received` where the source keeps it in a Solid store inside `createClientConnection`: the status lives with the loop, in the promise client, because the loop does (named difference, ruling). `received` sets `'connected'` when an attempt's `server.connected` arrives (:106-115), `'reconnecting'` when an attempt ends, fails, is refused or stalls (:163; the next attempt keeps it, :150), and `'connecting'` when the shared stream's signal aborts, the last subscriber leaving (the source's `stop()`, :208). `ConcivClient.connection` reads it as the source's `connection.status()` (:251) does, a plain value, plus `on(listener)`, called on each change and returning its unsubscribe, because the promise client has no Solid store for a reader to track. The idle timeout is the source's option: `Conciv.make(raw, {idleTimeout})` (`connection.ts:25` `readonly idleTimeout?: number`, read as `options.idleTimeout ?? defaultIdleTimeout` at :43). The idle watchdog is the source's (`connection.ts:35` `defaultIdleTimeout = 45_000`, `touch` at :87-92, :112, :126, cleared at :142), in `received` beside the loop: the 45 s timer starts with the attempt, before its first frame (the source arms it at `server.connected`, :112, and bounds the wait for that first frame with its 2 s connect timeout instead), and every frame of the attempt, `server.connected` first, rearms it and calls `onActivity`; when the timer fires it aborts that attempt's subscribe with `new DOMException('Event stream stalled', 'TimeoutError')` (the source aborts with `new Error('Event stream stalled')`), the loop logs it, waits 1 s and subscribes again; the timer is cleared when the attempt ends. The reason is the platform's timeout type so the widget's transport can tell a stall from any other abort: in the source the stream is an SSE fetch, and aborting it drops the connection that carries it; in the widget the stream rides the contract's one socket, so a streaming call aborted with a `TimeoutError` while that socket is open reconnects the socket once (the driver in `packages/client/src/engine-connection.ts` sends its machine a `stalled` event, which drops the open socket and connects again), and the next subscribe goes over the new socket. On the Node fetch path the abort ends the request, as in the source. A quiet healthy stream is not cut because the engine sends a `server.heartbeat` frame every 15 s by default (`packages/backend-defaults/src/engine/api/rpc/router.ts` `eventStream`, the source's `server/src/handlers/event.ts:23-25` as a frame, since the websocket peer has no SSE comment, `packages/backend-defaults/src/engine/api/rpc/README.md`); `received` counts it as activity and never yields it, and it is not a `ConcivEvent`.
- `conciv/banned-vocabulary` is off for `packages/backend-plugin-api/src/**` (`.oxlintrc.json`) because opencode's names are kept exactly.

### Effect entry (`effect/`, `promise/adapter.ts`)

- `effect/` holds `agent`, `event`, `model`, `permission`, `plugin`, `registration`, `rpc`, `session`, `skill`, `storage`, `tool` and the entry `effect`. Not ported: `aisdk`, `artifact`, `command`, `integration`, `mcp`, `provider`, `reference`, `shell`, `vcs`, `websearch`, `worktree` (domains conciv does not declare).
- `@opencode/client/effect/api` is not ported: each `*Api<unknown>` a domain extends is inlined as the members conciv implements, or comes from `client/effect/rpc.ts`. So `agent` has no `reload`; `model` is `list` and `default` only (no `ModelEditor`, `transform`, `reload`); `skill` inlines `list`; `permission` inlines `list`, `get`, `reply`; `event` builds its output from the server events plus an `rpc.*` event.
- `plugin.ts` `Context` has only the declared domains (no `aisdk`, `command`, `credential`, `integration`, `mcp`, `generate`, `provider`, `reference`, `shell`, `vcs`, `websearch`, `worktree`, `experimental.terminal`, `experimental.artifact`) and adds conciv's `servers` with its Promise types. `session.ts` keeps the `prompt`, `context`, `compaction` and `experimental.idle` hooks (source has 15) and types its domain from the Promise client types. `storage.ts` adds `directory`. `effect.ts` re-exports the schema namespaces conciv has: `Agent`, `Location`, `Model`, `Provider`, `Rpc`, `Skill`.
- `promise/adapter.ts` keeps the source's way of encoding events, one union of the server events and a generic `rpc.*` event, with conciv's rpc event fields (`created`; `location` an optional `Location.Ref`, where source's is a required `Location.PublicRef`), while the Effect `EventDomain` in `effect/event.ts` types an rpc event's `location` as `Location.PublicRef`, so for rpc events the type and the wire differ.
- OPEN: Widget first load grows 267 KB gzip; the way to get it back is subpath imports in the SDK schema files so effect's root loads lazily (measured path, not built). First load is 1,887,640 bytes gzip before and 2,161,184 after.

### Finding a plugin's parts (`host.ts`)

- `host.ts` ports `plugin/src/host.ts`; it does not re-export itself as `Host` (the `@conciv/protocol` `schema/rpc.ts` rule above): callers import it as a namespace, `import * as Host from '@conciv/backend-plugin-api/host'`.
- `Entrypoints` has `server`, `rpc` and `experimental` (source `gui`); no `tui`. Bundle file names are `plugin-experimental.*` and the package export is `./plugin-experimental`.
- A local plugin's own TypeScript loads as opencode's does on Node (`@conciv/backend-app-api` `src/plugin/source.node.ts`): Node's own type stripping loads its `.ts`, `.mts` and `.cts` files, so syntax that needs a transform (enums, namespaces with runtime code, parameter properties, import aliases) and `.tsx` files do not load: the plugin fails to load, and the engine log carries Node's error. Once Node's resolver fails, a relative import resolves by Bun's documented order for a local ESM `import` (https://bun.sh/docs/runtime/modules), less the `.tsx` and `.jsx` forms Node cannot load: `./x.js` to `x.ts`, `./x.mjs` to `x.mts`, then the path with `.mts`, `.ts`, `.mjs`, `.js`, `.cts`, `.cjs`, `.json` appended (an extensionless `./helper` too), then a folder's `index` with the same extensions. As on Bun, `./x.cjs` never maps to `x.cts`. Imports inside `node_modules` and the engine's own modules resolve as Node does.
- `resolveModule` and `importModule` are `util/runtime/import.node.ts` (the Node runtime), re-exported by `util/runtime-import.ts`; the Bun and workerd runtimes and the runtime switch are dropped. No package export reaches them.
- An absolute specifier (a local directory's conventional file) resolves by a file lookup with the same extension list instead of Node's resolver: Node refuses every file under a `package.json` that does not parse, so source's Node runtime fails source's own "package.json that does not parse" case (its tests run on Bun, whose resolver finds the file).
- A resolved specifier must be a regular file; anything else is a miss, so the next candidate is tried (a package without `exports` that has a `server/` directory gives its root `index.js` as `server`). Source runs on Bun, where the resolver finds the file; on Node, which conciv runs on, the same code returns the directory and loading fails later (opencode `util/src/runtime/import.node.ts:32`).
- The manifest is read with zod (`name`, `exports`, both unknown); a `package.json` that is not a JSON object counts as missing. Error codes are read with zod instead of `"code" in error`; `host.ts` and `util/runtime/import.node.ts` each keep their own guard, as source inlines one in each.
- The source's `//` comments are dropped; `packageID` is `packageId`.
- The engine serves a plugin's `./plugin-experimental` as the text it read when it loaded the plugin, under the revision hashed from that text (`@conciv/backend-app-api` `src/core/plugin/module.ts`, `src/core/plugin.ts`), where source reads the file again on each fetch (`core/src/plugin.ts:58`) under the revision it hashed at load (`core/src/plugin/module.ts:142`), so a fetch between an edit and its reload got the new code under the old revision. An edited bundle reaches the app once its reload has hashed its new revision.

### Names and types

- `ID` is spelled `Id` (`sessionId`, `messageId`, `requestId`, `parentId`, `modelId`, `providerId`, `workspaceId`, `shellId`, `partId`).
- Branded ids (`Event.Id`, `Skill.Id`, `Skill.Name`, `Tool.CallId`, `Agent.Id`, `Agent.Name`, `Model.Id`, `Provider.Id`, `Permission.Id`) are source's Effect Schema brands, built with the schema's makers (`Skill.Id.make('deploy')`); session ids check the `ses_` prefix and `Session.Id.create()` makes one (`ses_` + descending, as opencode).
- No `any`: `PluginOptions` values are `Json`; `Tool.Metadata` is `Readonly<Record<string, unknown>>`. `Tool.ValueSchema`, `InputValue` and `OutputValue` keep source's `any` (`schema/src/tool.ts:61-76`).
- `Types.Mutable` / `Types.DeepMutable` become a mapped type that drops `readonly` one level deep (the edited values are flat); `ModelEditor` hands out `Model.Info` as is.
- `Tool.Info.execute` uses method syntax, so a `Tool.Info<Input, Output>` is assignable to `Tool.Info` without `any`.
- `Tool.ValueSchema` is source's `Schema.Codec<A, any> | StandardSchemaV1<any, A> | JsonSchema.JsonSchema` (`schema/src/tool.ts:61`), so `Tool.Info.input` and `output` and RPC method, error and event schemas take an Effect Schema, any Standard Schema or a raw JSON Schema object, as opencode's. Store schemas are Standard Schemas only: opencode's store bound is an Effect codec (`plugin/src/gui/core.ts:458`) and takes no JSON Schema.
- `Tool.Error` is source's Effect Schema tagged struct; `toolError({message, error?, metadata?})` takes the same input as opencode's `new Tool.Error({...})` (`schema/src/tool.ts:78-82`) and, like that class, returns an `Error` carrying those fields, so a thrown tool error keeps its message and metadata in the host and carries its cause in `error`; `isToolError()` checks it.
- A failed tool call's `metadata` stays in the host and the model gets the message, but the session's recorded failure carries no metadata (as a successful result's metadata today): opencode keeps it on the stored failed part (`core/src/session/runner/step.ts:154-155`). The recorded tool result has no slot a server tool can fill.
- `Tool.Freeform`, `Tool.FreeformFormat` and `Tool.Info.freeform` are absent: MCP takes JSON input only.
- `Tool.Context.messageId`, `ToolContext.messageId` and the tool hooks' `messageId` are `string | undefined` (calls arrive from the CLI over MCP).
- `Tool.Context.origin` (and `ToolContext.origin`), type `Tool.Origin` (`'hub' | 'chat'`), is conciv's: the engine sets `'hub'` for a call an outside (hub) agent made, from the call trace, and `'chat'` otherwise.
- `Permission` `source.messageId` accepts `undefined` for the same reason.
- RPC schemas are source's (`schema/src/rpc.ts`): methods and events take `Tool.ValueSchema`, Effect Schema included; the `Portable*` types leave Effect Schema out.
- `Rpc.EventPayload` builds on `PayloadBase` (`schema/src/event.ts`, private there, exported from `@conciv/protocol` `schema/event.ts` for it) in place of `Event.Payload`, which is not ported; no `durable` (RPC events are ephemeral). `RpcEventPayload` derives from the `rpc.*` member of `ConcivEvent`, as source derives it from `OpenCodeEvent`.
- `RpcCallOptions` is `RequestOptions` (`{signal}`), without `location` (one project per engine).
- `Conciv.make(raw, {server})` (`client/promise/client.ts`) is the source's one client builder (`client/src/promise/client.ts`), and `ConcivClient` is its return type as `OpenCodeClient` is (`client/src/promise/index.ts:29`). `ServerRef.client` and `BaseContext.client` are `ConcivClient`. It takes the contract client (`RpcClient`, built by `@conciv/client`: `makeRpcClient` over fetch, or the widget's WebSocket connection) where the source's `make(options)` builds its one generated client. It returns a plain object: the contract's 18 groups written out and checked against the contract at compile time (oRPC's client is a Proxy, so the source's `{...raw}` would copy nothing), `rpc` as `Object.assign(makeRpc(raw, events, options.server), {call: raw.plugin.call})` (conciv's counterpart of the source's `raw.rpc` group, whose one member is `call`), and `event`, `SharedEvents.make` over the contract's `event.subscribe`. `server` names the engine the client talks to (the widget passes its api base, the engine list each engine's): every rpc method's query key carries it as `['plugin', {server}, id, method, input?]`, so two engines never share a cached read; the engine's own in-process client uses `in-process`. oRPC hides its keepalive frames, so `onActivity` is called once per event received (ruling). The return type is written out (`Omit<RpcClient, 'event'> & {rpc, event}`) because the inferred one names contract types `tsc` cannot emit. `@conciv/protocol` is a dependency for the contract and its type.
- One of those groups is `experimental`, which holds the session terminal: `ctx.client.experimental.persistentPty.create` opens the session's terminal (or returns the one already open), `remove` closes it, `output` streams it (replay from a cursor, a meta frame with the absolute cursor, then live output), and `write`, `resize` and `inject` drive it.
- The one cast in the SDK's conciv-written code: `client/promise/client.ts` yields each received envelope `as EventSubscribeOutput`, the source's own `yield JSON.parse(data) as A` (`client/src/promise/generated/client.ts:457`): the contract validates the envelope, the precise union is the SDK's type (ruling). No lint rule flags it, so it carries no directive.
- `ServerRef` fields that differ from opencode's browser meaning: `name` is the folder name of the engine's project root (opencode: the connection's label); `url` is the engine's bare origin and there is no `password`: the engine's client carries the engine token from the home database row itself; `local` is always true (an engine binds 127.0.0.1 only); `connected` is whether the last health check reached the engine (opencode: the event connection's status); `compatible` is true until a call to that engine fails because the engine is too old for this contract (a missing procedure or an answer outside the contract, `engineTooOld` in `@conciv/client`), then false until that engine's home database row changes, e.g. it restarts (opencode's is false only for a plugin-contributed server that declares itself incompatible, `app/src/runtime/server/health-machine.ts:164-166`).

### Context members

- Absent, not ours: `aisdk`, `credential`, `integration`, `mcp`, `provider`, `reference`, `shell`, `vcs`, `websearch`, `worktree`, `experimental.terminal`, `experimental.artifact`. Also absent: top-level `generate` (deprecated in source; `experimental.generate` replaces it).
- Added by ruling: `servers`, `storage.directory`.
- `servers` (engine side, conciv-only: opencode's engine plugins have no `servers`) lists every running conciv engine on the machine; `get(id)` is `undefined` for an id not listed, and the same ref for the same id. Before the first health check after a plugin's first read, `list()` is empty.
- `app` is typed `App | undefined` where the source types it `App`; the engine always sets it: `name` is `conciv`, `version` is the `@conciv/backend-defaults` package version, `channel` is `unknown` (`packages/backend-defaults/src/engine/runtime/plugin-runtime.ts` `provideApp`, `App.make`).
- `plugin.list`, `skill.list`, `model.list`, `model.default`: no `location` input (one project per engine); every domain method's request options are `{signal}` only (no `headers`, no `onActivity`).

### Agent and events

- `agent` is ported for permission rules only (ruling; conciv runs one agent per session): `AgentDomain` has `transform` alone, without `AgentApi`'s `list` and `get` and without `reload`; `AgentEditor` has `list` alone, without `get`, `default`, `update` and `remove`.
- `Agent.Info`, `Agent.Color`, `Agent.Info.default` and `Agent.Event` (`agent.updated`) are the source's; conciv's engine reads only `id`, `name` and `permissions` (the other agent settings are the CLI's).
- The agent editor's `Types.DeepMutable<Agent.Info>` is a mapped type that drops `readonly` from the info and from each permission rule.
- `ConcivEvent` is opencode's `OpenCodeEvent` (`protocol/src/groups/event.ts:82`) cut to what conciv's bus publishes plus `server.connected` and `rpc.*`: `agent.updated`, `skill.updated`, `plugin.updated`, `bundler.diagnostic` (conciv's own: each diagnostic of the attached dev server), `bundler.status` (conciv's own: whether a dev server is attached), `permission.asked`, `permission.replied`, `session.created`, `session.renamed`, `session.deleted`, `session.execution.started`, `.succeeded`, `.failed` and `.interrupted`, `session.instructions.updated`, each the source's generated member type, with field names and values as the engine sends them (`session.execution.failed` carries `error` as a string, the host's `schema/session-event.ts`, where the source carries a `SessionStructuredError`): `sessionID` on session events, `sessionId` / `requestId` on permission events (the host's `@conciv/protocol` `schema/permission.ts`). `id` is a string, `metadata` `Record<string, unknown>`, the durable members carry the source's `durable: {aggregateID, seq, version: 2}`.
- `server.connected` is in `ConcivEvent` as the source's `V2EventServerConnected`; `EventDomain`'s event type excludes it, as the source's.
- The engine's event stream (`event.subscribe`) carries what conciv's bus publishes: `agent.updated`, `session.created`, `session.renamed`, `session.deleted`, `session.instructions.updated`, `session.inbox.enqueued`, `session.inbox.delivered`, `session.execution.started`, `.succeeded`, `.failed` and `.interrupted`, `permission.asked`, `permission.replied`, `plugin.updated`, `skill.updated`, `rpc.*`, plus `server.connected` first and a `server.heartbeat` frame every 15 s by default, which the client counts as activity and never hands to a reader. The other source server events are not carried, each added when its feature publishes it: `location.shutdown`, `models-dev.refreshed`, `credential.updated`, `credential.switched`, `integration.updated`, `provider.updated`, `model.updated`, `session.agent.selected`, `session.model.selected`, `session.moved`, `session.metadata.updated`, `session.permissions`, `session.viewed`, `session.archived`, `session.unarchived`, `session.usage.updated`, `session.forked`, `session.synthetic`, `session.skill.activated`, `session.shell.*`, `session.step.*`, `session.text.*`, `session.reasoning.*`, `session.tool.*`, `session.retry.scheduled`, `session.compaction.*`, `session.revert.*`, `session.status`, `session.idle`, `filesystem.changed`, `reference.updated`, `project.updated`, `worktree.updated`, `worktree.resolved`, `command.updated`, `config.updated`, `pty.*`, `persistent-pty.*`, `shell.*`, `form.*`, `websearch.updated`, `artifact.updated`, `tui.*`, `installation.updated`, `installation.update-available`, `vcs.branch.updated`, `mcp.status.changed`, `mcp.resources.changed`, `experimental.mcp.event`. `session.viewed`, `.archived`, `.unarchived` and `.synthetic` have definitions in the host but no publisher yet, and `session.inbox.cancelled` and `session.inbox.delivery.changed` have their definitions and projectors, published by the inbox's `cancel`, `steer` and `queue`, which nothing calls yet.
- `SubscribeOptions` has the source's `onActivity`, and `client/shared-events.ts` holds the source's `SharedEvents.make` in full; `Conciv.make` wires it as `client.event`.

### Session

- `session.hook` is `ModelHooks<SessionHooks>` with `ModelHookOptions` (`providerId`), as the source.
- `SessionHooks` has `prompt`, `context`, `compaction` and `experimental.idle` only; `fork`, `generate`, `title`, `experimental.model.resolve`, `model.request`, `http.request`, `http.response`, `experimental.ws.handshake`, `experimental.ws.send`, `experimental.ws.receive` and `retry` are not ours, with their event types.
- `experimental.idle` runs when a run completes and no session inbox input is waiting (waiting input, such as a finished page queue's `session.synthetic` notice, wakes the session, whose completion runs it instead); it does not run after a stopped or failed run, as in opencode; a failing hook is shown to the user as an error after the completed answer (the run stays completed and its answer stays), the plugin is not disabled, the later `experimental.idle` callbacks of that trigger are skipped, the next run triggers again; no second hook exists (ruling: whiteboard drafts from such a turn stay drafts). A hook that waits on its own session (`ctx.session.wait({sessionId})`) waits until that session is stopped or the engine closes, as in opencode: the run it is the end of is still running; Stop (and `ctx.session.interrupt`) then interrupts the hook and answers that it stopped something, and an interrupted hook is not a failure (the run stays completed with no error).
- `prompt` (`SessionPrompt`, opencode `plugin/src/promise/session.ts:14-20`) runs as the source's (`core/src/session/prompt.ts:40-54`): once per new user message (a resent message whose id is already stored does not run it again), after `Plugin.awaitActivation`, before the message is stored and before the agent is called; hooks run in registration order, one after the other, on one event. When the hooks leave the event equal in value to the one they were given (compared deep, by value, against a copy taken before the first hook; no hook registered counts as unchanged), the user message is stored and sent exactly as it arrived, part for part, part metadata included; this is a difference from the source, which always stores the event's form. When a hook changed it, the event they leave is rebuilt into the stored user message: one text part with `prompt.text` (the message's text parts joined with newlines), then one part per file; part metadata is not carried over, and files are `data:` URIs only. Its `PromptInput` types (`PromptInput`, `PromptInputFileAttachment`, `PromptInputSkillAttachment`, `PromptAgentAttachment`, `PromptFileSource`) are opencode's `schema/src/prompt-input.ts` and `schema/src/prompt.ts` written as plain TypeScript and already mutable (source: `Types.DeepMutable<PromptInput.Prompt>`). `messageId` is a `string`: conciv's message ids are the client's, without opencode's `msg_` prefix. Stopping the turn while a hook still runs ends it with nothing stored, as the source's interrupted preparation.
- Members of `prompt`'s event conciv does not fill: `prompt.files[].name`, `source`, `description` and `mention` (a composer attachment reaches the engine as a bare `image` or `document` part with a `data:` URI, its file name stays in the browser), `prompt.agents` and `prompt.skills` (the composer names neither on the wire: a message carries only text, image and document parts), and `delivery`, which is always `'queue'` (the widget sends a message after the running turn ends; a value a hook sets is not read). `metadata` is filled: it is the user message's metadata as the client sent it (absent when it sent none; a message sent with notes carries opencode's `displayText`, `comments` and `attachments` keys at its top level), and when a hook changed the event, the `metadata` it leaves is stored on the user message, as the source does (`core/src/session/prompt.ts:51` and `:87`).
- A file a hook adds must be a `data:<mime>;base64,<payload>` URI: an image mime becomes an `image` part, any other a `document` part, checked against the chat part schema. Any other URI (`file:`, `media:`) fails the prompt with `Unsupported attachment URI`: conciv has no `materializeAttachment` (`core/src/session/prompt.ts:93-146`), so no file reading, size cap, mime sniffing or image resizing.
- `context` and `compaction` (`SessionContext`, `SessionCompaction`, opencode `plugin/src/promise/session.ts:25-55`) run as the source's (`core/src/session/model-request.ts:262-300` and `:444-449`): before every model request of a turn (TanStack AI's `beforeModel` config phase, once per model call of `chat()`), after `Plugin.awaitActivation`, hooks in registration order on one event; `compaction` for a compact turn, `context` for every other turn. The event is the request the turn hands the adapter: `system` (one `SystemPart` per system prompt: the configured system prompt, the plugin instructions and the code-mode preface), `messages` (the provider messages, TanStack AI's `ModelMessage`, through `@conciv/protocol/chat-message-types`), `options` (the harness's `modelOptions`, a fresh copy per request), `tools` (each offered tool's `description` and JSON Schema `input`, keyed by name), `model` (the adapter's model, the harness id as `providerId`, the session's effort as `variant`) and `agent`. What the hooks leave is what the adapter gets: the system prompts, the provider messages (the stored conversation is not changed), the `modelOptions`, and the tools, matched to the offered tool by identity, then by name, as the source; a definition that matches neither is dropped, a moved definition renames its tool, an edited `description` or `input` replaces the tool's (an unchanged `input` keeps the tool's own schema and its validation), and a removed tool is neither offered nor run (the agent loop runs only the tools of the request). Each request starts again from the turn's own values, so edits do not pile up across the model calls of one turn. A stop interrupts the hooks as `prompt`'s: an Effect hook is interrupted, a Promise hook is abandoned and runs on until it settles, the harness is not called, and the run ends stopped, not failed. `SystemPart` is opencode's `ai/src/schema/messages.ts:22-28` as a plain interface without `cache` and without the `SystemPart.make` static: a plugin pushes `{type: 'text', text}`; a part's `metadata` does not reach the request. `options` is `Record<string, unknown>` (source: generation fields and provider keys); the hook option `providerId` is not read. `SessionCompaction.result` is the source's (`plugin/src/promise/session.ts:42-53`, read at `core/src/session/compaction.ts:635` `fromHook`): a compaction hook that sets it replaces the compaction model request; the harness is not called, `summary` is stored as the compaction's assistant text (the run's one message, stamped as the compaction), and `tokens` (`TokenUsageInfo`) are recorded as the run's usage, as the source bills them. The engine carries the result in that model call's own config and the wrapped adapter answers it (`packages/backend-defaults/src/ai/model-request.ts` `answeredAdapter`). Not ported from the result: `native` (a provider replacement window; conciv's CLIs keep their own transcripts) and `metadata` (the stored message keeps only TanStack's and conciv's stamps, so it would be dropped). For the CLI harnesses (Claude Code, Codex, OpenCode, the ACP ones) the request is one CLI run, which runs its own agent loop: the hooks run once per run, not before the CLI's own model calls; `system` reaches the CLI as its appended system prompt (Claude Code) or as text before the prompt (the others); `tools` are the TanStack tools the adapter bridges to the CLI over MCP, so a removed tool is not listed to the CLI; `messages` reach the CLI as its prompt, and a resumed CLI session is sent only from the last user message; `options` reach the adapter as `modelOptions`, which each adapter reads by its own keys (`permissionMode`, `sessionId`, ...) and ignores otherwise.
- `SessionIdle.background` is always empty: conciv keeps no background jobs; the CLI owns that work.
- `session.create` fails with `Session.AgentNotFoundError` for an agent other than `build`, and with `Session.NotFoundError` for a model the session's harness does not list (or lists disabled, or without the given `variant`), as `switchAgent` and `switchModel` do; nothing is created. The source accepts both unchecked (`core/src/session/session.ts:290-310`) and fails at run time, which conciv has no place to do. The errors' `sessionId` is the supplied `id`, or the id the call minted for the new session.
- `session.create`'s `id` is `string | undefined` (a `null` id is rejected, as the source). The Promise adapter decodes the `id` only, with the host's Session id schema, and passes the rest of the input through untouched, so a bad id fails the call before the session key's `create` runs; the source decodes its whole payload (`plugin/src/promise/adapter.ts:635` with `protocol/src/groups/session.ts:169`), and conciv has no schema for the rest. An `id` naming a live session returns that session unchanged, as the source (`core/src/session.ts:291-293`). An `id` naming a deleted session is refused with `Session.NotFoundError` (the same error `session.get` answers for it), and the deleted session is left as it was, so it can still be restored; an `id` naming no session at all creates a new session under that id. This differs from the source: it deletes the row outright when a session is removed (`core/src/session/projector.ts:963-966`), so its `create` with that id finds nothing and makes a fresh session (`core/src/session.ts:290-293`); conciv keeps the deleted session.
- The other session calls (`list`, `get`, `remove`, `switchAgent`, `switchModel`, `compact`, `interrupt`, `update`, `wait`, `instructions.entry.list`, `put`, `remove`) validate their input at the Promise adapter as opencode's endpoints do (`protocol/src/groups/session.ts`): the session id with the host's Session id schema, and each field the call reads with the source's schema (`list` `limit` a positive whole number, `search` a string, `archived` a boolean; `switchAgent` `agent`; `switchModel` `model` a model reference; `compact` `id` a message id; `interrupt` `resume` a boolean; `update` `title` a string, `metadata` JSON values by key, `permissions` a permission ruleset, `archived` a boolean; an instruction entry's `key` and JSON `value`). A bad value fails the call with a `SchemaError` before the session key runs; keys a call does not declare pass through untouched (the source drops them). Not validated, because conciv has no schema for them: `list`'s `order`, `parentId` (the source's id-or-null union) and `cursor` (the source's `SessionsCursor`; conciv's cursor is its own JSON, which the key refuses with `Session.InvalidListCursorError`), and `compact`'s `delivery` (the source's `SessionInbox.Delivery`); the key reads none of them except `cursor`. The SDK types stay as the source's: a `limit` that is not a positive whole number and a compact `id` that does not start with `msg_` are typed `number` and `string` but refused.
- `SessionDomain` has no `move` (not ours: one directory per engine).
- The session list input has no `directory`, `project` or `subpath`, and the session create input no `location` (one project per engine).
- `interrupt`'s `resume` is accepted and does nothing more than the stop: conciv has no steering inbox, so `resume` has nothing to wake.

### Model

- `Model` keeps `Id`, `VariantId`, `Ref`, `Family`, `Type`, `Settings`, `Overlays`, `Capabilities`, `Cost`, `Variant` and `Info`; `Event` is not ported, and `Compatibility` is not exported (it types `Info.compatibility` only).
- `Model.Ref.providerId` is the session's harness id (`claude`, `codex` ...), as `Model.Info.providerId` and `SessionInfo.model` are (a model's provider is the harness); it is typed `string | undefined` where the source requires it. `Model.Ref.variant` is the session's reasoning effort, absent when none is set (`packages/backend-defaults/src/engine/runtime/plugin-sessions.ts`). A `Model.Ref` whose `providerId` is not the session's harness answers not-found.
- `Model.Info` keeps the source's `compatibility`, `package`, `settings`, `headers` and `body`; conciv fills none of them (provider wire settings are not ours).
- `Model.Variant` is the source's, with `Record<string, any>` typed `Record<string, unknown>`; conciv fills only `settings.effort` today, from the harness's efforts (`packages/backend-defaults/src/engine/runtime/plugin-runtime.ts`, `variants` from `model.efforts`).
- `ModelEditor.provider` is absent: providers are not ours.

### Skill and servers

- `Skill.DirectorySource`, `Skill.UrlSource`, `Skill.EmbeddedSource`, `Skill.Source` and `Skill.Event` are the source's; a plugin adds skills through `ctx.skill.transform` and never names a source.
- Where skills come from, besides plugins: the engine's `conciv.config.skill` plugin (a port of opencode's `ConfigSkillPlugin`, `core/src/config/plugin/skill.ts`) scans `skill/` and `skills/` in conciv's home (opencode's global config directory) and in the project's `conciv/` folder (opencode's `.opencode/`), in that order, so a project skill replaces a home skill of the same id. A skill is a folder holding `SKILL.md` (searched six folders deep) or a loose `*.md` at the root of one of those folders; its id is the folder (or file) name. Frontmatter `name`, `description`, `disable-model-invocation` and `metadata["conciv/autoinvoke"]` (opencode's `opencode/autoinvoke`) are read, with `js-yaml` where opencode uses `gray-matter`. A change in a watched folder rescans after 100 ms. Without the native watcher binding, a change inside an existing skills folder is not seen until the engine restarts; adding the folder is seen.
- Built-in skills: the engine's `conciv.skill` plugin (a port of opencode's `SkillPlugin`, `core/src/plugin/skill.ts`) adds `conciv` (points the agent at conciv's documentation, opencode's `opencode`) and `report` (how to report a conciv issue with the GitHub CLI), at `skill://conciv/SKILL.md` and `skill://report/SKILL.md`. Their text is conciv's own, kept in `skill/conciv.md` and `skill/report.md` beside the plugin. The report skill ends with a snapshot taken when it is registered: conciv's version, Node, the OS and the configured plugins (sorted, or `None found in config`); the source's terminal and shell lines are not carried (they read environment variables, and the snapshot carries none), and no harness line (the harness is chosen per session).
- Not ported from opencode's skill sources: the walk up from the project to find more `conciv/` folders, opencode's managed system directory, the `skills` config key (paths and URLs, with `SkillDiscovery`), and the rescan on `config.updated` (conciv has no config service). `ConfigCompatibilityPlugin` (`.claude/skills`, `.agents/skills`) is not ported either: the agent CLIs conciv runs load those folders themselves, so listing them again would offer every such skill twice.

### Files outside this package

- conciv did not port opencode's code mode interpreter (TanStack's code mode runs programs), so `toolExpression` (`packages/backend-defaults/src/codemode/tool-runtime.ts`) answers `external_x_y` where opencode answers `tools.x.y`: in TanStack's code mode a tool is a global function and there is no `tools` object.
- A discovered plugin's mtime leaves its browser bundle out (`packages/backend-app-api/src/core/config/plugin/source.ts`), so a bundle edit reloads the browser part only. The source's `core/src/config/plugin/source.ts:180-191` includes it, although `core/src/plugin.ts:44-45` and the docs (`gui/index.mdx:225`) say a changed bundle restarts nothing.
