# plugin-testkit src

## Purpose

The engine a test makes, the mount that shows the app on it, and the vitest projects that wire both per place a test runs.

## Files

- `node.ts`, `browser.ts`: the two public entries.
- `../bin/conciv-test.js`: the `conciv-test` bin, committed so it exists at install time; it starts `@conciv/harness-testkit/run-tests`.
- `engine.ts`: `createEngine` on `createHarnessEngine` from `@conciv/harness-testkit`, with the plugin names resolved from the package under test and `env`, `policies`, `systemPrompt`, `sessionId`, `timeouts`, `staleness`, `app`, `directory`, `models`, `commands`, `harnesses` and `fs` passed through to the engine. The engine carries its `address` (`apiBase` and `token`), so a test can call an engine route, and its `root`, the project folder's real path (in browser mode on the engine handle), and `opened()`, what the engine was asked to open in the editor (in browser mode the `concivOpened` command), and `event(type)`, a wait for the next engine event of that type (in browser mode `concivEvent` returns a wait id once live, and `concivEventArrived` the event), and `rpc.call` / `rpc.failure` for a plugin's own rpc (in browser mode two commands, `concivRpcCall` and `concivRpcFailure`, because a thrown error crosses without its fields), and `loginCode()` and `revokeBrowsers()` (in browser mode `concivLoginCode` and `concivRevokeBrowsers`), and `restart()`, a stop and boot on the same folder and address (in browser mode `concivRestart`). An engine made inside a test stops when the test ends; one made at file level stops after the file (`node-setup.ts`).
- `browser-engine.ts`: the same `createEngine` for browser mode. Each call is a browser command, and the engine runs in Node (`test-projects.ts`). The browser project aliases `/node` to this file. Both re-export `TestLLM` from `@conciv/harness-testkit/test-llm`, so `import {createEngine, TestLLM} from '@conciv/plugin-testkit/node'` is the same line in node, happy-dom and browser mode.
- `mount.ts`: renders `ConcivApp` bound to the engine's address, with browser storage seeded, the route opened, the host's settings (`host`, handed over as the embed does) and an in-memory draft store; `login: 'none'` binds the app to the engine's bare origin with no token source (the browser is logged out), and without `login` the app uses the engine's token path, and resolves once the app calls `onInteractive`, whether the chat opens closed or open. It reads the address from the engine it is given. `happy-dom.ts` and `browser.ts` export it.
- `dom-environment.ts`: the happy-dom environment, keeping Node's fetch, WebSocket and storage so the page reaches the engine over the real socket, and giving it a `navigation` that fires `currententrychange` on history changes so the page tab attaches.
- `test-projects.ts` (export `./vitest`): `concivTest()`, a vite plugin whose `config` hook adds the node, happy-dom and browser projects. The projects hold only what makes them exist (name, file patterns, environment, setup files, vite plugins, the browser provider and its commands, the poll timeout they provide, the browser pre-bundle list). The tunable settings (test and hook timeout 30 s, `expect.poll` 5 s every 50 ms, a worker cap read from `VITEST_MAX_FORKS`, since vitest itself reads only `VITEST_MAX_WORKERS`) are given by the hook as `author ?? kit`, because vite merges a plugin's `config` result over the user's config (vite `node.js` `runConfigHook`, `mergeConfig(conf, res)`) and vitest merges a project's inline `test` over the config it extends (`resolveSharedServerEntry`; a project with its own server re-runs the config file, so the hook runs again inside each project, `resolveSingleProjectEntry`). So the author's `test: {...}` wins in all three projects. The hook adds the projects only at the root (`test.name` unset); inside a project it gives the defaults only. An author's own `test.projects` is kept beside the kit's: vite concatenates arrays. Reporters, coverage and `teardownTimeout` are left to the author's root config, the only place vitest reads them. `happy-dom-setup.ts` and `browser-setup.ts` run Testing Library's `cleanup` after each test.

## Invariants

- The engine graph loads as plain Node modules (`server.deps.external` on the engine chunk), so `ws` and the server entries never get browser conditions.
- In browser mode every engine and session call, the recorded model requests (system prompts, tools with their JSON Schema inputs, model, effort and options) and a session's stop included, crosses as a browser command and returns plain JSON.
- State is put in place only through the engine's own rpc (settings, real turns) and browser storage; no test-only endpoint.
