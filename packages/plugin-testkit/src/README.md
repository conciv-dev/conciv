# plugin-testkit src

## Purpose

The engine a test makes, the mount that shows the app on it, and the vitest projects that wire both per place a test runs.

## Files

- `node.ts`, `browser.ts`: the two public entries.
- `../bin/conciv-test.js`: the `conciv-test` bin, committed so it exists at install time; it starts `@conciv/harness-testkit/run-tests`.
- `engine.ts`: `createEngine` on `createHarnessEngine` from `@conciv/harness-testkit`, with the same two arguments: the plugin names in `config.plugins` are resolved from the package under test, and the rest of `config` and the whole of `start` are passed through to the engine. The engine carries its `address` (`apiBase` and `token`), so a test can call an engine route, and its `root`, the project folder's real path (in browser mode on the engine handle), and `opened()`, what the engine was asked to open in the editor (in browser mode the `concivOpened` command), and `event(type)`, a wait for the next engine event of that type (in browser mode `concivEvent` returns a wait id once live, and `concivEventArrived` the event), and `rpc.call` / `rpc.failure` for a plugin's own rpc (in browser mode two commands, `concivRpcCall` and `concivRpcFailure`, because a thrown error crosses without its fields), and `loginCode()` and `revokeBrowsers()` (in browser mode `concivLoginCode` and `concivRevokeBrowsers`), and `restart()`, a stop and boot on the same folder and address (in browser mode `concivRestart`), and `outside(agent?)`, an outside agent's `describe`, `discover` and `call` (in browser mode `concivOutsideDescribe`, `concivOutsideDiscover` and `concivOutsideCall`), and `clock` (`advance(until)` and `drain()`, with `clock: 'test'`, from `@conciv/harness-testkit`; in browser mode the page holds `until` and sends one `concivClockTick` per step, and `concivClockDrain`); `start.port: 'connect'` and `start.token` reach the engine as given (in browser mode inside `concivCreateEngine`'s arguments). An engine made inside a test stops when the test ends; one made at file level stops after the file (`node-setup.ts`).
- `browser-engine.ts`: the same `createEngine` for browser mode. Each call is a browser command, and the engine runs in Node (`test-projects.ts`). The browser project aliases `/node` to this file. Both re-export `TestLLM` from `@conciv/harness-testkit/test-llm`, so `import {createEngine, TestLLM} from '@conciv/plugin-testkit/node'` is the same line in node, happy-dom and browser mode.
- `mount.ts`: renders `ConcivApp` bound to the engine's address, with browser storage seeded, the route opened, the host's settings (`host`, handed over as the embed does) and an in-memory draft store; `login: 'none'` binds the app to the engine's bare origin with no token source (the browser is logged out), and without `login` the app uses the engine's token path, and resolves once the app calls `onInteractive`, whether the chat opens closed or open. It reads the address from the engine it is given. `plugins` takes the config's own form, a name or `[name, JSON options]`; each name is turned into the plugin by `virtual:conciv-test-plugins` (`test-projects.ts`), composed as the site composes a window plugin (`{...declarations, id, windowEntry}`) and handed to the app with its options. Without an engine and with at least one plugin, the app runs in servers mode (`{kind: 'servers'}`) on the memory route `/panel/connect?open=true`, as the embed does with `defaultOpen`; without an engine and without a plugin `mount` throws. `happy-dom.ts` and `browser.ts` export it.
- `dom-environment.ts`: the happy-dom environment, keeping Node's fetch, WebSocket and storage so the page reaches the engine over the real socket, and giving it a `navigation` that fires `currententrychange` on history changes so the page tab attaches.
- `vitest.ts` (export `./vitest`): `concivTest()`, a vite plugin whose `config` hook returns nothing unless vite's mode is `test` (vitest sets it: `mode: options.mode || 'test'`, and each project inherits the parent's mode), and only then imports `test-projects.ts` and returns `kitTestConfig(config)`. It imports nothing at load, so `vite build` and `vite dev` of a package that lists it load none of the test stack (engine, harness-testkit, Playwright, vite-plugin-solid, UnoCSS, the app).
- `test-projects.ts`: `kitTestConfig(config)` adds the node, happy-dom and browser projects. The projects hold only what makes them exist (name, file patterns, environment, setup files, vite plugins, the browser provider and its commands, the poll timeout they provide, the browser pre-bundle list). The tunable settings (test and hook timeout 30 s, `expect.poll` 5 s every 50 ms, a worker cap read from `VITEST_MAX_FORKS`, since vitest itself reads only `VITEST_MAX_WORKERS`) are given by the hook as `author ?? kit`, because vite merges a plugin's `config` result over the user's config (vite `node.js` `runConfigHook`, `mergeConfig(conf, res)`) and vitest merges a project's inline `test` over the config it extends (`resolveSharedServerEntry`; a project with its own server re-runs the config file, so the hook runs again inside each project, `resolveSingleProjectEntry`). So the author's `test: {...}` wins in all three projects. The hook adds the projects only at the root (`test.name` unset); inside a project it gives the defaults only. An author's own `test.projects` is kept beside the kit's: vite concatenates arrays. Reporters, coverage and `teardownTimeout` are left to the author's root config, the only place vitest reads them. The happy-dom and browser projects serve `virtual:conciv-test-plugins` (`virtual-test-plugins.d.ts` types it): one loader per plugin that `mount` can name, the package under test and each of its dependencies and devDependencies whose package.json parses with a `name` and `keywords` holding `conciv-plugin` (any other manifest is skipped), found with the lookup `createEngine` uses; the loader imports the package folder (its `.` export) and carries the package name as the plugin id, the engine's id for a plugin it loads with no server definition (`Host.packageId`); a plugin with a server definition takes that definition's id in the engine, which the kit can read only by loading the server module, so `mount` keeps the package name. The browser project also hands the same plugin to vite's dependency scan (`optimizeDeps.rolldownOptions.plugins`), so the scan follows each by-name plugin's import and pre-bundles its browser dependencies at start instead of reloading the page when a test first imports them. `happy-dom-setup.ts` and `browser-setup.ts` run Testing Library's `cleanup` after each test.

## Invariants

- The engine graph loads as plain Node modules (`server.deps.external` on the engine chunk), so `ws` and the server entries never get browser conditions.
- In browser mode every engine and session call, the recorded model requests (system prompts, tools with their JSON Schema inputs, model, effort and options) and a session's stop included, crosses as a browser command and returns plain JSON.
- State is put in place only through the engine's own rpc (settings, real turns) and browser storage; no test-only endpoint.
