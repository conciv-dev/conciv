# client/src/session

## Overview

The Solid client-side chat session. It wraps `useChat` from `@tanstack/ai-solid` with run lifecycle tracking, hydration, stop and approval decisions, over a connection the caller supplies.

## Interface

- `session.ts`: `createChatSession` takes the session id, a `connect(callbacks)` that returns the connection, and the `stop` and `decide` network callbacks; the caller supplies the transport. Exported through `chat.ts` (`@conciv/client/chat`).

## Invariants

- `session.ts:newerRun` - hydration does not overwrite a run that started later, or the same run when it is already terminal.
- `session.ts:readHarness` - the harness that produced a message, by message id, merged from every hydration's `messageHarness`; `undefined` for a message no hydration named.
- `session.ts:loadFailed` - the history load failed when the chat's current error is the error of the latest history load itself: the session's `hydrate` wrapper records the error of a load with no `before` cursor (older pages, which pass `before`, never count) as `historyError` in its `served` store, rethrows that same object so the library sets it as `chat.error()`, and clears it on the next successful load; any other error (a refused or failed send, an empty thread or not) is never a failed load; the loading state itself is `useChat`'s `isHydrating`, which goes false on success or failure.
- `session.ts:onApprovalAsk` - pending approvals are deduplicated by `approvalId`.
- `session.ts:joinedRun` - does not join a run the local chat owns (loading, or the same `runId`), nor a run this session already knew that is no longer running in its `runSource` (checked again after the window fetch, so a stop that lands while the fetch is pending also declines), so an announcement that lands after a stop cannot bring the run back as running; nor any run while the chat's history load has failed: that chat is reopened, never patched, so its load error and Retry stay. A run the session never saw (another client's, even one already finished) is still joined so its end refreshes the session list.
- `session.ts` `onLifecycle`: an `aborted` lifecycle for the run the local chat is still loading (the same `runId`, as another client stopped it) calls `chat.stop()`, because a stopped run's stream carries no `RUN_FINISHED`; a lifecycle for any other run never touches the local turn.
- `session.ts:stopRun` - marks the run source `stopping` as soon as Stop is pressed (so the composer blocks every submit until the stop lands), then always calls `chat.stop()` and marks it `aborted` even if `options.stop` throws, then refreshes. Output the agent sent before the stop landed stays in the turn, followed by the Stopped line.
- `session.ts:stop` - a Stop pressed while a turn is in flight but before the engine has acknowledged it (no running lifecycle yet, and no lifecycle for the local run) is queued: the run state moves to the `stop-queued` phase with the local run id (`null` for a run the engine started), `stopping()` is true from that instant (so "Stopping…" shows and Stop, Escape and Send are blocked), and the local stream is not cut. When the local run id is known, the same press also sends `options.stop([runId])` so the engine aborts a run a plugin prompt hook is still preparing (`stopPreparing`); the session stays queued whatever the answer (a rejected call goes to `options.onError`), and the aborted run's stream error then ends the phase through `withdrawn` below. The phase ends on events only: the first lifecycle for that run (any running lifecycle when the run id is `null`) moves it back to `known`, and a running one then runs `stopRun` with its id; a chat error while queued (the send failed or its stream ended with no lifecycle) moves it to `withdrawn`, holding that error: the session's `error()` hides exactly that error (so no run error row and no load failure shows for it), `withdrawn()` is true, and the session's `sendMessage` drops the message from the last user message on and rejects, so the caller can put the text back. A later send resets the chat error, which ends the hiding. A queued phase whose local run is gone (`chat.runId()` changed or the chat is idle) reads as not stopping and is never released, so it cannot stop a later run. There is no timeout.
- `session.ts:decide` - sends the reply and withdraws the card once the server answers, either way; it never sends a chat message.
- `session.ts:createChatSession` - `useChat` is configured with `persistence: true`, `history: {pageSize: CHAT_HISTORY_PAGE_SIZE}` (50), `live: true`, `queue: 'queue'`.
- `session.ts:messages` - the list the UI renders follows the live `chat.messages()` at most once every 16 ms (`createScheduled` with `throttle`, trailing, so the newest list always lands), at once when the run stops streaming (so the last chunk lands with the status that says the run ended), and at once when the tab becomes visible again. Every piece of session logic (`stop`, `refresh`, `joinedRun`, `sendMessage`'s refusal check) reads and writes the live list, never this one.
- `session.ts:refresh` - stored message ids are the rendered ids, so a refresh stitches by id: messages shown before the refreshed page's first message stay in front of it. A page that starts past everything shown, an empty chat included, pulls the pages before it until it reaches a shown message (or the thread start), so loaded history is kept and the gap is filled. Messages added while the fetch was in flight (a send right after Stop, and its streamed reply) are not in the fetched page, so the refresh keeps them after it instead of dropping them; `joinedRun` applies its window the same way.

## Side Effects

- `session.ts:createChatSession` - opens the connection through `options.connect` and closes it in `onCleanup`.
- `session.ts:sendMessage` / `neverLeft` / `answered` - after the library returns, a send that was withdrawn (above) or that raised a new chat error with no assistant content after the last user message and no lifecycle for its own run (the engine refused it) never left: both go through the one drop (`beforeLastUser`) and reject, the withdrawn one with its own error and the refused one with the chat error, so the composer puts the text back and no ghost turn stays in the log. A refused send keeps its error in `error()`, as the thread's first message too, so its run error row shows beside the welcome and never a failed load. A run the engine acknowledged is never a refused send: when `runSource()` holds a lifecycle for the send's run (`lastLocalRunId`, the last run id the chat had in flight, since `chat.runId()` is back to `null` once the send returns; the engine's terminal lifecycle arrives on the stream before its `RUN_ERROR`), the user message stays and the send resolves (except when the client gave up on the stream, `StreamReconnectLimitError`, as when the engine goes away mid-run: that send never left, it is dropped and rejects, so its text comes back), so the run's error row shows with its Retry and the composer stays empty, and no empty thread reads as a failed load. The composer puts text back only when the send rejects (`packages/ui-kit-chat/src/primitives/composer/composer.tsx`); a change to which sends reject is a change to which sends come back.
- `session.ts:stopRun` / `refresh` / `decide` - call the supplied network callbacks and `chat.sendMessage`.
