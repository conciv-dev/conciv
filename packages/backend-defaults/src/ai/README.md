# backend-defaults/src/ai

## Overview

The server-side chat runtime. It runs turns through the TanStack `chat()` pipeline with middleware for persistence, locks, sandbox, code mode, tool approval and run lifecycle events, delivers runs as async generators that resume from an event id (`send` starts a run once then tails it, `join` tails a run from an event id, `drive` runs headless), and stores runs, threads and metadata in drizzle SQLite tables (`../db/run-schema.ts`). The run sandbox is `localSandbox` from `@conciv/harness/local-sandbox`.

## Invariants

- `chat-server.ts:createChatServer` - async factory returning a `ChatServer` (delivery plus `stop`, `endRuns`, `endAllRuns` (ends every live run on every thread the way `endRuns` does, waits for all of them to settle, disposes the code mode driver, then rethrows any failed cancel writes and a failed driver dispose together as one `AggregateError`), `settled`, `hydrate`, `record`, `codeRunner`).
- `chat-server.ts:record` - folds the given chunks through a `StreamProcessor` and appends the assistant messages to the thread the same way a stopped turn is saved, skipping tool calls the thread already holds.
- `code-mode.ts:codeModeTools` - the code-mode `discover_tools` carries our own short description (`DISCOVER_DESCRIPTION`) in place of the library's, which embeds the whole capability catalog; the same tool serves chat turns and MCP.
- `delivery.ts:readTerminalPhase` - maps RUN_ERROR to `failed` and RUN_FINISHED to `completed`, unless its finish reason (`readFinishReason`) is `tool_calls`, which ends one model call and not the run; `endsTheRun` also counts a terminal run-lifecycle chunk.
- `chat-stores.ts:drizzleChatStores(db, {readHarness, saved})` - implements `ChatStores` (messages, runs, metadata) on a `NodeSQLiteDatabase`; a new run row records `readHarness(threadId)` in `harness_id`. `messages.saveThread` upserts one `chat_messages` row per message (rewriting only rows whose JSON changed) and deletes rows past the new end; once that commits and anything changed, it calls `saved(threadId, messages, at)`, where `at` is the newest `createdAt` among the rewritten rows, or now when none has one. `messages.loadThread` with a `limit` reads one page: the end position (the row count, or the `before` message's row through the `thread_id, message_id` index), the nearest user row at or before `end - limit`, then only the rows in that range, and returns a `MessagePage`; the window starts on a user message so no turn is split, its `cursor` is that message's id, and an unknown `before` gives an empty complete page. Without a `limit` it returns the whole transcript, which every write path uses. `messages.loadMessage(threadId, messageId)` reads that one message's row through the same index, or null; a turn uses it to find the message it prompts.
- `child-cards.ts:childCardChunks` / `childCards` - turn the `conciv.code-mode-call/result/error` custom events (`codeModeCallEvent` and friends in `@conciv/types/chat-event-types`) into TOOL_CALL_* chunks linked to the parent `execute_typescript` call, keyed by their `callId`; the library's own id-less `code_mode:external_*` events are dropped.
- `model-request.ts:hookedRequest` - hands the request hook each offered tool as its description and JSON Schema input keyed by name, and maps what the hook leaves back to tools by definition identity, then by name; a definition matching neither is dropped, a moved one renames its tool, and an unchanged input keeps the tool's own schema.
- `model-request.ts:answeredAdapter` - wraps `chatStream`: when the call's `metadata.conciv.answer` holds a result (`answeredMetadata`, set fresh for every call by the `beforeModel` phase), it streams that `summary` as one assistant text message and finishes with the result's `tokens` as the run's usage, without calling the wrapped adapter; otherwise it calls the adapter. The answer travels in the call's own config, so nothing outlives the call.
- `chat-server.ts:compactionStamp` - middleware added only to `kind: 'compact'` runs: merges `compaction: true` into `metadata.conciv` (`CompactionMetadataSchema`, other `conciv` keys kept) on TEXT_MESSAGE_START, REASONING_MESSAGE_START and RUN_FINISHED chunks so the live message carries it, and on finish writes it onto the stored assistant messages of that run (`metadata.tanstack.run.id`; no write when the run stored none), so a reload carries it too.
- `code-mode.ts:codeModeTools` / `CodeFilesCapability` - each `execute_typescript` run builds its own code-mode tool whose child calls each get a slot in a run-local file list, in call order; a child tool hands its file parts to the `CodeFilesCapability` it finds through `context.getOptional`. The files never enter the sandbox: they are attached after the program's text as `files` on the run's result, also when the program throws, and the key is left out when no call produced any.
- `code-mode.ts:stoppedWith` - wraps a driver so aborting the signal disposes the running context; a turn passes its run signal, so stopping the turn stops its program; a failed dispose is logged.
- `quickjs-thread.ts:quickJSThreadDriver` - an `IsolateDriver` with `dispose` that runs `createQuickJSIsolateDriver` in `piscina` worker threads (task `quickjs-worker`, resolved beside the thread module with its extension: `dist/quickjs-worker.js` when built, `src/ai/quickjs-worker.ts` run by Node's type stripping from source). One pool per driver, created with the driver: `minThreads: 1` keeps one worker warm (zod, oRPC and the QuickJS WASM module loaded at worker start), `maxThreads` is `max(2, availableParallelism())` so concurrent programs run side by side, and a worker above the minimum leaves after 60 s idle. Each execute is one task (the tool port moves with it through `move`) that builds a fresh QuickJS runtime and context and disposes it before the task ends. `dispose` runs `closePool`: it destroys the pool and waits for every worker thread to exit, and destroys again if piscina respawned one (a worker that errors during `destroy` settles piscina's wait early, so its later exit respawns a worker), at most 3 passes; workers still left after a pass without a respawn or after the last pass are logged and terminated directly, so shutdown never loops or hangs. `waitForExit` resolves at once for a thread that has already exited; the next `createContext` or execute creates a new pool.
- `run-guard.ts:guardedAdapter` - wraps `chatStream` with an end signal and two limits: from the stream's start to the adapter's first `RUN_STARTED` the start limit (`startMs`, failing through `onNotStarted`), then from that `RUN_STARTED` to the first output other than `RUN_STARTED` and `CUSTOM` the silence limit (`firstOutputMs`, failing through `onSilence`). The first output disarms whichever limit is armed; an adapter that sends output with no `RUN_STARTED` only ever has the start limit.
- `chat-server.ts:toolHistory` - middleware placed right after `withSandbox`: the sandbox's tool-history recorder writes each harness tool call into `ctx.messages` without its TOOL_CALL_START metadata, without the result's `output-error` state and without a message id; this middleware records the start metadata and failed results per `toolCallId` and, on TOOL_CALL_END, TOOL_CALL_RESULT and each iteration, restores them on the recorded messages (metadata such as `parentToolCallId` merged into the call, `error` on a failed result, and the id `<toolCallId>-call` on the assistant message, so a reload keeps nesting, errors and one id per call). It runs after `withSandbox` so the recorder's messages exist, and `withPersistence` saves `ctx.messages` after these chunk hooks, so the stored thread carries the restored fields. It also stamps `time.start` on each TOOL_CALL_START's metadata and `time: {start, end}` on each TOOL_CALL_RESULT's metadata, and records that time on the stored call. @tanstack/ai folds a result's metadata onto its one tool-call part as `part.resultMetadata`, live and in the chat server's own stream processors, so a stopped turn and an outside call keep their end time too, and `readToolCallTime` reads the start metadata and the result metadata together.

- `chat-server.ts:run` (`conciv-steer` middleware) - starting a run ends every other live run on the same thread.
- `@conciv/harness/local-sandbox` `killGroups` - every process group the sandbox spawns (POSIX) is kept until its process exits, and a synchronous `process.once('exit')` hook SIGKILLs the groups still in that set: an engine process that exits without stopping its runs (a shutdown deadline, a second Ctrl+C, Next's `process.exit`) leaves no agent CLI running. A process killed by a signal it does not handle runs no exit hook.
- `chat-server.ts:planned` - an exception from `hooks.plan` becomes a `failed-launch` adapter that emits RUN_ERROR.
- `chat-server.ts:admitted` - `hooks.admit(turn)` is awaited before the last user message is looked up or handed to `TurnPlan.prompt`, before `chat()` runs: a rejection removes the live entry and ends the run stream with that error as its one RUN_ERROR, with no run row, no stored message, no `hooks.started` and no `hooks.end`.
- `chat-server.ts:endedPhase` - a `completed` phase is reported as `aborted` when the record has `cancelRequested` (the user stopped the run while it was finishing by itself); `terminalChunk` and `buildLifecycle` both use it, so the terminal chunk, `hydrate`'s `lastRun` and `hooks.end` agree.
- `chat-server.ts` `onStart`: `hooks.started` (the run announcement) is skipped once the run's controller is aborted; `@tanstack/ai` calls `onStart` after setup even for a cancelled run.
- `chat-server.ts:endedWithItsRecord` - a run stream that ends without a terminal chunk is closed with its recorded terminal run-lifecycle chunk, so a replay or join of a stopped run reads its `aborted` end. A stopped run gets no `RUN_FINISHED`, because the run's owner reads the same log and a late `RUN_FINISHED` would settle the owner's next turn. A run recorded `completed` whose last RUN_FINISHED was a `tool_calls` one (the loop ended after a tool step) gets a closing `RUN_FINISHED` with `finishReason: 'stop'`, because the chat client settles a turn only on a RUN_FINISHED that is not `tool_calls`, and without it the pane stays on "Responding…".
- `chat-server.ts` `agentLoopStrategy` - `untilFinishReason(['length'])`: the TanStack loop keeps calling the model after each tool step until the model stops or runs out of length, with no step limit. Without it `chat()` stops after 5 model calls. Only a harness whose tools conciv executes (the scripted engine harness) loops here; the CLI harnesses run their own loop and always finish with `stop`.
- `chat-server.ts:stop` - cancels only the thread's active run, and only if it is in `runIds` when given; answers `true` exactly when it requested the cancel, and `false` when there is no active run, it is not in `runIds`, a cancel was already requested for it (a repeat stop), or this process is already stopping it: a run this process drives is marked `stopping` on its live entry in the same synchronous step that decides the answer, by `stop` and by `endRuns` alike, so of two stops at the same moment exactly one answers `true`, and a stop of a run a newer turn is ending answers `false`; the cancel write and the abort follow, and the abort happens even if the write fails. A run this process does not drive (an abandoned row before the sweep) is decided by the stored `cancelRequested` alone.
- `chat-server.ts:stopPreparing` - when the thread has no active run record, `stop` aborts with `RUN_CANCEL_REASON` every live run of the thread that is in `runIds` (all of them when not given): a Stop pressed right after sending, while the run is live but its `running` row is not written yet, stops it, and `stop` answers whether it aborted any. Known open hole: a Stop that reaches the engine before the run's request has arrived (no live entry and no row) is a no-op, and the run then runs to its end.
- `chat-server.ts:hydrate` - waits for aborted live runs to settle before reconstructing, passes the optional `limit` and `before` to `reconstructChat` (one window of the thread plus `page`), and validates the result with `ReconstructedSchema`. `activeRun` and `lastRun` are never paged.
- `code-mode.ts:childCall` - wraps each code-mode tool: mints a `callId` per call, emits `conciv.code-mode-call` then `conciv.code-mode-result` or `conciv.code-mode-error` through `context.emitCustomEvent`, hands the tool `toolCallId: callId`, validates the input and output against the tool's own schemas (the library gets the same JSON Schemas, so its generated stubs are unchanged, and runs no checks of its own), so a call with bad arguments still gets its error card, and throws (as an error event) when a tool parameter was flagged as a secret; `codeModeTools` returns null when there are no `__toolSide === 'server'` tools.
- `code-mode.ts:loadIsolateDriver` - code mode runs only on QuickJS in a worker thread (256 MB memory, 2 MB stack); timeout `CODE_MODE_TIMEOUT_MS` from `@conciv/types/chat-types` (150000 ms).
- `quickjs-thread.ts` - guest code never runs on the server thread, so a busy program cannot block HTTP, SSE or stop requests. Tool calls are oRPC calls (`toolRouter.call`, `RPCHandler` from `@orpc/server/message-port` on the host, `RPCLink` from `@orpc/client/message-port` in the worker) over a `MessageChannel` port handed to the task; the result crosses through oRPC's RPC serializer (JSON plus Date, BigInt, Map, Set, URL, RegExp, undefined), a missing binding is a `NOT_FOUND` error, and a tool error reaches the guest as an Error with the same message.
- `quickjs-thread.ts:run` - aborts the piscina task, which terminates its worker (piscina boots a replacement), when the program outlives its timeout by 1 s (reported as `TimeoutError`, like the QuickJS driver) or on context dispose (`AbortError`), and returns once that worker has exited; driver dispose ends a running execution as `AbortError`. A result whose error is `TimeoutError`, `MemoryLimitError`, `StackOverflowError`, `WasmRuntimeError` or `RuntimeError` retires only the worker that produced it, because the WASM module it shares across runtimes may hold a leaked or broken runtime: the worker sends the result through `toolRouter.retire` and never finishes the task, and the host keeps the result and aborts that task, so piscina terminates exactly that worker and the result is returned once it has exited. If the retire call itself fails, the worker task rejects with that error instead of waiting, so the run ends as a logged worker failure. A guest throw keeps the worker. A worker that throws or dies mid-run, even with a tool call in flight, ends that run as a failed run and is logged, and piscina replaces it. Every worker error is logged, and the pool's `error` event has a listener, so an error outside an execution never reaches the server thread unhandled.
- `run-guard.ts:guarded` - the first-output timer fires `onSilence` unless a chunk other than RUN_STARTED/CUSTOM arrives first.
- `delivery.ts:events` - returns 400 for an invalid body, and replays from offset `-1` when `seenRun(runId)` is true. A socket run frame and an events POST each check `seenRun` and start the run while holding a per-runId `InMemoryLockStore` lock (`@tanstack/ai/locks`), so the same runId sent twice back to back starts one run: the second waits for the first to register its live run and then sees it.
- `chat-stores.ts:metadata.set` - throws a TypeError on a null or undefined value; `runs.createOrResume` throws if the row is missing after insert-or-ignore.
- `image-tool-results.ts:askingToolProvisioner` - responds 401 without a matching bearer token (`timingSafeBearerEqual`), 405 for non-POST, 400 for invalid JSON.

## Side Effects

- `image-tool-results.ts:askingToolProvisioner.provision` - starts a `node:http` server on `127.0.0.1` on a random port with a random 24-byte token.
- `chat-stores.ts:drizzleChatStores` - SQLite reads and writes on `chat_runs`, `chat_messages` and `chat_metadata`.
- `chat-server.ts:createChatServer` - on startup marks every `running` run as `aborted` (`sweepAbandonedRuns`) and calls `hooks.end`.
- `chat-server.ts:createChatServer` - the `conciv-run-record` middleware, placed right before `withSandbox`, writes the run's `running` row through `stores.runs.createOrResume` and then saves the incoming messages through `getPendingTurn(ctx, {optional: true})?.snapshot()` (conciv's only import from the `@tanstack/ai` adapter internals). `withSandbox` emits `sandbox.starting` from its `setup`, and `chat()` sends `RUN_STARTED` ahead of that event, before `withPersistence` has stored the run or the user's message; with this step a client that has seen `RUN_STARTED` finds the run active and the user's message in the thread.
- `chat-server.ts:createChatServer` - creates a `localSandbox` from `config.sandbox` (`dir`, optional `groupExitTimeoutMs`) and runs without a run journal: the agent CLI's stdout is read straight from its pipe, so the `guardedAdapter` watchdog is the only limit on a silent CLI: `startTimeoutMs` until the agent's first `RUN_STARTED` (`the agent did not start within Ns`), then `firstOutputTimeoutMs` until its first output (`the agent produced no output within Ns`). The journal stays off because `@tanstack/ai-sandbox` 1.2.0 `journalOptionsFor` (`dist/esm/durability.js`) passes `attachWaitMs` to the journal reader only when `durability.attach` is true; a fresh run falls back to the reader's `firstByteTimeoutMs ?? 1e4` default (`journal-reader.js`, `firstByteTimeout`) and fails as a stalled journal after 10s, before the 30s first-output limit can fire. Dependency patches are not allowed, so the journal stays off until upstream carries the option on a fresh run.
- `chat-server.ts:saveStoppedTurn` - on abort saves the partial assistant messages and marks the run `failed` if an error was seen.
- `chat-server.ts:createChatServer` - keeps an in-process `live` run map and an `InMemoryLockStore`.
- `quickjs-thread.ts:quickJSThreadDriver` - starts one worker thread when the driver is created and keeps it; the worker imports `@tanstack/ai-isolate-quickjs` and loads the QuickJS WASM module before it reports ready. Workers are unref'd while idle, so they never hold the process open.
- `delivery.ts:send` / `join` - async generators over the in-memory `memoryStream` log; each event carries its log offset as its event id, a resend of a known run id tails it instead of running it again (`seenRun`).
