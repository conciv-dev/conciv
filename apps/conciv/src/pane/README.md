# pane

## Overview

The chat pane for one session: transcript, composer with attachments and element grabs, drafts kept in two copies, send checks, queue strip, pending approvals, context usage tracker, status bar with view tabs, and refresh.

The composer draft has two copies. The first is in this browser: the IndexedDB database `conciv-drafts`, written at each change, with no batch (the draft `persistStore` takes a zero `delay`), and flushed when the page is hidden or left, so text and images survive an instant reload even when the engine socket is already closed. When the page is left, the same draft (text, selection, stamps and attachments by blob id, no bytes) is also put in `sessionStorage` in the `pagehide` task, before the IndexedDB write starts, because Chromium aborts that write with the document when another tab's transaction on the store is ahead of it (`runtime/persistence/leaving-copy.ts`). The second is the engine's `drafts` row, saved over rpc after each local write; it can lag the local copy, and it is what another origin, another port, a fresh profile or cleared site data gets back. On load the local copy is applied as soon as it is read, without waiting for the engine; the engine row is read at the same time and, when it arrives, `reconcileDraft` (`draft-reconcile.ts`) picks one by comparing stamps for equality only: when the row's stamp is one this browser sent (the last acknowledged one, or one whose answer never came back), the local copy wins; when it differs, the engine wins; a synced local copy whose row is gone (a delete) is cleared. The local copy is opencode's draft persistence, ported in `runtime/persistence/` (`drafts.ts`, `drafts-machine.ts`, and the `persist.ts` write batch they reuse); that folder's README lists what came from opencode and each difference from it. The reconcile rule and the engine copy are conciv's own: opencode keeps its draft only in the browser.

## Interface

- `ChatPane({sessionId, viewTab?})` (`chat-pane.tsx`): the pane for one session
- `DeletedSessionPanel({sessionId})` (`deleted-session-panel.tsx`): what `ChatPane` shows in place of the chat and composer when the session's row is `hidden` (deleted): the title `This session was deleted.` (`role="status"`, focus is not moved), the line `Your draft moves to the new session.` while the deleted session's saved draft has text or attachments, and one `New session` button
- `SESSION_DELETED_MESSAGE`, `sessionDeleted(error)` (`run-error-row.tsx`): the sentence `This session was deleted, so your message was not sent.` and the check for a failure carrying `SESSION_DELETED_CODE`
- `createPaneSession`, `SessionHeaderSlot`, `SessionStatusSlot`, `SessionComposerPills`, `SessionLinks`, `SessionComposerBinding` (`plugin-session-parts.tsx`): the chat pane's plugin parts: the `session.header` and `session.status` slots, the composer pills, the markdown link and code block provider (always mounted, so nothing remounts when the session object arrives), and the composer binding the mounted session writes through
- `PluginComposerPills({input})` (`plugin-composer-pills.tsx`): the plugins' `ComposerPill` registry above the composer, beside the `session.status` slot, ascending by `order`; each pill runs `show(input)` in a memo inside its plugin's `Contribution` and renders nothing while it returns undefined, so the lane holds no pill (and hides when nothing else is in it). Three shapes: a plain pill (icon in its tone, truncated label, `title` as its accessible name) runs `run` on click; a `menu` pill opens a ui-kit-system popover the host owns (placement, dismissal, heading `title ?? label`) around the plugin's content, rendered untracked once per open with `{session, screen, close}`; a `rows` pill opens a ui-kit-system menu with the heading as its group label and one item per row (`detail` as its badge, disabled without `run`). The popover body and the menu content stop at `max-h-80` and scroll, like the app's other lists. A `run` that throws is logged under the plugin's id
- `PaneComposer`, `PaneComposerProps` (`pane-composer.tsx`): composer with attachment, send and stop buttons
- `ComposerInputAdapter`, `ComposerInputHandle`, `SelectionOffsets` (`composer-input-adapter.tsx`)
- `usePaneMessaging(deps)`, `PaneMessaging` (`use-pane-messaging.ts`): send, `onAnswer` (a tool card answer: the same send-state check as Send, saying "Your answer was not sent." when the engine is unreachable, and rejecting only for that refusal; otherwise `chat.uiReply`, whose failure keeps its own notice and does not reject) and `sessions.compact` mutations
- `makeDraftStorage(appData, sessionId)`, `appendDraft(appData, keep, sessionId, text)`, `prependDraft(appData, keep, sessionId, text)`, `PaneDraftStorage` (`draft-storage.ts`): composer draft storage backed by `AppData.readDraft`, `cachedDraft` and `saveDraft` (`data/app-data.ts`): the `drafts.get` query cache entry and a `drafts.set` mutation scoped to the session; `draftCacheSink(keep, appData, sessionId, write)` is the draft sink for a session whose pane is not mounted: it writes text to the saved draft with `appendDraft` (the lost queue) or `prependDraft` (a refused Steer), and images with their local blob and engine encoding, each as one step on `keep`, the one write chain `makeLiveSessions` makes per app (`makeDraftWriteChain`): the step reads the base, writes the local draft and starts the engine save, and returns without waiting for the save's answer, so a later write reads what an earlier one saved and saves reach `onMutate` in the order of their local writes; a step reads the engine row only when this browser has no local copy of the draft; when it has a local copy but this tab never loaded the session's `drafts.get` row, the step still saves to the engine, with the attachments built from local data only (each local image encoded from its stored bytes), so a lost queue reaches the engine even when the row was never read; only when some local attachment has no stored bytes (its image is held only by the engine row) does the step keep the text locally and send no engine save, because a save would drop that image, so the pane's reconcile at its next load picks the local copy (its `syncedAt` still equals the row's stamp) and saves it with the row's attachments taken by id; when the saved draft cannot be read, `appendDraft` logs it and treats it as no earlier draft, so the text becomes the draft in the cache first and the engine save then lands or fails by itself (the same rule `makeDraftStorage.restore` applies after a failed read; the cost is that once a save lands, it replaces an earlier engine draft this page never read); the plugin `draft` host call writes its prompt with `appendDraft` on the same chain
- `checkSend(content, state)`, `checkSendState(state)`, `MAX_CONTENT_PARTS` (`send-checks.ts`): pre-send validation verdict; `state` is `{busy, reachable, locked}`, `locked` being the `EngineLock` read from `useEngineReachability().locked()`
- `makeGrabStaging(deps)`, `GrabStaging`, `ComposerGrabPort` (`grab-staging.ts`): stages page element grabs as composer attachments
- `resolveGrabSource(grab, symbolicate)` (`grab-source-resolve.ts`)
- `paneAttachments`, `returnQueueToDraft`, `putBackInDraft` (`pane-attachments.ts`): image and text attachment adapters, and the attachment cards: the built-in page plugin's grab card (`pageAttachmentCards` from `@conciv/builtin-plugins/renderer`) (each in a plugin boundary); `putBackInDraft(items, sink)` is the one put-back (text joined by newlines through `sink.insert`, images through `sink.addFile`) and `returnQueueToDraft` cancels every queued item and passes them all to it. A Steer the engine refuses passes its one item (already out of the queue) to it through `use-pane-messaging.ts` `onSteerError` and `LiveSessions.returnSteered` (only once it is out of the queue); while the pane is mounted that is a sink that puts the text at the start of the composer (`insertFirst`: `select` at 0, then `insert` with a trailing newline), so the steered text, first in line, comes before the queued messages the failed stream returned; its images still join the attachments after theirs. With no pane of that session mounted (the user left before the refusal landed) the text goes to the start of the saved draft through `draftCacheSink` with `prependDraft`, after the lost queue was appended there, so it is still first on return; a steered image on that path is lost, as every image `draftCacheSink` gets is. Stop takes the queued messages out of the queue and puts them back in the draft (text in order, images as attachments), unsent. The same function runs when the chat stream fails while messages are queued (see `live-sessions.ts` in `app/`); each item leaves the queue through `cancelQueued`, so nothing stays queued to be sent later. Images queued by URL are not carried back; on a stream failure with the pane open, images come back as attachments through the same `returnQueueToDraft` path Stop uses, which no run exercises separately. A returned image is a `File` named `image` (`partFile`), the same name Stop has always given it
- `makeRefreshCoordinator(deps)`, `RefreshCoordinator` (`refresh-coordinator.ts`)
- `useComposerTriggerSources({sessionId, openModelMenu})` (`trigger-sources.ts`): `{triggers, runTyped}`: slash command and tool trigger sources, plus `runTyped(text)` that runs a widget command whose `/<name>` is the whole text; widget commands are the built-in `/model` (opens the model menu), the plugins' `Command` registry entries that carry a `slash` (in plugin order, each `slash.after` placed behind its anchor, `run(input)` with the typed arguments when `slash.arguments` is set, a throw logged under the plugin's id)
- `PaneAlert({message, busy, onRetry})` (`pane-alert.tsx`): a danger `role="alert"` line with a Retry button that reads `Retrying…` and is disabled while `busy`; the chat pane's failed history load uses it
- `QueueStrip` (`queue-strip.tsx`), `PendingApprovals` (`pending-approvals.tsx`), `ContextTracker`, `ContextSummary` (`context-tracker.tsx`), `StatusBar` (`status-bar.tsx`)
- `Divider`, `CompactSpinner`, `ConversationSkeleton({label?})`, `ThinkingBubble` (`indicators.tsx`)
- `OlderMessages({sessionId, chat})` (`older-messages.tsx`): rendered inside the thread viewport; a solid-query query keyed on the session and the oldest shown message id runs `chat.loadOlderMessages()` (each oldest id loads once; the next key waits until no older-page load is in flight, via `useIsFetching`) while the viewport reports `isNearTop()` (within three viewport heights of the top, so the page before loads while the reader still has history above them; a newest page shorter than that keeps loading pages until it is not); shows a `Loading earlier messages` status row at the top while it loads, and an alert with Retry when it fails
- `makeToolViewCtx` (`tool-view-ctx.ts`)
- `CHAT_VIEW_ID`, `viewTabId`, `viewTabPanelId`, `viewTabPanelAttributes` (`view-tab-ids.ts`)

## Invariants

- `send-checks.ts:checkSend`: refuses empty content, then whatever `checkSendState` refuses, then more than `MAX_CONTENT_PARTS` (16) parts or a JSON payload over `WS_RPC_PAYLOAD_BUDGET_BYTES`, each with a warning while the message stays in the composer
- `send-checks.ts:checkSendState`: refuses silently while a compaction runs; while the page is logged out or its login was revoked it refuses with the locked notice's own sentence (`lockedMessage` from `shell/engine-lock-messages.ts`); while the engine is unreachable it refuses with `conciv lost connection to the engine. Your message is still in the composer.`
- `use-pane-messaging.ts:usePaneMessaging`: one gate for every send. A failed `checkSend` verdict throws `sendRejection(verdict)` before any rpc call; `onSteer` throws the `checkSendState` rejection before the kit's Steer resends a queued message. The pane wires the composer (Send and Enter), the empty-state starters and tool card replies (`chat-pane.tsx:sendFromButton`, which is `onSend` then `onSendError`) and Steer (`onSteer`, and `onSteerError`, which puts a refused item back through `LiveSessions.returnSteered` and then calls `onSendError`) through it. `onSendError` shows a refusal as a notice row, except the unreachable refusal while `sustainedOffline()` is true and the page is not locked: the standing lost-connection notice (`EngineUnreachableNotice`, mounted in the panel, the quick view and the pop-out) and the disabled Send already say it; in the first second of a lost connection, and for a locked page, the row still shows. A send the session took back (`chat.withdrawn()`: Stop was pressed before the engine had the run and the send then failed) is converted to a refusal with no message, so the kit puts the text back in the composer and no notice shows; a failed send with no Stop pressed still shows its notice. A Stop pressed while a plugin is still preparing the prompt ends the same way: the session sends the stop at once, the engine aborts the preparing run, and the message comes back to the composer with the thread as it was
- `pane-composer.tsx:PaneComposer` while this browser is locked out (`useEngineReachability().locked()` not `null`: logged out, or its login revoked; Decision 27): the composer takes no input, so nothing typed while the store refuses writes can be lost. The input is the kit's disabled `RichTextField` (`editor.setEditable(false)`, `aria-disabled="true"`), dimmed with `opacity-50` and `cursor-not-allowed`, with the placeholder `Log in to continue`; text already in it stays on screen and cannot be edited; Add an attachment is disabled too; a non-editable editor has no tabindex (tiptap's `Tabindex` extension), so the box leaves the tab order; when the composer holds focus as it locks, the locked notice (`shell/engine-notice.tsx:LockedNotice`) moves focus to its Log in button, so focus never falls to the browser's fix-up off the non-editable box (Chromium blurs it to the document) or to an unrelated control; focus held elsewhere stays where it is; that notice (`role="alert"`) says why; the focus the notice hands back after the log in still lands, because tiptap's `focus` runs in the next animation frame, after the input is editable again; once the trust comes back the composer takes input again
- `pane-composer.tsx:ComposerSendControl`: Send is disabled while the engine is unreachable or the page is locked; its accessible name is then the locked notice's sentence, else `conciv lost connection to the engine`; Send takes the idle grey when the composer is empty and whenever it is disabled (unreachable, locked, attachments still sending, stopping), and a disabled Send is dimmed to `opacity-40`, the look of the kit's styled composer Send (`@conciv/ui-kit-chat` `styled/composer.tsx`)
- `refresh-coordinator.ts:makeRefreshCoordinator`: a refresh while one is running is ignored; a refresh on a chat whose history load failed reopens it (`liveSessions.reopen`) instead of re-fetching into the failed chat
- `chat-pane.tsx:ChatPane`: keyed on the session's chat instance, so a reopened chat remounts the pane; while the page is logged out, its login was revoked or the engine is unreachable (`usePaneMessaging().resendAllowed()`, the `checkSendState` gate without the compaction check) the run error row offers no Retry (`RunErrorRow` `onRetry` is optional and left out) and every assistant message's Refresh is disabled (`Thread.Messages` `refreshDisabled`); Retry also needs a retryable failure (`usePaneMessaging().retryable()`: a failed run, not a failed idle hook); a failed history load shows `Couldn’t load this conversation` with Retry, which calls `liveSessions.reopen(sessionId)`; while the reopened chat loads the alert stays up as a disabled `Retrying…`
- `older-messages.tsx:OlderMessages`: one older page loads at a time; nothing loads once `chat.hasOlderMessages()` is false or after a failure until Retry
- `deleted-session-panel.tsx:DeletedSessionPanel`: `New session` reads the deleted session's draft as the composer does (`readMovedDraft`: the local copy first, read as a step on the app's write chain, the engine row when there is none, read outside the chain, so text the engine never took still moves), starts a session through `useStartSession`, carries the draft into the new session's draft (`carryMovedDraft`: the text first, then the deleted draft's attachments with their local blobs, and for the engine copy each image with a local blob encoded and each one with none taken from the deleted session's row by id, as the composer restores them; one step on the chain), clears the deleted session's draft (`clearMovedDraft`: its local document removed as a step on the chain, its engine row saved empty outside it); the create runs outside the chain, so a New session that waits on the engine holds no other pane's local writes, and the old draft is cleared only once one copy holds the carried draft: the local write succeeded, or the engine save answered true; then calls the pane's `replaceSession` (the quick terminal swaps the pane in place, the panel and the pop-out open `/panel/<new>`); a failed draft read, or a carry where the local write failed and the engine save failed too, logs `[conciv] could not move to a new session` and leaves the old draft as it was; a failed create is logged once by `useStartSession` and leaves the old draft as it was; a carry that fails after the session was created leaves that new, empty session behind
- `chat-pane.tsx:ChatPane`: a send refused with `SESSION_DELETED_CODE` shows `This session was deleted, so your message was not sent.` in the run error row and the notice, with no Retry, also when it was the thread's first message; a compaction refused with `NOT_FOUND` (the session is deleted or does not exist) notifies `This session no longer exists.` (`SESSION_NOT_FOUND_MESSAGE`)
- `chat-pane.tsx:threadDividers`: dividers before the first loaded message (the `New session` line) show only once no older page is left
- `chat-pane.tsx:renderTurnPrefix`: an assistant turn carries its harness name only once the session's replies (hydrated `readHarness(messageId)`, else the current harness) span more than one harness
- `draft-storage.ts:makeDraftStorage`: the composer renders at once with an empty draft; `restore` reads the row through `appData.readDraft` (`ensureQueryData` on `utils.drafts.get`) and hands it to `restoreDraft` (text and selection only into an untouched composer, attachments merged by id); a composer the user emptied before the read lands gets nothing restored and its cleared draft is written at once; no write reaches the server before that restore settles, then the latest typed draft is written; `storage.setItem` sends nothing when the draft equals the cached `drafts.get` row in every field a save would send (text, selection, attachments), so restoring a saved row never writes it back; every save is a `drafts.set` mutation with `scope: {id: sessionId}`, so saves for one session reach the server in order, and its `onMutate` (from the `drafts.set` mutation defaults) cancels the `drafts.get` fetch and writes the new row into the `drafts.get` cache entry (kept with `staleTime` and `gcTime` Infinity and `retry: false` in `app-data.ts`); `storage.getItem` returns that cached row, else the pane-local value, so a pane rebuilt after a view switch paints the text at once; keystrokes are batched by the kit's own 300 ms debounce, which flushes when the composer unmounts; clearing a non-empty draft persists the cleared draft immediately
- `queue-strip.tsx:QueueStrip`: shows at most 3 queued messages (`VISIBLE_LIMIT`), the rest as an overflow count

## Side Effects

- `data/app-data.ts` `drafts.set` mutation defaults: `gcTime` Infinity so a failed save stays in the mutation cache, and its notice stays up, for as long as the draft is unsaved; at most one failed save per session is kept, the latest: a save that starts (`onMutate`) or fails (`onError`) removes the session's earlier failed saves, so their text and `File`s do not pile up (the default 5 minute `gcTime` would drop the failed save and the notice with it while the draft is still unsaved); a successful save removes the session's earlier settled `drafts.set` mutations, which clears the notice, and itself stays as the content the engine holds; a save that ended without sending removes only the failed ones; `endDraftSaves` (a deleted session) removes every settled one
- `draft-storage.ts:makeDraftStorage`, `appendDraft`: `drafts.get` through the query cache and `drafts.set` through a scoped mutation whose defaults live in `data/app-data.ts` (`setMutationDefaults` on the `drafts.set` mutation key): a save that fails on the transport or with an `INTERNAL_SERVER_ERROR` is tried again up to 3 times with the library's default back-off, never after a 4xx or validation answer; a save that fails for good is logged with `console.error` once, in `onError`, and the `drafts.get` cache entry keeps the row the save wrote, so a pane rebuilt by a view switch still paints the typed text and Retry sends what is on screen; `DraftUnsavedNotice` says the draft is unsaved. This departs from the TanStack optimistic-update guide, which rolls the cache back on error: here the composer is the user's truth and a rollback can only lose text. `onMutate` still cancels an in-flight `drafts.get` fetch so it cannot overwrite newer text; every settled save invalidates that entry. While the engine socket is down the save pauses and resumes on reconnect. Only the user's Send clears the draft; no run, compaction run or page queue run touches the engine row. The composer's Send empties the composer before `onSend` runs (also when the message goes to the client queue), and that emptied composer is written like any other change: its save is a cleared save (empty text, no attachments, a fresh stamp) in the session's `drafts.set` scope, so a save queued or on the wire before it lands first, a save still waiting or in its retry back-off finds the cleared row's stamp in the `drafts.get` cache and ends without sending, and text typed after the Send is saved after the clear; the clear's stamp goes into `sent` and becomes `syncedAt` on its ack, as for any save, so a reload keeps a follow-up typed after the Send, also while its save fails. A Send refused by the send checks puts the text back in the composer, whose save then follows the clear. A failed clear raises the unsaved notice as any failed save does, because the engine still holds the sent text another browser would get back; its Retry sends the composer as it is. A message sent from a button (a starter or a tool card) is not a Send and leaves the draft alone
- `draft-storage.ts:makeDraftStorage` with the local draft store (`appData.drafts` set): the pane hands the kit a `draftWriter`, so the kit writes no storage of its own. Each change sets a `persistStore` document (text, selection, attachments by id with their blob id, `syncedAt`) that the store writes to `conciv-drafts` under the session id at each change, with no batch (`delay: 0`; the source batches for 100 ms); each flush then feeds the engine save. The feed encodes the composer's files with `encodeAttachments` (the 1,000,000 character budget of the engine copy) and compares the draft, with exactly the attachments the engine copy can hold (each one with a file as encoded, each one with no file taken from the cached row by id), to the cached `drafts.get` row; when they are equal nothing is sent, no stamp is made and nothing is written, so an attached image too big for the engine copy is not sent again after every answer. When they differ the stamp (`Date.now()`) is added to the document's `sent` list and the document is written as a step on the app's draft write chain (like every other local draft write, so it never lands over a returned text that `keepInDraft` wrote on the chain before it), and the save goes with that `updatedAt` and the encoded attachments at the end of that same step, so `onMutate` puts the full row in the cache at once and the last save to reach `onMutate` is always the newest local write, whichever writer made it. A save is dropped when the document no longer holds the text and attachments it copied (`sameContent`), checked when it starts and again after the local write: a late image encode, or a local write still running, after a send cleared the composer would otherwise save the sent text to the engine again; a save the feed made is also dropped when, after its local write, the cached row already holds what it would send, since two feeds can record the same content while the first save waits on the chain; a dropped save settles as not sent, so its stamp leaves `sent`. On the engine's ack the document's `syncedAt` becomes the stamp that save sent and `sent` drops it and every stamp sent before it; on a save that failed for good, or that ended without sending (below), `sent` drops that save's entry only, so `sent` holds one entry per save still in flight (two saves made in the same millisecond carry the same stamp and each has its own entry, so a dropped one never takes away the stamp of one still in flight). A save that a newer one superseded ends at its next attempt without sending: every attempt of a `drafts.set` mutation first reads the `drafts.get` cache entry, which each save's `onMutate` sets to its own row, and an attempt whose row's stamp is not the cached row's stamp sends nothing (stamps are compared for equality only, so a row another browser stamped is never ordered against this one) and `saveDraft` answers false; so while the engine refuses every save, the saves queued behind a retried one end at once when it is tried again, and only the newest is still tried. An ended save is a success to the mutation cache that the engine never answered: its `onSuccess` removes the session's failed saves only (the newer save that ended it decides the notice), and the unsaved notice does not count it as content the engine holds. `keepInDraft` and `keepImageInDraft` add the stamp they send to `sent` in the same local write that comes before their save, and `draftCacheSink` settles that stamp once the save answers, as a later step on the write chain (on the ack `syncedAt` becomes it and `sent` drops it and every stamp before it; on a failure or a save ended without sending `sent` drops it only); a pane that takes the row on load settles its `sent` the same way against the row's stamp; the unsaved notice's Retry sends the content on screen with a new stamp the same way, so its ack sets `syncedAt`. A failed local write is logged by `persistStore`, the engine save still goes, and the unsaved notice no longer says the draft is kept in this browser. Once the session is deleted (`AppData.sessionDeleted`, set on `session.deleted`) the writer stops talking to the engine: the persist batch, the flush when the pane unmounts included, still writes the text on screen to the local draft, and no feed, stamp or engine save goes, so the local draft holds the text on screen when the pane closed and no row is upserted for the deleted session; the `session.deleted` handler leaves that local draft in place for the deleted session panel to move, and `clearMovedDraft` removes it once New session has carried it. No engine save goes before the engine row is read. `restore` starts the engine read and reads the local copy (`DraftStore.getItem`, its image Blobs through `resolveBlobUrl`, so a local image comes back as a composer attachment with its `File`), and applies the local copy to the composer as soon as it is read, so an unreachable engine never keeps it from the user; when the row arrives `reconcileDraft` (`draft-reconcile.ts`) picks the copy by comparing stamps for equality only: the engine row stamp equals the local `syncedAt` or a stamp in its `sent` list (a save this browser sent whose answer never came back, such as a reload before the ack), so the local copy wins and is saved to the engine if it differs; a different stamp, so the engine wins and the local copy is overwritten with the row and its stamp; a local copy with no `syncedAt` and no row, so the local copy wins and is saved to the engine (also when it has sent stamps: with no acknowledged save a missing row is read as one the engine never took, so the draft is kept, not cleared); a row and no local copy, so the row is taken and written locally; a local copy with a `syncedAt` and no row (a delete), so the local copy is cleared, not brought back, whatever its `sent` list holds: the composer is emptied and the document becomes an empty draft with no stamp. An empty draft is never sent to an engine that has no row. A local attachment with no stored bytes is taken from the row by id when the row has it. Text typed before the local copy is read keeps that copy's stamps: the writer starts the local read when it is made, `restore` uses that same read, every write of the document waits for it and writes the document as it is at that step, and the read's `syncedAt` and `sent` go into a document typed before it landed, so a write, or a reload, before the read lands never wipes the stored stamps and hands the draft to the engine row. Text typed before the row lands (since the local copy was applied, or at all when there was none) is never overwritten: the composer keeps it, the document takes the row's stamp (or loses its stamp when the row is gone) and the typed text is saved; a composer emptied before it lands gets nothing restored. An untouched composer that shows the local copy is replaced by the row when the engine wins (`DraftApplyMode` `replace`: `clearDraft`, then `restoreDraft`), and only gains the row's attachments for local ones with no stored bytes when the local copy wins. A local copy that cannot be read or parsed is logged and treated as absent. A failed engine read is not a row that is gone: the local copy is kept and shown and nothing is removed; the copy as restored is not sent to the engine (it may be a draft whose row a delete removed), only text typed after it is, and the pick between the two copies waits for a load whose read succeeds. The cost: when the engine row is not the one this browser last sent, the engine wins and local edits that never reached the engine are lost. Without the local store (`appData.drafts` null) the kit's storage path is unchanged. In `data/app-data.ts` the `drafts.set` `mutationFn` writes the full row into the `drafts.get` cache and sends it inside the session's scope, so saves are sent in call order; `onMutate` writes the row into the cache at once
- `draft-storage.ts:makeLocalDraftWriter` leaving copy: the writer for the flush when the page is left (`writeLeaving`) first keeps the document as it is on screen in `sessionStorage` under the session id with a `Date.now()` stamp (`keepLeavingCopy`), then starts the IndexedDB write. The local read the writer starts when it is made takes that copy over the IndexedDB one (`preferLeavingCopy`) when there is no IndexedDB copy, or when the two differ in text or attachment ids and the newest stamp the IndexedDB copy holds (its `syncedAt` or a `sent` stamp) is older than the copy's stamp; otherwise the copy is dropped. Every IndexedDB write of the document that started after the copy was made drops it once it commits (`settleLeavingCopy`: the copy's stamp is older than the write's), so a write still running from before the page was left never drops the copy of what came after it. A copy that is not JSON or not a local draft is logged and dropped. A `sessionStorage` that throws or is full is logged and the IndexedDB write still goes. Images stay in IndexedDB only: the copy holds their blob ids, and an image whose bytes never reached IndexedDB comes back the way a local copy with no bytes does (taken from the engine row by id, or dropped and logged)
