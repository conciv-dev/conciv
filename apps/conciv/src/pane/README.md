# pane

## Overview

The chat pane for one session: transcript, composer with attachments and element grabs, drafts persisted over rpc, send checks, queue strip, pending approvals, context usage tracker, status bar with view tabs, and refresh.

## Interface

- `ChatPane({sessionId, viewTab?})` (`chat-pane.tsx`): the pane for one session
- `createPaneSession`, `SessionHeaderSlot`, `SessionStatusSlot`, `SessionComposerPills`, `SessionLinks`, `SessionComposerBinding` (`plugin-session-parts.tsx`): the chat pane's plugin parts: the `session.header` and `session.status` slots, the composer pills, the markdown link and code block provider (always mounted, so nothing remounts when the session object arrives), and the composer binding the mounted session writes through
- `PluginComposerPills({input})` (`plugin-composer-pills.tsx`): the plugins' `ComposerPill` registry above the composer, beside the `session.status` slot, ascending by `order`; each pill runs `show(input)` in a memo inside its plugin's `Contribution` and renders nothing while it returns undefined, so the lane holds no pill (and hides when nothing else is in it). Three shapes: a plain pill (icon in its tone, truncated label, `title` as its accessible name) runs `run` on click; a `menu` pill opens a ui-kit-system popover the host owns (placement, dismissal, heading `title ?? label`) around the plugin's content, rendered untracked once per open with `{session, screen, close}`; a `rows` pill opens a ui-kit-system menu with the heading as its group label and one item per row (`detail` as its badge, disabled without `run`). The popover body and the menu content stop at `max-h-80` and scroll, like the app's other lists. A `run` that throws is logged under the plugin's id
- `createPluginToolCards(session)` (`plugin-tool-cards.tsx`): the tool card entries of the plugins' `ToolCall` registry, first claim per tool name, placed first in the chat pane's list; an entry accepts a finished call while a session object exists and the plugin has not declined that call id; the plugin's render runs once each time the card mounts, and its view is the `body` of the normal card for that call (the catalog card when the catalog declares the tool, else the pane's fallback card), so the header is that card's own; when the catalog arrives after the card mounted, the same view moves into the catalog card and the plugin is not asked again. A render that returns nothing or throws marks the call id declined, so the next entry, the catalog card or the fallback draws it
- `PaneComposer`, `PaneComposerProps` (`pane-composer.tsx`): composer with attachment, send and stop buttons
- `ComposerInputAdapter`, `ComposerInputHandle`, `SelectionOffsets` (`composer-input-adapter.tsx`)
- `usePaneMessaging(deps)`, `PaneMessaging` (`use-pane-messaging.ts`): send, `onAnswer` (a tool card answer: the same send-state check as Send, then `chat.uiReply`; rejects when refused) and `sessions.compact` mutations
- `makeDraftStorage(appData, sessionId)`, `appendDraft(appData, sessionId, text)`, `prependDraft(appData, sessionId, text)`, `PaneDraftStorage` (`draft-storage.ts`): composer draft storage backed by `AppData.readDraft`, `cachedDraft` and `saveDraft` (`data/app-data.ts`): the `drafts.get` query cache entry and a `drafts.set` mutation scoped to the session; `draftCacheSink(keep, appData, sessionId, write)` is the draft sink for a session whose pane is not mounted: it writes text to the saved draft with `appendDraft` (the lost queue) or `prependDraft` (a refused Steer) through `keep`, the one write chain `makeLiveSessions` makes per app (`makeDraftWriteChain`), so a later write reads what an earlier one saved; when the saved draft cannot be read, `appendDraft` logs it and treats it as no earlier draft, so the text becomes the draft in the cache first and the engine save then lands or fails by itself (the same rule `makeDraftStorage.restore` applies after a failed read; the cost is that once a save lands, it replaces an earlier engine draft this page never read); queued images are not kept there (`addFile` does nothing), because encoding them needs `fileToDataSource` from `@conciv/ui-kit-chat`, and that package does not load in the app's node tests, which import this file
- `checkSend(content, state)`, `checkSendState(state)`, `MAX_CONTENT_PARTS` (`send-checks.ts`): pre-send validation verdict; `state` is `{busy, reachable, locked}`, `locked` being the `EngineLock` read from `useEngineReachability().locked()`
- `makeGrabStaging(deps)`, `GrabStaging`, `ComposerGrabPort` (`grab-staging.ts`): stages page element grabs as composer attachments
- `resolveGrabSource(grab, symbolicate)` (`grab-source-resolve.ts`)
- `paneAttachments`, `returnQueueToDraft`, `putBackInDraft` (`pane-attachments.ts`): image and text attachment adapters; `putBackInDraft(items, sink)` is the one put-back (text joined by newlines through `sink.insert`, images through `sink.addFile`) and `returnQueueToDraft` cancels every queued item and passes them all to it. A Steer the engine refuses passes its one item (already out of the queue) to it through `use-pane-messaging.ts` `onSteerError` and `LiveSessions.returnSteered` (only once it is out of the queue); while the pane is mounted that is a sink that puts the text at the start of the composer (`insertFirst`: `select` at 0, then `insert` with a trailing newline), so the steered text, first in line, comes before the queued messages the failed stream returned; its images still join the attachments after theirs. With no pane of that session mounted (the user left before the refusal landed) the text goes to the start of the saved draft through `draftCacheSink` with `prependDraft`, after the lost queue was appended there, so it is still first on return; a steered image on that path is lost, as every image `draftCacheSink` gets is. Stop takes the queued messages out of the queue and puts them back in the draft (text in order, images as attachments), unsent. The same function runs when the chat stream fails while messages are queued (see `live-sessions.ts` in `app/`); each item leaves the queue through `cancelQueued`, so nothing stays queued to be sent later. Images queued by URL are not carried back; on a stream failure with the pane open, images come back as attachments through the same `returnQueueToDraft` path Stop uses, which no run exercises separately. A returned image is a `File` named `image` (`partFile`), the same name Stop has always given it
- `makeRefreshCoordinator(deps)`, `RefreshCoordinator` (`refresh-coordinator.ts`)
- `useSessionCaptures(sessionId)` (`session-captures.ts`), `useComposerTriggerSources({sessionId, openModelMenu})` (`trigger-sources.ts`): `{triggers, runTyped}`: slash command and tool trigger sources, plus `runTyped(text)` that runs a widget command whose `/<name>` is the whole text; widget commands are the built-in `/model` (opens the model menu) and extension commands from `useInstances()`
- `PaneAlert({message, busy, onRetry})` (`pane-alert.tsx`): a danger `role="alert"` line with a Retry button that reads `Retrying…` and is disabled while `busy`; the chat pane's failed history load uses it
- `QueueStrip` (`queue-strip.tsx`), `PendingApprovals` (`pending-approvals.tsx`), `ContextTracker`, `ContextSummary` (`context-tracker.tsx`), `StatusBar` (`status-bar.tsx`)
- `Divider`, `CompactSpinner`, `ConversationSkeleton({label?})`, `ThinkingBubble` (`indicators.tsx`)
- `OlderMessages({sessionId, chat})` (`older-messages.tsx`): rendered inside the thread viewport; a solid-query query keyed on the session and the oldest shown message id runs `chat.loadOlderMessages()` (each oldest id loads once; the next key waits until no older-page load is in flight, via `useIsFetching`) while the viewport reports `isNearTop()` (within three viewport heights of the top, so the page before loads while the reader still has history above them; a newest page shorter than that keeps loading pages until it is not); shows a `Loading earlier messages` status row at the top while it loads, and an alert with Retry when it fails
- `makeToolViewCtx` (`tool-view-ctx.ts`), `toolFallbackCard` (`tool-fallback-card.tsx`), `createToolDurations` (`tool-durations.ts`, one pane-level record of tool durations; each chunk folds only the live turn's tool calls, settled entries stay, so a row that scrolls away and back reads the same duration)
- `CHAT_VIEW_ID`, `viewTabId`, `viewTabPanelId`, `viewTabPanelAttributes` (`view-tab-ids.ts`)

## Invariants

- `send-checks.ts:checkSend`: refuses empty content, then whatever `checkSendState` refuses, then more than `MAX_CONTENT_PARTS` (16) parts or a JSON payload over `WS_RPC_PAYLOAD_BUDGET_BYTES`, each with a warning while the message stays in the composer
- `send-checks.ts:checkSendState`: refuses silently while a compaction runs; while the page is logged out or its login was revoked it refuses with the locked notice's own sentence (`lockedMessage` from `shell/engine-lock-messages.ts`); while the engine is unreachable it refuses with `conciv lost connection to the engine. Your message is still in the composer.`
- `use-pane-messaging.ts:usePaneMessaging`: one gate for every send. A failed `checkSend` verdict throws `sendRejection(verdict)` before any rpc call; `onSteer` throws the `checkSendState` rejection before the kit's Steer resends a queued message. The pane wires the composer (Send and Enter), the empty-state starters and tool card replies (`chat-pane.tsx:sendFromButton`, which is `onSend` then `onSendError`) and Steer (`onSteer`, and `onSteerError`, which puts a refused item back through `LiveSessions.returnSteered` and then calls `onSendError`) through it. `onSendError` shows a refusal as a notice row, except the unreachable refusal while `sustainedOffline()` is true and the page is not locked: the standing lost-connection notice (`EngineUnreachableNotice`, mounted in the panel, the quick view and the pop-out) and the disabled Send already say it; in the first second of a lost connection, and for a locked page, the row still shows. A send the session took back (`chat.withdrawn()`: Stop was pressed before the engine had the run and the send then failed) is converted to a refusal with no message, so the kit puts the text back in the composer and no notice shows; a failed send with no Stop pressed still shows its notice. A Stop pressed while a plugin is still preparing the prompt ends the same way: the session sends the stop at once, the engine aborts the preparing run, and the message comes back to the composer with the thread as it was
- `pane-composer.tsx:ComposerSendControl`: Send is disabled while the engine is unreachable or the page is locked; its accessible name is then the locked notice's sentence, else `conciv lost connection to the engine`; Send takes the idle grey when the composer is empty and whenever it is disabled (unreachable, locked, attachments still sending, stopping), and a disabled Send is dimmed to `opacity-40`, the look of the kit's styled composer Send (`@conciv/ui-kit-chat` `styled/composer.tsx`)
- `refresh-coordinator.ts:makeRefreshCoordinator`: a refresh while one is running is ignored; a refresh on a chat whose history load failed reopens it (`liveSessions.reopen`) instead of re-fetching into the failed chat
- `chat-pane.tsx:ChatPane`: keyed on the session's chat instance, so a reopened chat remounts the pane; while the page is logged out, its login was revoked or the engine is unreachable (`usePaneMessaging().resendAllowed()`, the `checkSendState` gate without the compaction check) the run error row offers no Retry (`RunErrorRow` `onRetry` is optional and left out) and every assistant message's Refresh is disabled (`Thread.Messages` `refreshDisabled`); Retry also needs a retryable failure (`usePaneMessaging().retryable()`: a failed run, not a failed idle hook); a failed history load shows `Couldn’t load this conversation` with Retry, which calls `liveSessions.reopen(sessionId)`; while the reopened chat loads the alert stays up as a disabled `Retrying…`
- `older-messages.tsx:OlderMessages`: one older page loads at a time; nothing loads once `chat.hasOlderMessages()` is false or after a failure until Retry
- `chat-pane.tsx:threadDividers`: dividers before the first loaded message (the `New session` line) show only once no older page is left
- `chat-pane.tsx:renderTurnPrefix`: an assistant turn carries its harness name only once the session's replies (hydrated `readHarness(messageId)`, else the current harness) span more than one harness
- `draft-storage.ts:makeDraftStorage`: the composer renders at once with an empty draft; `restore` reads the row through `appData.readDraft` (`ensureQueryData` on `utils.drafts.get`) and hands it to `restoreDraft` (text and selection only into an untouched composer, attachments merged by id); a composer the user emptied before the read lands gets nothing restored and its cleared draft is written at once; no write reaches the server before that restore settles, then the latest typed draft is written; every save is a `drafts.set` mutation with `scope: {id: sessionId}`, so saves for one session reach the server in order, and its `onMutate` writes the row into the `drafts.get` cache entry (kept with `staleTime` and `gcTime` Infinity and `retry: false` in `app-data.ts`); `storage.getItem` returns that cached row, else the pane-local value, so a pane rebuilt after a view switch paints the text at once; keystrokes are batched by the kit's own 300 ms debounce, which flushes when the composer unmounts; clearing a non-empty draft persists the cleared draft immediately
- `queue-strip.tsx:QueueStrip`: shows at most 3 queued messages (`VISIBLE_LIMIT`), the rest as an overflow count

## Side Effects

- `draft-storage.ts:makeDraftStorage`, `appendDraft`: `drafts.get` through the query cache and `drafts.set` through a scoped mutation; a failed save is logged with `console.error` and the cache keeps the text, with no rollback, so after a refused save the text lives only in this page's cache until a later save succeeds
- `use-pane-messaging.ts:usePaneMessaging`: `rpc.chat.uiReply` and `rpc.sessions.compact`, then `invalidateSession` for the pane's session
- `refresh-coordinator.ts:run`: `chat().refresh()` and refetches `sessions.list`, `sessions.search`, the pane's `sessions.get`, `markers.list`, `captures.list`; screen reader announcements
- `chat-pane.tsx:ChatPane`: announces `conciv is asking for permission.` and `conciv replied.`; invalidates sessions and refetches markers when a run settles
- `trigger-sources.ts:useComposerTriggerSources`: `ensureQueryData` for `meta.commands` and `meta.tools`
- `trigger-sources.ts:useComposerTriggerSources`: a built-in or extension command replaces the harness command of the same name in the `/` list; a built-in beats an extension command of the same name
- `chat-pane.tsx:ChatPane`: a sent text that is exactly `/<name>` of a widget command runs it and is never sent to the agent
- `chat-pane.tsx:ChatPane`: owns the model menu (`useModelMenu`); `/model` opens it with `popover().setOpen(true)`, which focuses its search field, and every close (a pick, Escape, outside click, a settled harness-switch confirm) returns focus to the composer
- `composer-input-adapter.tsx:ComposerInputAdapter`: `keydown` listener for Escape
