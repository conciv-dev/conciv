# pane

## Overview

The chat pane for one session: transcript, composer with attachments and element grabs, drafts kept in two copies, send checks, queue strip, pending approvals, context usage tracker, status bar with view tabs, and refresh.

The composer draft has two copies. The first is in this browser: the IndexedDB database `conciv-drafts`, written within 100 ms of each change and flushed when the page is hidden or left, so text and images survive an instant reload even when the engine socket is already closed. The second is the engine's `drafts` row, saved over rpc after each local write; it can lag the local copy, and it is what another origin, another port, a fresh profile or cleared site data gets back. On load the local copy is applied as soon as it is read, without waiting for the engine; the engine row is read at the same time and, when it arrives, `reconcileDraft` (`draft-reconcile.ts`) picks one by comparing stamps for equality only: when the row's stamp is one this browser sent (the last acknowledged one, or one whose answer never came back), the local copy wins; when it differs, the engine wins; a synced local copy whose row is gone (a send or a delete) is cleared. The local copy is opencode's draft persistence, ported in `runtime/persistence/` (`drafts.ts`, `drafts-machine.ts`, and the `persist.ts` write batch they reuse); that folder's README lists what came from opencode and each difference from it. The reconcile rule and the engine copy are conciv's own: opencode keeps its draft only in the browser.

## Interface

- `ChatPane({sessionId, viewTab?})` (`chat-pane.tsx`): the pane for one session
- `DeletedSessionPanel({sessionId})` (`deleted-session-panel.tsx`): what `ChatPane` shows in place of the chat and composer when the session's row is `hidden` (deleted): the title `This session was deleted.` (`role="status"`, focus is not moved), the line `Your text moves to the new session.` while the deleted session's draft has text (the local copy in this browser first, the engine row when there is none), and one `New session` button
- `SESSION_DELETED_MESSAGE`, `sessionDeleted(error)` (`run-error-row.tsx`): the sentence `This session was deleted, so your message was not sent.` and the check for a failure carrying `SESSION_DELETED_CODE`
- `createPaneSession`, `SessionHeaderSlot`, `SessionStatusSlot`, `SessionComposerPills`, `SessionLinks`, `SessionComposerBinding` (`plugin-session-parts.tsx`): the chat pane's plugin parts: the `session.header` and `session.status` slots, the composer pills, the markdown link and code block provider (always mounted, so nothing remounts when the session object arrives), and the composer binding the mounted session writes through
- `PluginComposerPills({input})` (`plugin-composer-pills.tsx`): the plugins' `ComposerPill` registry above the composer, beside the `session.status` slot, ascending by `order`; each pill runs `show(input)` in a memo inside its plugin's `Contribution` and renders nothing while it returns undefined, so the lane holds no pill (and hides when nothing else is in it). Three shapes: a plain pill (icon in its tone, truncated label, `title` as its accessible name) runs `run` on click; a `menu` pill opens a ui-kit-system popover the host owns (placement, dismissal, heading `title ?? label`) around the plugin's content, rendered untracked once per open with `{session, screen, close}`; a `rows` pill opens a ui-kit-system menu with the heading as its group label and one item per row (`detail` as its badge, disabled without `run`). The popover body and the menu content stop at `max-h-80` and scroll, like the app's other lists. A `run` that throws is logged under the plugin's id
- `createPluginToolCards(session)` (`plugin-tool-cards.tsx`): the tool card entries of the plugins' `ToolCall` registry, first claim per tool name, placed first in the chat pane's list; an entry accepts a finished call while a session object exists and the plugin has not declined that call id; the plugin's render runs once each time the card mounts, and its view is the `body` of the normal card for that call (the catalog card when the catalog declares the tool, else the pane's fallback card), so the header is that card's own; when the catalog arrives after the card mounted, the same view moves into the catalog card and the plugin is not asked again. A render that returns nothing or throws marks the call id declined, so the next entry, the catalog card or the fallback draws it
- `PaneComposer`, `PaneComposerProps` (`pane-composer.tsx`): composer with attachment, send and stop buttons
- `ComposerInputAdapter`, `ComposerInputHandle`, `SelectionOffsets` (`composer-input-adapter.tsx`)
- `usePaneMessaging(deps)`, `PaneMessaging` (`use-pane-messaging.ts`): send, `onAnswer` (a tool card answer: the same send-state check as Send, saying "Your answer was not sent." when the engine is unreachable, and rejecting only for that refusal; otherwise `chat.uiReply`, whose failure keeps its own notice and does not reject) and `sessions.compact` mutations
- `makeDraftStorage(appData, keep, sessionId)`, `appendDraft(appData, sessionId, text)`, `prependDraft(appData, sessionId, text)`, `PaneDraftStorage` (`draft-storage.ts`): composer draft storage backed by `AppData.readDraft`, `cachedDraft` and `saveDraft` (`data/app-data.ts`): the `drafts.get` query cache entry and a `drafts.set` mutation scoped to the session; `draftCacheSink(keep, appData, sessionId, write)` is the draft sink for a session whose pane is not mounted: it writes text to the saved draft with `appendDraft` (the lost queue) or `prependDraft` (a refused Steer) through `keep`, the one write chain `makeLiveSessions` makes per app (`makeDraftWriteChain`) and exposes as `LiveSessions.keepDraft`, so a later write reads what an earlier one saved; the same chain carries each pane's persist write (`makeDraftStorage` takes it), and the deleted session panel's local read and local removal, so that read sees the flush the pane wrote when it unmounted; `keep(step)` returns the step's own promise, so a caller that awaits it sees its own failure, and the chain logs a failed step once (`[conciv] a local draft step failed`) and runs the next; `draftCacheSink`'s steps log their own failure (`[conciv] could not keep the queued message as a draft`) and resolve, because nothing awaits them; a chain step does local IndexedDB work only; nothing in it waits on the engine, because every pane's local writes queue behind it; each step goes through the same local-first write as typing: it reads what the step before it wrote from the local copy (the engine row only when there is no local copy; nothing when the local copy was synced and the cached `drafts.get` answer says its row is gone, a send or a delete; a step with a local copy never waits on the engine), writes the joined text to the `conciv-drafts` document and fires the engine save without waiting for it. The chain orders the local writes only: the `drafts.set` mutation scope (`scope: {id: sessionId}`) already sends one session's engine saves in call order, and waiting on each engine save let a pane that mounted while a save was held restore a half-written draft (#880). A failed save raises `DraftUnsavedNotice` as any other save does, and later steps still land locally. Without the local store (`appData.drafts` null) each step still waits for its engine save, because the next step reads that row; when the saved draft cannot be read, `appendDraft` logs it and treats it as no earlier draft, so the text becomes the draft in the cache first and the engine save then lands or fails by itself (the same rule `makeDraftStorage.restore` applies after a failed read when there is no local store; the cost is that once a save lands, it replaces an earlier engine draft this page never read); images go through `addFile` on the same chain (`keepImageInDraft`): the Blob into the local store with `keepDraftImage` (the attach rule, used by `paneAttachments` too), and the engine save carries it already encoded (`encodeAttachments` from `@conciv/ui-kit-chat/draft-storage`), not as `pending`: `onMutate` keeps the cached attachments while a `pending` file encodes, and a pane that mounts while the earlier saves are still retried reconciles against that cached row, so the image has to be in it at once; this file imports only that subpath and types from `@conciv/ui-kit-chat`, because the package's main entry does not load in the app's node tests, which import this file
- `DraftUnsavedNotice({sessionId, retry})` (`draft-unsaved-notice.tsx`): mounted in `ChatPane` above the queue strip; raises the persisted warn notice keyed `draft-unsaved` while the session's latest failed `drafts.set` save holds content other than its latest save the engine took (read with `useMutationState` over the `drafts.set` mutation key, no state of its own), so it clears when the text on screen is saved, when it is edited back to what the engine holds, and on a send (`endDraftSaves` drops the session's settled saves). With the local store (`appData.drafts` set) it says `conciv could not save your draft. It is kept in this browser, but the engine copy failed, so it is not on your other devices or in other browsers.`; without it (engine-only) `conciv could not save your draft. It is still in the composer, but a reload would lose it.` Its Retry is `PaneDraftStorage.retry`: with the local store it sends the content on screen with a new stamp through the same path as a typed save (the stamp goes into `sent` first and its ack sets `syncedAt`), skipping only the check against the cached row, which holds the failed save; engine-only it re-sends the cached row with a new stamp; a paused save raises nothing, the standing lost-connection notice already covers it
- `checkSend(content, state)`, `checkSendState(state)`, `MAX_CONTENT_PARTS` (`send-checks.ts`): pre-send validation verdict; `state` is `{busy, reachable, locked}`, `locked` being the `EngineLock` read from `useEngineReachability().locked()`
- `makeGrabStaging(deps)`, `GrabStaging`, `ComposerGrabPort` (`grab-staging.ts`): stages page element grabs as composer attachments
- `resolveGrabSource(grab, symbolicate)` (`grab-source-resolve.ts`)
- `paneAttachments`, `returnQueueToDraft`, `putBackInDraft` (`pane-attachments.ts`): image and text attachment adapters; `putBackInDraft(items, sink)` is the one put-back (text joined by newlines through `sink.insert`, images through `sink.addFile`) and `returnQueueToDraft` cancels every queued item and passes them all to it. A Steer the engine refuses passes its one item (already out of the queue) to it through `use-pane-messaging.ts` `onSteerError` and `LiveSessions.returnSteered` (only once it is out of the queue); while the pane is mounted that is a sink that puts the text at the start of the composer (`insertFirst`: `select` at 0, then `insert` with a trailing newline), so the steered text, first in line, comes before the queued messages the failed stream returned; its images still join the attachments after theirs. With no pane of that session mounted (the user left before the refusal landed) the text goes to the start of the saved draft through `draftCacheSink` with `prependDraft`, after the lost queue was appended there, so it is still first on return; an image on that path (`draftCacheSink.addFile`, a steered one or one from a lost queue) joins the saved draft's attachments under a new id: its Blob goes into the local draft store (`draft-storage.ts` `keepDraftImage`, the attach rule, so none over 20 MiB) and the engine save carries it already encoded, so it is back in the composer on return. Stop takes the queued messages out of the queue and puts them back in the draft (text in order, images as attachments), unsent. The same function runs when the chat stream fails while messages are queued (see `live-sessions.ts` in `app/`); each item leaves the queue through `cancelQueued`, so nothing stays queued to be sent later. Images queued by URL are not carried back; on a stream failure with the pane open, images come back as attachments through the same `returnQueueToDraft` path Stop uses, which no run exercises separately. A returned image is a `File` named `image` (`partFile`), the same name Stop has always given it
- `makeRefreshCoordinator(deps)`, `RefreshCoordinator` (`refresh-coordinator.ts`)
- `useSessionCaptures(sessionId)` (`session-captures.ts`), `useComposerTriggerSources({sessionId, openModelMenu})` (`trigger-sources.ts`): `{triggers, runTyped}`: slash command and tool trigger sources, plus `runTyped(text)` that runs a widget command whose `/<name>` is the whole text; widget commands are the built-in `/model` (opens the model menu) and extension commands from `useInstances()`
- `PaneAlert({message, busy, onRetry})` (`pane-alert.tsx`): a danger `role="alert"` line with a Retry button that reads `Retrying…` and is disabled while `busy`; the chat pane's failed history load uses it
- `QueueStrip` (`queue-strip.tsx`), `PendingApprovals` (`pending-approvals.tsx`), `ContextTracker`, `ContextSummary` (`context-tracker.tsx`), `StatusBar` (`status-bar.tsx`)
- `Divider`, `CompactSpinner`, `ConversationSkeleton({label?})`, `ThinkingBubble` (`indicators.tsx`)
- `OlderMessages({sessionId, chat})` (`older-messages.tsx`): rendered inside the thread viewport; a solid-query query keyed on the session and the oldest shown message id runs `chat.loadOlderMessages()` (each oldest id loads once; the next key waits until no older-page load is in flight, via `useIsFetching`) while the viewport reports `isNearTop()` (within three viewport heights of the top, so the page before loads while the reader still has history above them; a newest page shorter than that keeps loading pages until it is not); shows a `Loading earlier messages` status row at the top while it loads, and an alert with Retry when it fails
- `makeToolViewCtx` (`tool-view-ctx.ts`), `toolFallbackCard` (`tool-fallback-card.tsx`, the generic card of a call no card claims: the kit's `genericToolHeadline` gives its 'Called <tool>' title, its subtitle and its `key=value` arguments; it publishes no header, so its trace row is derived from the same headline), `createToolDurations` (`tool-durations.ts`, one pane-level record of tool durations; each chunk folds only the live turn's tool calls, settled entries stay, so a row that scrolls away and back reads the same duration)
- `CHAT_VIEW_ID`, `viewTabId`, `viewTabPanelId`, `viewTabPanelAttributes` (`view-tab-ids.ts`)

## Invariants

- `send-checks.ts:checkSend`: refuses empty content, then whatever `checkSendState` refuses, then more than `MAX_CONTENT_PARTS` (16) parts or a JSON payload over `WS_RPC_PAYLOAD_BUDGET_BYTES`, each with a warning while the message stays in the composer
- `send-checks.ts:checkSendState`: refuses silently while a compaction runs; while the page is logged out or its login was revoked it refuses with the locked notice's own sentence (`lockedMessage` from `shell/engine-lock-messages.ts`); while the engine is unreachable it refuses with `conciv lost connection to the engine. Your message is still in the composer.`
- `use-pane-messaging.ts:usePaneMessaging`: one gate for every send. A failed `checkSend` verdict throws `sendRejection(verdict)` before any rpc call; `onSteer` throws the `checkSendState` rejection before the kit's Steer resends a queued message. The pane wires the composer (Send and Enter), the empty-state starters and tool card replies (`chat-pane.tsx:sendFromButton`, which is `onSend` then `onSendError`) and Steer (`onSteer`, and `onSteerError`, which puts a refused item back through `LiveSessions.returnSteered` and then calls `onSendError`) through it. `onSendError` shows a refusal as a notice row, except the unreachable refusal while `sustainedOffline()` is true and the page is not locked: the standing lost-connection notice (`EngineUnreachableNotice`, mounted in the panel, the quick view and the pop-out) and the disabled Send already say it; in the first second of a lost connection, and for a locked page, the row still shows. A send the session took back (`chat.withdrawn()`: Stop was pressed before the engine had the run and the send then failed) is converted to a refusal with no message, so the kit puts the text back in the composer and no notice shows; a failed send with no Stop pressed still shows its notice. A Stop pressed while a plugin is still preparing the prompt ends the same way: the session sends the stop at once, the engine aborts the preparing run, and the message comes back to the composer with the thread as it was
- `pane-composer.tsx:ComposerSendControl`: Send is disabled while the engine is unreachable or the page is locked; its accessible name is then the locked notice's sentence, else `conciv lost connection to the engine`; Send takes the idle grey when the composer is empty and whenever it is disabled (unreachable, locked, attachments still sending, stopping), and a disabled Send is dimmed to `opacity-40`, the look of the kit's styled composer Send (`@conciv/ui-kit-chat` `styled/composer.tsx`)
- `refresh-coordinator.ts:makeRefreshCoordinator`: a refresh while one is running is ignored; a refresh on a chat whose history load failed reopens it (`liveSessions.reopen`) instead of re-fetching into the failed chat
- `chat-pane.tsx:ChatPane`: keyed on the session's chat instance, so a reopened chat remounts the pane; while the page is logged out, its login was revoked or the engine is unreachable (`usePaneMessaging().resendAllowed()`, the `checkSendState` gate without the compaction check) the run error row offers no Retry (`RunErrorRow` `onRetry` is optional and left out) and every assistant message's Refresh is disabled (`Thread.Messages` `refreshDisabled`); Retry also needs a retryable failure (`usePaneMessaging().retryable()`: a failed run, not a failed idle hook); a failed history load shows `Couldn’t load this conversation` with Retry, which calls `liveSessions.reopen(sessionId)`; while the reopened chat loads the alert stays up as a disabled `Retrying…`
- `older-messages.tsx:OlderMessages`: one older page loads at a time; nothing loads once `chat.hasOlderMessages()` is false or after a failure until Retry
- `deleted-session-panel.tsx:DeletedSessionPanel`: `New session` reads the deleted session's draft as the composer does (`readMovedDraft`: the local copy first, read as a step on the app's write chain, the engine row when there is none, read outside the chain, so text the engine never took still moves), starts a session through `useStartSession`, prepends the text to the new session's draft, clears the deleted session's draft (`clearMovedDraft`: its local document removed as a step on the chain, its engine row saved empty outside it); the create and the prepend run outside the chain, so a New session that waits on the engine holds no other pane's local writes, then calls the pane's `replaceSession` (the quick terminal swaps the pane in place, the panel and the pop-out open `/panel/<new>`); a failed draft read or draft write logs `[conciv] could not move to a new session`, a failed create is logged once by `useStartSession`; text only, attachments are not carried; when the new session cannot be created the old draft is left as it was; a draft write that fails after the session was created leaves that new, empty session behind
- `chat-pane.tsx:ChatPane`: a send refused with `SESSION_DELETED_CODE` shows `This session was deleted, so your message was not sent.` in the run error row and the notice, with no Retry, also when it was the thread's first message; a compaction refused with `NOT_FOUND` (the session is deleted or does not exist) notifies `This session no longer exists.` (`SESSION_NOT_FOUND_MESSAGE`)
- `chat-pane.tsx:threadDividers`: dividers before the first loaded message (the `New session` line) show only once no older page is left
- `chat-pane.tsx:renderTurnPrefix`: an assistant turn carries its harness name only once the session's replies (hydrated `readHarness(messageId)`, else the current harness) span more than one harness
- `draft-storage.ts:makeDraftStorage`: the composer renders at once with an empty draft; `restore` reads the row through `appData.readDraft` (`ensureQueryData` on `utils.drafts.get`) and hands it to `restoreDraft` (text and selection only into an untouched composer, attachments merged by id); a composer the user emptied before the read lands gets nothing restored and its cleared draft is written at once; no write reaches the server before that restore settles, then the latest typed draft is written; `storage.setItem` sends nothing when the draft equals the cached `drafts.get` row in every field a save would send (text, selection, attachments), so restoring a saved row never writes it back; every save is a `drafts.set` mutation with `scope: {id: sessionId}`, so saves for one session reach the server in order, and its `onMutate` (from the `drafts.set` mutation defaults) cancels the `drafts.get` fetch and writes the new row into the `drafts.get` cache entry (kept with `staleTime` and `gcTime` Infinity and `retry: false` in `app-data.ts`); `storage.getItem` returns that cached row, else the pane-local value, so a pane rebuilt after a view switch paints the text at once; keystrokes are batched by the kit's own 300 ms debounce, which flushes when the composer unmounts; clearing a non-empty draft persists the cleared draft immediately
- `queue-strip.tsx:QueueStrip`: shows at most 3 queued messages (`VISIBLE_LIMIT`), the rest as an overflow count

## Side Effects

- `data/app-data.ts` `drafts.set` mutation defaults: `gcTime` Infinity so a failed save stays in the mutation cache, and its notice stays up, for as long as the draft is unsaved; at most one failed save per session is kept, the latest: a save that starts (`onMutate`) or fails (`onError`) removes the session's earlier failed saves, so their text and `File`s do not pile up (the default 5 minute `gcTime` would drop the failed save and the notice with it while the draft is still unsaved); a successful save removes the session's earlier settled `drafts.set` mutations, which clears the notice, and itself stays as the content the engine holds; a save that ended without sending removes only the failed ones; `endDraftSaves` (a send, a deleted session) removes every settled one

- `draft-storage.ts:makeDraftStorage`, `appendDraft`: `drafts.get` through the query cache and `drafts.set` through a scoped mutation whose defaults live in `data/app-data.ts` (`setMutationDefaults` on the `drafts.set` mutation key): a save that fails on the transport or with an `INTERNAL_SERVER_ERROR` is tried again up to 3 times with the library's default back-off, never after a 4xx or validation answer; a save that fails for good is logged with `console.error` once, in `onError`, and the `drafts.get` cache entry keeps the row the save wrote, so a pane rebuilt by a view switch still paints the typed text and Retry sends what is on screen; `DraftUnsavedNotice` says the draft is unsaved. This departs from the TanStack optimistic-update guide, which rolls the cache back on error: here the composer is the user's truth and a rollback can only lose text. `onMutate` still cancels an in-flight `drafts.get` fetch so it cannot overwrite newer text; every settled save invalidates that entry. While the engine socket is down the save pauses and resumes on reconnect. A send ends the session's draft saves before its run starts: `onSend` (`use-pane-messaging.ts`) calls `AppData.endDraftSaves`, which sets the `drafts.get` cache entry to null, as the run start deletes the row; the attempt that then finds no row in that entry sends nothing and `saveDraft` answers false (the same check that ends a superseded save), so a save still waiting in its scope or in its retry back-off cannot bring the sent text back as a row, and its stamp leaves `sent` without becoming `syncedAt`; the cleared composer then sends nothing (an empty draft is never sent to an engine that has no row), so the local copy is an empty draft and a reload shows none. Not covered: an attempt already on the wire when the send starts can still land after the run start
- `draft-storage.ts:makeDraftStorage` with the local draft store (`appData.drafts` set): the pane hands the kit a `draftWriter`, so the kit writes no storage of its own. Each change sets a `persistStore` document (text, selection, attachments by id with their blob id, `syncedAt`) that the source's 100 ms batch writes to `conciv-drafts` under the session id; each flush then feeds the engine save. The feed encodes the composer's files with `encodeAttachments` (the 1,000,000 character budget of the engine copy) and compares the draft, with exactly the attachments the engine copy can hold (each one with a file as encoded, each one with no file taken from the cached row by id), to the cached `drafts.get` row; when they are equal nothing is sent, no stamp is made and nothing is written, so an attached image too big for the engine copy is not sent again after every answer. When they differ the stamp (`Date.now()`) is added to the document's `sent` list and the document is written, and only then the save goes with that `updatedAt` and the encoded attachments (not as `pending`, so `onMutate` puts the full row in the cache at once). On the engine's ack the document's `syncedAt` becomes the stamp that save sent and `sent` drops it and every stamp sent before it; on a save that failed for good, or that ended without sending (below), `sent` drops that stamp only, so `sent` holds only the stamps of saves still in flight. A save that a newer one superseded ends at its next attempt without sending: every attempt of a `drafts.set` mutation first reads the `drafts.get` cache entry, which each save's `onMutate` sets to its own row, and an attempt whose row is older than the cached one sends nothing and `saveDraft` answers false; so while the engine refuses every save, the saves queued behind a retried one end at once when it is tried again, and only the newest is still tried. An ended save is a success to the mutation cache that the engine never answered: its `onSuccess` removes the session's failed saves only (the newer save or the send that ended it decides the notice), and the unsaved notice does not count it as content the engine holds. `keepInDraft` and `keepImageInDraft` add the stamp they send to `sent` in the same local write that comes before their save; the unsaved notice's Retry sends the content on screen with a new stamp the same way, so its ack sets `syncedAt`. A failed local write is logged by `persistStore` and the engine save still goes. Once the session is deleted (`AppData.sessionDeleted`, set on `session.deleted`) the writer stops talking to the engine: the persist batch, the flush when the pane unmounts included, still writes the text on screen to the local draft, and no feed, stamp or engine save goes, so the local draft holds the text on screen when the pane closed and no row is upserted for the deleted session; the `session.deleted` handler leaves that local draft in place for the deleted session panel to move, and `clearMovedDraft` removes it once New session has carried it. No engine save goes before the engine row is read. `restore` starts the engine read and reads the local copy (`DraftStore.getItem`, its image Blobs through `resolveBlobUrl`, so a local image comes back as a composer attachment with its `File`), and applies the local copy to the composer as soon as it is read, so an unreachable engine never keeps it from the user; when the row arrives `reconcileDraft` (`draft-reconcile.ts`) picks the copy by comparing stamps for equality only: the engine row stamp equals the local `syncedAt` or a stamp in its `sent` list (a save this browser sent whose answer never came back, such as a reload before the ack), so the local copy wins and is saved to the engine if it differs; a different stamp, so the engine wins and the local copy is overwritten with the row and its stamp; a local copy with no `syncedAt` and no row, so the local copy wins and is saved to the engine (also when it has sent stamps: with no acknowledged save a missing row is read as one the engine never took, so the draft is kept, not cleared); a row and no local copy, so the row is taken and written locally; a local copy with a `syncedAt` and no row (a send or a delete), so the local copy is cleared, not brought back, whatever its `sent` list holds: the composer is emptied and the document becomes an empty draft with no stamp. An empty draft is never sent to an engine that has no row. A local attachment with no stored bytes is taken from the row by id when the row has it. Text typed before the row lands (since the local copy was applied, or at all when there was none) is never overwritten: the composer keeps it, the document takes the row's stamp (or loses its stamp when the row is gone) and the typed text is saved; a composer emptied before it lands gets nothing restored. An untouched composer that shows the local copy is replaced by the row when the engine wins (`DraftApplyMode` `replace`: `clearDraft`, then `restoreDraft`), and only gains the row's attachments for local ones with no stored bytes when the local copy wins. A local copy that cannot be read or parsed is logged and treated as absent. A failed engine read is not a row that is gone: the local copy is kept and shown and nothing is removed; the copy as restored is not sent to the engine (it may be a sent draft whose row a send removed), only text typed after it is, and the pick between the two copies waits for a load whose read succeeds. The cost: when the engine row is not the one this browser last sent, the engine wins and local edits that never reached the engine are lost. Without the local store (`appData.drafts` null) the kit's storage path is unchanged. In `data/app-data.ts` the `drafts.set` `mutationFn` encodes the `pending` files inside the session's scope, writes the full row into the `drafts.get` cache and sends it, so saves are encoded and sent in call order; `onMutate` writes the text and selection at once and keeps the cached attachments until the encode lands
- `use-pane-messaging.ts:usePaneMessaging`: `rpc.chat.uiReply` and `rpc.sessions.compact`, then `invalidateSession` for the pane's session
- `refresh-coordinator.ts:run`: `chat().refresh()` and refetches `sessions.list`, `sessions.search`, the pane's `sessions.get`, `markers.list`, `captures.list`; screen reader announcements
- `chat-pane.tsx:ChatPane`: announces `conciv is asking for permission.` and `conciv replied.`; invalidates sessions and refetches markers when a run settles
- `trigger-sources.ts:useComposerTriggerSources`: `ensureQueryData` for `meta.commands` and `meta.tools`
- `trigger-sources.ts:useComposerTriggerSources`: a built-in or extension command replaces the harness command of the same name in the `/` list; a built-in beats an extension command of the same name
- `chat-pane.tsx:ChatPane`: a sent text that is exactly `/<name>` of a widget command runs it and is never sent to the agent
- `chat-pane.tsx:ChatPane`: owns the model menu (`useModelMenu`); `/model` opens it with `popover().setOpen(true)`, which focuses its search field, and every close (a pick, Escape, outside click, a settled harness-switch confirm) returns focus to the composer
