The engine part runs inside the conciv engine, in node. It is written with `@conciv/backend-plugin-api`, which has two
entries that do the same work:

- **The Effect entry**, `@conciv/backend-plugin-api/effect`. `Plugin.define({id, effect})`, and every `ctx` domain
  returns an [Effect](https://effect.website). Every plugin conciv ships uses it.
- **The promise entry**, `@conciv/backend-plugin-api`. `Plugin.define({id, setup})`, and every `ctx` domain returns a
  `Promise`. See [The promise entry](#the-promise-entry).

The engine loads both. A definition with `effect` runs as it is. A definition with `setup` is wrapped by `fromPromise`
from `@conciv/backend-plugin-api/promise/adapter` first, so both run the same way.

| Import                                         | What it has                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------ |
| `@conciv/backend-plugin-api/effect`            | `Plugin`, `Skill`, `Rpc`, `Agent`, `Location`, `Model`, `Provider`       |
| `@conciv/backend-plugin-api/effect/plugin`     | the `Context` type of `ctx`                                              |
| `@conciv/backend-plugin-api/effect/tool`       | the tool domain's types (`ToolEditor`, `ToolDomain`)                     |
| `@conciv/backend-plugin-api/effect/rpc`        | the RPC domain's types (`RpcHandlers`, `RpcRegistration`)                |
| `@conciv/backend-plugin-api/effect/permission` | the permission domain's types                                            |
| `@conciv/backend-plugin-api/effect/session`    | the session domain's types                                               |
| `@conciv/protocol/schema/rpc`                  | `Rpc.define`, for the contract both parts import                         |
| `@conciv/backend-plugin-api`                   | the promise entry: `Plugin`, `Tool`, `Skill`, `Rpc` and the domain types |
| `@conciv/backend-plugin-api/promise/adapter`   | `fromPromise`                                                            |
| `@conciv/backend-plugin-api/host`              | what a plugin host uses to find a plugin's entry files                   |

## Define the plugin

`Plugin.define({id, effect})` is the default export of the engine part. The engine runs `effect(ctx)` when it loads
the plugin:

```ts title="packages/plugins/test-runner/src/test-runner.ts"
import {Plugin} from '@conciv/backend-plugin-api/effect'
import type {Context} from '@conciv/backend-plugin-api/effect/plugin'

export default Plugin.define<RunnerServices>({
  id: 'test-runner',
  effect: Effect.fn('TestRunner.plugin')(function* (ctx: Context) {
    const config = testRunnerConfig.safeParse(ctx.options)
    if (!config.success) return yield* Effect.die(config.error)
    const adapter = getRunner(config.data.runner) ?? vitest
    const manager = yield* adapter
      .create(ctx.location.directory)
      .pipe(Effect.catchTag('TestRunner.RunnerUnavailable', (error) => Effect.die(error)))
    yield* register(ctx, manager)
    yield* ctx.skill.transform((editor) => editor.add(info))
    const registration = yield* registerRpc(ctx.rpc, manager).pipe(Effect.orDie)
  }),
})
```

`effect` runs in a scope that the engine closes when the plugin stops, reloads or is turned off. What it registers
there goes with it, and so does a fiber it starts with `Effect.forkScoped`.

## Tools

Add tools inside `ctx.tool.transform`. `editor.namespace` describes a group, and `editor.add` adds one tool.
`execute` returns an `Effect` of the result:

```ts title="packages/plugins/test-runner/src/tools.ts"
const codeMode = {namespace: 'test_runner', codemode: true}
const direct = {namespace: 'test_runner', codemode: false}

export const register = Effect.fn('TestRunnerTools.register')(function* (
  ctx: Pick<Context, 'tool'>,
  manager: TestRunnerManager,
) {
  yield* ctx.tool.transform((editor) => {
    editor.namespace({
      name: 'test_runner',
      description: "The project's test runner: list the test files, run them or a pattern, read the last result.",
    })
    editor.add({
      name: 'list',
      description: 'List the test files without running them.',
      input: z.object({}),
      output: ListResultSchema,
      options: codeMode,
      execute: () =>
        manager.list(false).pipe(
          Effect.map((output) => ({output})),
          Effect.catchTag('TestRunner.RunnerUnavailable', toolFailure),
        ),
    })
    editor.add({
      name: 'status',
      description: 'Read the result of the last finished run without starting one.',
      input: z.object({}),
      output: TestRunResultSchema,
      options: direct,
      execute: () => manager.status.pipe(Effect.map((output) => ({output}))),
    })
  })
})
```

object.

### The tool context

`execute` gets the input and a context:

```ts title="packages/protocol/src/schema/tool.ts"
export type Origin = 'hub' | 'chat'

export interface Context {
  readonly sessionId: Session.Id
  readonly agent: Agent.Id
  readonly messageId: SessionMessage.Id | undefined
  readonly id: CallId
  readonly origin: Origin
  readonly progress: (update: Metadata) => Effect.Effect<void>
  readonly cancel?: Effect.Effect<void>
}
```

`origin` says where the call came from. `chat` is a call from a turn in the widget's chat. `hub` is a call from an
agent outside the widget, which the engine knows by the `conciv-origin: hub` header on the request. The page plugin
reads it when it starts a [job](#jobs) for a queue of page actions: for a `chat` call it posts the result into the
session when the job ends, and for a `hub` call it leaves the result to the hub, which reads it with `jobs.wait`.

In the promise entry, the context is `ToolContext`: the same fields, plus a `signal` that aborts when the call is
cancelled, and a `progress` that returns a `Promise`.

### Tool.Error

Fail the effect with a `Tool.Error` to fail the call with a message the agent reads. `Tool.toolError` makes one, and
`metadata` travels with it. The plugins conciv ships import `Tool` from `@conciv/protocol/schema/tool`; the promise
entry exports the same `Tool`.

```ts title="packages/plugins/whiteboard/src/refusal.ts"
import * as Tool from '@conciv/protocol/schema/tool'

export function fail({code, ...failure}: Failure) {
  return Effect.fail(Tool.toolError(code === undefined ? failure : {...failure, metadata: {code}}))
}
```

A typed failure becomes a `Tool.Error` once, at the edge, with `catchTag`:

```ts title="packages/plugins/test-runner/src/tools.ts"
function toolFailure(error: RunnerUnavailable) {
  return Effect.fail(Tool.toolError({message: error.message, error}))
}
```

## Skills

Add a skill inside `ctx.skill.transform`. The agent sees its `description`, and reads its `content` when it needs
it:

```ts title="packages/plugins/test-runner/src/skill.ts"
import {Skill} from '@conciv/backend-plugin-api/effect'
import {AbsolutePath} from '@conciv/protocol/schema/schema'

export const info: Skill.Info = {
  id: Skill.Id.make('test-runner'),
  name: Skill.Name.make('Test runner'),
  description:
    "Run the project's tests: list the test files, run all of them or the files matching a pattern, and read the last result. Load it before your first test_runner tool call.",
  path: AbsolutePath.make('skill://test-runner/SKILL.md'),
  content: [
    '# Test runner',
    '',
    "The test runner drives the project's own test framework (vitest by default, or playwright when the plugin is configured with `runner: 'playwright'`) in a separate process in the project directory.",
  ].join('\n'),
}
```

```ts title="packages/plugins/test-runner/src/test-runner.ts"
yield * ctx.skill.transform((editor) => editor.add(info))
```

For skills written as files in the project, see [Skills](/docs/skills).

## RPC

An RPC contract lets the browser part, another plugin or a terminal call the engine part. Put it in its own module and
export it as `./rpc`, so both parts import it.

### Rpc.define

`Rpc.define({id, methods, events})` from `@conciv/protocol/schema/rpc` declares the contract. Each method has an
`input` and an `output` schema, and optional named `errors`. Each event has a `schema`.

```ts title="packages/plugins/test-runner/src/rpc.ts"
import * as Rpc from '@conciv/protocol/schema/rpc'
import {z} from 'zod'

const unavailable = {UNAVAILABLE: z.object({available: z.literal(false), error: z.string()})}

export const TestRunner = Rpc.define({
  id: 'test-runner',
  methods: {
    status: {input: NoInputSchema, output: TestRunResultSchema},
    current: {input: NoInputSchema, output: CurrentRunSchema},
    list: {input: ListInputSchema, output: ListResultSchema, errors: unavailable},
    run: {input: RunArgsSchema, output: TestRunResultSchema, errors: unavailable},
    stop: {input: NoInputSchema, output: z.object({ok: z.boolean()})},
  },
  events: {event: {schema: TestEventSchema}},
})
```

An error name that starts with `rpc.` is reserved: `Rpc.define` throws on it.

### Register the handlers

`ctx.rpc.register(contract, handlers)` answers the methods. A handler gets the parsed input and a call context with
`error(name, message, data)`, which makes one of the method's declared errors. It returns an `Effect`:

```ts title="packages/plugins/test-runner/src/test-runner.ts"
function registerRpc(rpc: Context['rpc'], manager: TestRunnerManager) {
  return rpc.register(TestRunner, {
    status: () => manager.status,
    current: () => manager.current,
    list: (input, call) =>
      manager
        .list(input.failedOnly)
        .pipe(
          Effect.catchTag('TestRunner.RunnerUnavailable', (error: RunnerUnavailable) =>
            Effect.fail(call.error('UNAVAILABLE', UNAVAILABLE_MESSAGE, {available: false, error: error.message})),
          ),
        ),
    stop: () => manager.stop.pipe(Effect.as(OK)),
  })
}
```

The registration has `events.emit(name, data)`, which sends an event to every subscriber. A subscriber sees it as
`rpc.<id>.<event>`, here `rpc.test-runner.event`:

```ts title="packages/plugins/test-runner/src/test-runner.ts"
yield *
  manager.events.pipe(
    Stream.runForEach((event) =>
      registration.events
        .emit('event', event)
        .pipe(Effect.catchCause((cause) => Effect.logError('a live test event was not delivered', cause))),
    ),
    Effect.forkScoped({startImmediately: true}),
  )
```

To call these methods from the widget, see [Call the engine part](/docs/plugins/browser#call-the-engine-part). From a
terminal, see [`conciv plugin call`](/docs/plugins/terminal).

## Permissions

A tool that changes something can ask the user first. `ctx.permission.assert` checks the action against the session's
rules: a `deny` rule fails the call, an `allow` rule lets it run, and otherwise the user gets a card in the chat and the
call waits for the answer.

```ts title="packages/plugins/whiteboard/src/refusal.ts"
export function confirmed(
  permission: Confirm,
  action: string,
  metadata: Record<string, unknown>,
  tool: Pick<Tool.Context, 'sessionId' | 'agent' | 'messageId' | 'id'>,
) {
  return permission.assert({
    action,
    resources: ['*'],
    save: ['*'],
    metadata,
    sessionId: tool.sessionId,
    agent: tool.agent,
    source: {type: 'tool', messageId: tool.messageId, id: tool.id},
  })
}
```

The whiteboard adds `ask` rules for its destructive tools to every agent, so these calls always reach the user:

```ts title="packages/plugins/whiteboard/src/refusal.ts"
export const CONFIRMATION_RULES: Permission.Rule[] = CONFIRMED_TOOLS.map((action) => ({
  action,
  resource: '*',
  effect: 'ask',
}))
```

```ts title="packages/plugins/whiteboard/src/whiteboard.ts"
yield * ctx.agent.transform((editor) => editor.list().forEach((agent) => agent.permissions.push(...CONFIRMATION_RULES)))
```

`fallback: 'ask'` asks even when the only rule that allows the action is a catch-all `*` rule. The page plugin passes
it for the page actions that ask.

## Browser tabs

Every open widget is a browser tab the engine knows. The widget opens one for the session it shows with `tabs.open`
and keeps it open while that session stays on screen; the engine stores the tabs and lists them whether or not any
plugin is installed. A plugin reads them with `ctx.browserTabs`:

```ts title="packages/backend-plugin-api/src/effect/plugin.ts"
export interface BrowserTabDomain {
  readonly list: (sessionId: SessionId) => Effect.Effect<BrowserTabList>
  readonly sessions: () => Effect.Effect<SessionId[]>
}
```

`list` gives a session's tabs, each with its `id`, `url`, `title`, `focused` and `visible`, and `focusedTabId`, the
tab focused last. `sessions` gives the sessions that have a tab open. A plugin that acts inside a tab, as the page
plugin does, addresses it by its id. When a tab opens or closes the engine publishes `tab.opened` or `tab.closed`, which
a plugin hears with `ctx.event.subscribe`.

## Jobs

Work a tool call starts that finishes later is a job. `ctx.job.start` runs `run` in the background and keeps its
result, `wait` waits for it, and `cancel` stops it:

```ts title="packages/backend-plugin-api/src/effect/job.ts"
export interface JobDomain {
  readonly start: (input: JobStartInput) => Effect.Effect<JobInfo>
  readonly get: (id: string) => Effect.Effect<JobInfo | undefined>
  readonly wait: (input: JobWaitInput) => Effect.Effect<JobWaitResult>
  readonly cancel: (id: string) => Effect.Effect<JobInfo | undefined>
  readonly completeBackground: (notificationID: string) => Effect.Effect<void>
}
```

A job ends `completed`, `error` or `cancelled`. A job started with `background: true` and a `recovery` is kept in the engine's database,
so its result outlives the call that started it; one still running when the engine stopped reads as `cancelled`,
`Interrupted by server restart.`, after it starts again. Clients read background jobs through the contract's
`jobs.list` (a session's jobs, or the ones the given tool calls started) and `jobs.wait`. The page plugin starts one job per queue of page actions, with the call's `toolCallId` and
`origin` in its `metadata`, so an agent outside the widget gets the queue's result on its next call through the hub.

## The promise entry

`@conciv/backend-plugin-api` is the same engine part without Effect. `Plugin.define` takes `setup(ctx)` instead of
`effect`. `setup` may be async, and may return a cleanup that runs when the plugin stops or reloads. A tool's `execute`
and an RPC handler return a `Promise`, and a handler returns `call.error(...)` to fail with a declared error. This
plugin is the fixture of the CLI's tests:

```ts title="packages/cli/test/fixtures/plugins/plant-shelf/server.ts"
import {z} from 'zod'
import {Plugin} from '@conciv/backend-plugin-api'
import * as Rpc from '@conciv/protocol/schema/rpc'

const Plant = z.object({plant: z.string()})

const Stock = z.object({plant: z.string(), count: z.number()})

const Shelf = Rpc.define({
  id: 'plant-shelf',
  methods: {
    count: {input: Plant, output: Stock},
    sell: {input: Plant, output: Stock, errors: {'sold-out': Plant}},
  },
  events: {},
})

export default Plugin.define({
  id: 'plant-shelf',
  async setup(ctx) {
    const stock = {count: 1}
    await ctx.rpc.register(Shelf, {
      count: async ({plant}) => ({plant, count: stock.count}),
      sell: async ({plant}, call) => {
        if (stock.count === 0) return call.error('sold-out', `${plant} is sold out`, {plant})
        stock.count -= 1
        return {plant, count: stock.count}
      },
    })
    await ctx.tool.transform((tools) => {
      tools.add({
        name: 'shelf_restock',
        description: 'Restock a plant on the shelf, after the user allows it',
        input: Plant,
        output: z.object({plant: z.string(), restocked: z.boolean()}),
        execute: async ({plant}, tool) => {
          await ctx.permission.assert({
            sessionId: tool.sessionId,
            agent: tool.agent,
            action: 'shelf_restock',
            resources: [plant],
            save: [plant],
            metadata: {},
            source: {type: 'tool', messageId: tool.messageId, id: tool.id},
            fallback: 'ask',
          })
          return {output: {plant, restocked: true}}
        },
      })
    })
  },
})
```

A tool in the promise entry fails a call by throwing. A thrown `Tool.toolError(...)` reaches the agent as it is, and
any other error becomes a `Tool.Error` with that error's message.
