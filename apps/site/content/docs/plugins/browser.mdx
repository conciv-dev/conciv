The browser part runs in the widget. It is written with [Solid](https://www.solidjs.com) and
`@conciv/frontend-plugin-api`.

| Import                             | What it has                                                                         |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| `@conciv/frontend-plugin-api`      | `Plugin`, the registries (`Panel`, `Slot`, `ComposerPill`, ...), `usePlugin`, types |
| `@conciv/frontend-plugin-api/vite` | `experimental()`, the Vite build of the browser part                                |
| `@conciv/frontend-plugin-api/page` | `Page`, the page plugin's API, and `PageOperation`                                  |
| `@conciv/frontend-plugin-api/grab` | the element grab helpers                                                            |
| `@conciv/frontend-plugin-api/host` | `compose`, for an app that mounts the widget with its own plugins                   |

## Define it

`Plugin.define({setup})` is the default export of `src/plugin-experimental.tsx`. It declares no id: the widget gives
it the engine part's id as `ctx.id`. `setup` runs synchronously. Everything it adds with `ctx.add(Registry, item)` is
removed when the plugin reloads or stops, and `ctx.signal` aborts then.

The test runner's browser part adds the Tests tab:

```tsx title="packages/plugins/test-runner/src/plugin-experimental.tsx"
const runner: Plugin.Definition = Plugin.define({
  setup(ctx) {
    const runtime = ManagedRuntime.make(Layer.empty)
    onCleanup(() => void runtime.dispose())
    const tab: PanelTab = {
      id: 'tests',
      title: 'Tests',
      pinned: true,
      label: () => (
        <>
          <ctx.ui.Icon name="flask-conical" size="small" />
          Tests
        </>
      ),
    }

    ctx.add(Panel, {
      id: 'tests',
      region: 'pane',
      list: () => [tab],
      render: (props) => {
        const run = followRunView(runtime, ctx.client)
        return (
          <TestsPanel
            ui={ctx.ui}
            run={run()}
            directory={props.session.directory}
            canOpen={ctx.desktop !== undefined}
            onOpen={(error) => openFailure(ctx, runtime, error)}
            onFix={(error) => fixFailure(error, props.screen, props.session, props.session.directory)}
          />
        )
      },
    })
  },
})

export default runner
```

`ctx.add` takes an item, or a function that returns one. The widget runs the function again when what it reads
changes, and an `undefined` result adds nothing. `ctx.ui` holds the widget's own components (`Icon`, `Button`,
`SettingsRow`, ...), so a plugin draws as the widget does.

## Call the engine part

`ctx.client.rpc(Contract)` calls the plugin's own engine part, typed from the [RPC contract](/docs/plugins/engine#rpc).
The client is new after the engine restarts, so read `ctx.client` where you call it:

```ts title="packages/plugins/test-runner/src/follow.ts"
function readRun(client: Client) {
  return Effect.tryPromise({
    try: async (signal) => {
      const runner = client.rpc(TestRunner)
      const status = await runner.status(undefined, {signal})
      const current = await runner.current(undefined, {signal})
      return {status, current}
    },
    catch: (cause) => makeReadFailed({cause}),
  })
}
```

The engine part's events arrive on `client.event.subscribe`, as `rpc.<id>.<event>`. A `server.connected` event comes
after the engine connection comes back, so the test runner reads the run again then:

```ts title="packages/plugins/test-runner/src/follow.ts"
const TEST_EVENT = 'rpc.test-runner.event'

function decodeEvent(event: {readonly type: string; readonly data?: unknown}): TestRunnerFollowMachine.FollowEvent {
  if (event.type === 'server.connected') return {type: 'server-connected'}
  const parsed = TestEventSchema.safeParse(event.data)
  return parsed.success ? {type: 'event', event: parsed.data} : {type: 'event-invalid', error: parsed.error}
}
```

```ts title="packages/plugins/test-runner/src/follow.ts"
yield *
  Stream.fromAsyncIterable(client.event.subscribe({types: [TEST_EVENT]}), (cause) => makeStreamFailed({cause})).pipe(
    Stream.runForEach((event) => dispatch(decodeEvent(event))),
    Effect.catch((error) => dispatch({type: 'stream-failed', error: error.cause})),
  )
```

Import `useQuery`, `useMutation` and `useQueryClient` from `@conciv/client`, which the widget provides, so a view reads
through the widget's own query cache. The whiteboard loads its canvas this way, the first time the user opens it:

```tsx title="packages/plugins/whiteboard/src/plugin-experimental.tsx"
const surface = useQuery(() => ({
  queryKey: ['plugin', 'whiteboard', 'canvas-surface'],
  queryFn: () => import('./canvas-surface.js').then((module) => module.default),
  enabled: canvas.engaged,
  retry: false,
  refetchOnWindowFocus: false,
}))
```

## Registries

### Panel

A panel adds tabs to the session's pane. `list` returns the tabs to show, and `render` draws a tab's content. The test
runner's panel is in [Define it](#define-it). `list` gets `open`, the plugin's tab ids stored in the strip: return the
ones that still apply, plus any `pinned` tab.

### ToolRegistry

A tool card draws the calls of one tool in the thread. `render` gets the call's `tool`, `input`, `status`, `output`
and `metadata`. A tool with no card draws the widget's generic card, and a failed call draws `errorComponent`, or the
error card when there is none.

The test runner draws both of its direct tools with one card component, `render`:

```tsx title="packages/plugins/test-runner/src/plugin-experimental.tsx"
ctx.add(ToolRegistry, {name: 'test_runner_run', render})
ctx.add(ToolRegistry, {name: 'test_runner_status', render})
```

### Slot

A slot puts content at a fixed place in the widget:

```tsx title="packages/plugins/tanstack/src/plugin-experimental.tsx"
ctx.add(Slot, {at: 'session.status', render: () => <InspectorChip ui={ctx.ui} logo={ctx.icons.logo} />})
```

| `at`             | Where                           | `render` input                           |
| ---------------- | ------------------------------- | ---------------------------------------- |
| `window.bottom`  | the bottom of the widget window | none                                     |
| `session.header` | a session's header              | `session`, `screen`, `active`, `compact` |
| `session.status` | a session's status area         | `session`, `screen`                      |
| `page.overlay`   | over the page                   | none                                     |

The `session` a slot gets is the mounted session. Its `browserTab` is the browser tab this widget opened for it, the
`id` the engine lists in `tabs.list` (`packages/frontend-plugin-api/src/host-apis.ts:213`). A plugin that acts inside
the page, as the page plugin does, answers the commands addressed to that id.

A `page.overlay` slot holds the focus inside it unless it sets `hides: false`. The whiteboard adds its overlay only
while the canvas is visible:

```tsx title="packages/plugins/whiteboard/src/plugin-experimental.tsx"
ctx.add(Slot, () => (visible() ? overlay : undefined))
```

### ComposerPill

A pill sits above a session's composer. `show` returns the pill, or `undefined` to show none there, and `order` sorts
the pills:

```tsx title="packages/plugins/whiteboard/src/plugin-experimental.tsx"
const pill: ComposerPill = {
  id: 'whiteboard-open',
  order: 20,
  show: () => ({
    label: 'Whiteboard',
    icon: 'presentation',
    title: 'Open the whiteboard canvas',
    run: () => dispatchCanvas({type: 'toggled', surfaceFailed: surface.isError}),
  }),
}
```

A pill can instead open a list of `rows`, each with a `label` and its own `run`, or your own content through `menu`.

### SettingsPage

A settings page adds to the widget's settings. The whiteboard adds one row to the General section:

```tsx title="packages/plugins/whiteboard/src/plugin-experimental.tsx"
ctx.add(SettingsPage, {
  id: 'canvas-background',
  page: 'general',
  section: 'general',
  title: 'Whiteboard canvas background',
  entries: [
    {
      id: CANVAS_BACKGROUND_ROW,
      title: 'Canvas background',
      keywords: 'whiteboard canvas background transparent solid',
    },
  ],
  render: () => <CanvasBackgroundRow />,
})
```

| Fields                                  | Adds                          |
| --------------------------------------- | ----------------------------- |
| no `page`                               | a page of its own             |
| `page: 'general'`                       | a section on the General page |
| `page: 'general'`, `section: 'general'` | a row in the General section  |

`entries` are what the settings search finds. Frame a page of your own with `ctx.ui.SettingsLayout`, a section with
`ctx.ui.SettingsSection`, and a row with `ctx.ui.SettingsRow`, so it renders as the widget's own settings do.

### Command

A command runs from a keybind or a slash command:

```ts title="packages/frontend-plugin-api/src/registries.ts"
ctx.add(Command, {id: 'toggle', bind: 'mod+shift+e', title: 'Toggle', run: () => toggle()})
```

## Style it

The widget's own sheet holds the classes of the widget, its UI kits and the built-in plugins, and nothing else. Any
other plugin ships its own sheet. In this repo a plugin's `uno.config.ts` is one line, and its browser part adds the
sheet UnoCSS builds from its `src` with `Style`:

```ts title="packages/plugins/whiteboard/uno.config.ts"
import {pluginSheetConfig} from '@internal/uno-preset'

export default pluginSheetConfig(import.meta.url)
```

```tsx title="packages/plugins/whiteboard/src/plugin-experimental.tsx"
import pluginCss from 'virtual:uno.css?inline'
```

```tsx
ctx.add(Style, pluginCss)
```

`pluginSheetConfig` scans the package's `src` (not its tests, specs or stories) with `presetConciv({sheet: 'plugin'})`:
the preset's utilities, without the theme variables and the loader preflight, which the widget's sheet already
has (`packages/uno-preset/src/uno-preset.ts:30-60`).

A plugin's sheet applies only inside its own area. The widget draws each plugin's parts inside an element marked
`data-conciv-plugin="<id>"`, and adds `:where([data-conciv-plugin="<id>"], [data-conciv-plugin="<id>"] *)` to every rule
of that plugin's sheet (`packages/frontend-app-api/src/lib/plugin-fence.ts`), so a class in one plugin's sheet never
restyles the widget or another plugin. A popover or menu a plugin opens portals outside that element; the kit's
`LayerPortal` reads `LayerAreaContext` and wraps the portalled content in the same attribute, so the plugin's sheet
still reaches it (`packages/ui-kit-system/src/layer-portal.tsx`).

`@internal/uno-preset` is private. A plugin outside this repo writes its own UnoCSS config, or any CSS, and adds the
result with `ctx.add(Style, css)` the same way; the fence applies to it all the same.

## Build it

`experimental()` from `@conciv/frontend-plugin-api/vite` builds `src/plugin-experimental.tsx` into
`dist/plugin-experimental.cjs`, with one chunk per dynamic `import()` and Vite's manifest beside it. The test runner's
one Vite config builds the bundle and sets up its tests:

```ts title="packages/plugins/test-runner/vite.config.ts"
import {defineConfig} from 'vitest/config'
import {experimental} from '@conciv/frontend-plugin-api/vite'
import conciv from '@conciv/unplugin/vite'
import UnoCSS from 'unocss/vite'
import {concivTest} from '@internal/vitest-config/conciv-test'

export default defineConfig({
  publicDir: false,
  plugins: [UnoCSS(), experimental(), conciv(), concivTest({browser: true})],
})
```

Export the bundle as `./plugin-experimental` from the package. A plugin folder in the project ships it as
`plugin-experimental.cjs` or `plugin-experimental.js` beside its engine part. The widget loads the bundle and its
chunks from the engine, over its engine connection.

The build keeps the modules the widget provides external, and Node built-ins:

```ts title="packages/frontend-plugin-api/src/modules.ts"
export const pluginSharedModules = [
  'effect',
  '@conciv/frontend-plugin-api',
  '@conciv/protocol/schema/rpc',
  'zod',
] as const

export const pluginWindowModules = [
  'solid-js',
  'solid-js/web',
  'solid-js/store',
  '@conciv/client',
  '@conciv/frontend-plugin-api/page',
  '@conciv/frontend-plugin-api/grab',
] as const
```

An import of any other `effect/...`, `solid-js/...` or `@conciv/...` module fails the build: the widget does not
provide it, and a bundled copy would not share the widget's instance.
