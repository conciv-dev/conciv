<Accordion title="The conciv button never appears">

The widget probes the engine on load and only shows when the dev routes are live. Check that:

- the dev server is running, not a production build
- `enabled` is not set to `false`
- the engine port is reachable (set a fixed `port` if something else grabbed it)

On webpack and Rspack the widget is not injected for you. Set `widgetUrl`. See
[Configuration](/docs/configuration#widgeturl).

</Accordion>

<Accordion title="The chat does not answer, claude not found">

The default harness shells out to the `claude` CLI. Install Claude Code and make sure `claude` is
on your `PATH`, or point at it directly:

```ts
conciv({harnessBin: '/usr/local/bin/claude'})
```

See [Harnesses](/docs/harnesses).

</Accordion>

<Accordion title="Port conflicts">

Pin the engine port so server boot and the client widget agree:

```ts
conciv({port: 7378})
```

On the Vite dev server, the pinned port is a preference. When a second project already holds it,
the engine logs `port 7378 is already in use, the engine is listening on http://127.0.0.1:<other>
instead` and the page is stamped with the port it actually bound, so two dev servers can run side
by side. The Next.js integration and the generic webpack/rspack plugin are the exception: their
clients learn the port before the engine ever boots (Next inlines it into `next.config`'s env, and
the webpack/rspack plugin does not inject the widget at all — you set `widgetUrl` yourself), so a
taken port fails the boot instead of silently pointing the widget at another project's engine.

</Accordion>

</Accordions>
