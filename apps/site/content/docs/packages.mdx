An app installs one package, `@conciv/it`, as a dev dependency. The rest of conciv comes with it.

```bash
pnpm add -D @conciv/it
```

## What you install

| Package       | What it is                                                                                                                                                                        |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@conciv/it`  | The build plugin. Import paths: `@conciv/it/plugin/vite`, `/plugin/webpack`, `/plugin/rspack`, `/plugin/nextjs`, `/plugin/nextjs/widget`, `/plugin/rollup` and `/plugin/esbuild`. |
| `@conciv/cli` | The `conciv` command: `init`, `tools`, `auth`, `mcp` and `plugin`. Run `npx @conciv/cli@latest init` to set a project up. The build plugin also puts it on the agent's `PATH`.    |

The Vite, webpack and rspack entries start the engine and add the widget, in development only. The Rollup and esbuild
entries do nothing today. See [Quick start](/docs/quick-start) and [CLI](/docs/cli).

## How the rest is laid out

conciv has two sides. The engine runs in node next to your dev server. The widget runs in the browser, on your page.
Each side has the same four kinds of package, from the most stable to the most specific:

| Kind       | Engine side                  | Widget side                   | Holds                                                                                                |
| ---------- | ---------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------- |
| Plugin API | `@conciv/backend-plugin-api` | `@conciv/frontend-plugin-api` | What a plugin author imports: `Plugin.define`, the rpc contract helpers, the tool and context types. |
| App API    | `@conciv/backend-app-api`    | `@internal/frontend-app-api`  | The machinery behind the plugin API. Plugins never import it.                                        |
| Defaults   | `@conciv/backend-defaults`   | `@internal/frontend-defaults` | The product with no plugin in it.                                                                    |
| App        | `@conciv/backend`            | `@conciv/app`                 | The shipped product: the defaults plus the plugins conciv ships.                                     |

In more detail:

- **Plugin API.** Public and stable, with no implementation in it. `@conciv/backend-plugin-api` is the engine part's
  API, `@conciv/frontend-plugin-api` the browser part's. See [Plugins](/docs/plugins).
- **App API.** On the engine side: the plugin host, the tool service, permissions and hooks. On the widget side: the
  definitions the app and plugins share, plugin loading and persistence.
- **Defaults.** `@conciv/backend-defaults` is the engine: its HTTP, rpc, MCP and login surface, chat and code mode.
  `@internal/frontend-defaults` is the widget shell: router, pane, composer, sessions and settings. Neither ships a
  plugin.
- **App.** The plugins conciv ships are listed in one place per side. `@conciv/backend` calls `createBackend` from
  `@conciv/backend-defaults` with `plugins: [page]`. `@conciv/app` lists the page and terminal browser parts in
  `packages/app/src/builtins.ts`, and builds the widget bundle.

The layout is Backstage's: a plugin depends only on a small, stable API, and the product is the defaults plus a list of
plugins, so a plugin can be added or removed without touching the engine or the shell.

## Plugins

Each plugin is one package under `packages/plugins/`, with its engine part and its browser part together. A plugin's
code lives only there, never in the defaults or the app.

| Package                       | What it adds                                                                                       |
| ----------------------------- | -------------------------------------------------------------------------------------------------- |
| `@conciv/plugin-page`         | The connection to your page, its tools, and the cards in the widget. Shipped in both apps.         |
| `@internal/plugin-terminal`   | The session's terminal tab, over the engine's terminal. Shipped in `@conciv/app`.                  |
| `@conciv/plugin-test-runner`  | Runs your tests and streams each run into the Tests tab. See [Live tests](/docs/usage/live-tests). |
| `@conciv/plugin-recorder`     | Records the page with rrweb and gives the agent an action log with keyframes.                      |
| `@conciv/plugin-tanstack`     | Build errors, the route manifest and server function traces of a TanStack Router or Start app.     |
| `@conciv/plugin-ios`          | Builds and runs a native iOS app on the simulator. See [iOS](/docs/quick-start/ios).               |
| `@conciv/plugin-try-it`       | Lets a visitor on conciv.dev start a local engine with `npx` and connect to it.                    |
| `@internal/plugin-whiteboard` | A canvas you and the agent share. See [Whiteboard](/docs/usage/whiteboard).                        |

The plugins conciv ships are on [Built-in plugins](/docs/plugins/built-ins).

## Shared packages

| Package              | What it is                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `@conciv/protocol`   | The oRPC contract between widget and engine, and the zod schemas both sides share.                                   |
| `@conciv/types`      | Wire types and constants, such as the `.conciv` folder name and the rpc socket path.                                 |
| `@conciv/client`     | The browser's connection to the engine and its rpc client..                                                          |
| `@conciv/home`       | The per-user home registry. See [The home folder](#the-home-folder).                                                 |
| `@conciv/harness`    | The harness adapters: Claude Code, Codex, Gemini CLI, opencode and Pi. See [Harnesses](/docs/harnesses).             |
| `@conciv/serve`      | The node HTTP server the engine listens with. It binds `127.0.0.1` only.                                             |
| `@conciv/simulation` | The scripted agent and fixed network table an engine runs with under `CONCIV_SIMULATE`, and the driver side.         |
| `@conciv/cli`        | The `conciv` command.                                                                                                |
| `@conciv/unplugin`   | The build plugin itself, which `@conciv/it` wraps with the widget bundle's location.                                 |
| `@conciv/it`         | The package you install.                                                                                             |
| `@conciv/ui-kit-*`   | The widget's Solid components: `ui-kit-system`, `ui-kit-chat`, `ui-kit-chat-tools`, `ui-kit-tap`, `ui-kit-terminal`. |
| `@conciv/mascot`     | The robot mascot. `@conciv/mascot-react` is its React version.                                                       |

`@conciv/react`, `@conciv/preact` and `@conciv/solid` render `<ConcivWidget />` for an app that places the widget itself.

### The home folder

`@conciv/home` keeps one SQLite file, `home.db`, per user, so every engine on the machine and the `conciv` command can
find each other. It holds:

- the running engines: id, process id, project root, address and token. Each engine adds itself when it starts and
  marks itself gone when it stops.
- the agent CLIs connected to the conciv hub (`conciv init` connects them), and the hub's revocations.

The folder is `CONCIV_HOME` when set, else the user data folder:

| System  | Folder                                                |
| ------- | ----------------------------------------------------- |
| macOS   | `~/Library/Application Support/conciv`                |
| Linux   | `$XDG_DATA_HOME/conciv`, else `~/.local/share/conciv` |
| Windows | `%LOCALAPPDATA%\conciv\Data`                          |

It is created with mode `0700`, and `home.db` and `home.lock` with `0600`. The `conciv` command reads it to find the
engine to talk to, and checks each listed engine's `/health` first. An engine whose process, project folder or port is
gone is marked retired. Nothing is ever deleted from it. The engine also keeps its global settings in a `settings`
folder there.

## Test utilities

| Package                         | What it is                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------- |
| `@conciv/backend-test-utils`    | `test`, with a `createEngine` fixture that starts the real engine on a scripted model.      |
| `@internal/frontend-test-utils` | Renders a plugin's browser part, or the whole shell, against the fake engine or a real one. |
| `@internal/test-utils`          | The fake engine and its scripted model.                                                     |
| `@internal/engine-kit`          | The engine kit `@conciv/backend-test-utils` is built on.                                    |
| `@internal/vitest-config`       | The shared vitest projects and the isolated home folder each test run gets.                 |

See [Testing a plugin](/docs/plugins/testing).

## Published and private

A `@conciv/*` package is published to npm. An `@internal/*` package is private: never published, and built into the
package that uses it. `@internal/frontend-defaults`, for example, ships inside the `@conciv/app` widget bundle.

No workspace package may depend on another in a loop, through any of `dependencies`, `devDependencies`,
`peerDependencies` or `optionalDependencies`. CI checks this with `conciv-publish check-dependency-loops`. The loop rule
is what keeps the layout honest: a package can only build on the ones below it, so the plugin API can never come to
need the defaults, and the defaults can never need a plugin.
