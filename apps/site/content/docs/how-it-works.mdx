conciv has three running parts. Your dev server starts the engine and adds the widget to your page. The widget talks to
the engine over one websocket. The engine runs the harness, the agent CLI behind the chat.

## What runs where

  <Card

  />
  <Card

  />
  <Card
    title="Widget"
    description="@conciv/app: the conciv button, the panel and the terminal, mounted in a shadow root on your page."

When your dev server starts, the build plugin starts the engine. `@conciv/backend` calls `createBackend` from
`@conciv/backend-defaults` with the plugins conciv ships, and the engine serves HTTP on `127.0.0.1`. With no `port` in
your config, it takes the port it used last time (kept in `.conciv/server.json`) when that port is free, else any free
port.

Then the widget gets onto your page. Webpack and rspack add it to your build as one more entry. With Next.js, your app
imports `@conciv/it/plugin/nextjs/widget`. With Vite, the build plugin adds three tags to each HTML page it serves:

- `<meta name="conciv-api-base">` with the engine's address, `http://127.0.0.1:<port>`.
- `<meta name="conciv-widget">` with your `widget` settings.
- `<script type="module" src="/@conciv/widget.js">`, a module the build plugin answers itself. It imports
  `mountConciv` from `@conciv/app` and mounts the widget.

With `widget: false` only the first tag is added, for an app that renders `<ConcivWidget />` itself. A page with no
build plugin can load the widget as a classic script instead: `@conciv/app` also builds
`dist/conciv-widget.global.js`, which loads its chunks from the `widget/` folder beside it.

## How they talk

The browser talks to the engine over one oRPC websocket per tab, at `/rpc-ws`. Every widget call rides it: sessions,
settings, plugin calls, and the chat stream of a running turn. If the socket drops, the widget dials it again and
re-sends the calls in flight, and a running turn resumes from its last event.

Each open widget is a browser tab the engine knows. The widget calls `tabs.open` for the session it shows, and keeps
the call open while that session is on screen; when the widget goes, its socket drops, or it moves to another session,
the tab closes. The engine stores the open tabs and lists them with `tabs.list`, whatever plugins are installed. The
page plugin acts inside those tabs, and `conciv tools tabs` and a connected agent's `list_tabs` read the same list.

The engine serves these routes:

<TypeTable
  type={{
    '/rpc-ws': {required: true, type: 'websocket', description: "The widget's one oRPC socket."},
    '/rpc/*': {
      required: true,
      type: 'HTTP',
      description: 'The same oRPC procedures over HTTP, for node callers such as the conciv command.',
    },
    '/api/mcp': {required: true, type: 'MCP', description: 'The MCP endpoint for agents.'},
    '/health': {required: true, type: 'HTTP', description: 'Open to anyone. Reports the harness and the engine id.'},
    '/widget': {required: false, type: 'HTTP', description: 'The page the iOS app loads the widget in.'},
  }}
/>

Every route except `/health`, the login calls and `/widget` needs a token. A browser gets one by
[logging in](/docs/usage/logging-in) with the code the engine prints.

## A turn

<Steps>
  <Step>
    You send a message. The widget calls `chat.send` on the socket, which starts the run and streams its events back.
  </Step>
  <Step>
    The engine's chat picks the session's harness and asks it for a text adapter, then runs the turn through TanStack
    AI's `chat()` with conciv's tools and system prompt. The harness runs its CLI in your project folder.
  </Step>
  <Step>
    The agent calls tools. A plugin's tools come from the engine's tool service, filtered by the session's permission
    rules. The agent also finds the `conciv` command first on its `PATH`: the build plugin links it at
    `.conciv/bin/conciv`.
  </Step>
  <Step>
    When the CLI or a tool asks first, the engine's permission service holds the call and shows a permission card in the
    widget. The call goes on once you answer. See [Approvals](/docs/usage/approvals).
  </Step>
  <Step>Text, tool calls and cards stream back over the same socket into the panel.</Step>
</Steps>

## Plugins

A plugin has an engine part and a browser part, in one package. See [Plugins](/docs/plugins).

- The engine part is loaded by the engine. The plugins conciv ships are passed to `createBackend`. A plugin you add
  to `plugins` in your config is installed and loaded by the engine when it starts. Its `./server` export, else its
  main export, is the engine part.
- The browser part is loaded by the widget, from the engine. The engine reads the plugin's `./plugin-experimental`
  bundle when it loads the plugin, and the widget fetches it with the `plugin.experimental` rpc call, then evaluates
  it with the widget's own copies of Solid, Effect and the plugin API. Lazy chunks come the same way, on demand.
  The browser parts conciv ships are built into the widget bundle instead.

## The .conciv folder

The engine keeps its state in `.conciv/` at your project root. The folder has its own `.gitignore`, which ignores
everything in it except `settings/`.
