### 3. Journeys a lean rewrite would use

1. Grab payload (node): round trip, two-step budget, refusal table (forged/script/oversized/non-grab), preview budget, source label table.
2. Storage history (node): persist + reload (path/search/state/key/custom key), stack edges + truncation + cap, invalid-storage fallback table, throwing storage.
3. Wrapper component (it, per framework): mount → one launcher (StrictMode for React) → remove/restore → settings remount.

### 4. Cross-file / cross-level duplicates (verified by reading the other test)

- suite 160 vs e2e `vite-{preact,react,solid}-component` widget.spec:4: the e2e boots the component in a real consumer app (launcher visible, panel opens, no errors); the suite adds "exactly one" (meaningful only for React StrictMode) and the remove/remount/settings cases the e2e never does.
- storage:20 vs embed.it:2508 (open route survives reload end to end); different layer, both stay.
- grab vs conciv:2545: the app test stages grabs through the API, not the payload budget rules.

### 5. Odd things / rule breaks

- No mocks; storage-history uses a hand-written in-memory `WebStorage` (fake, allowed).
- suite 160 asserts `toHaveCount(1)` and then `expect(await fab(page).count()).toBe(1)`: the second read is redundant.
- `distDir: new URL('dist', import.meta.url)` resolves to `packages/<pkg>/test/dist` (the fixture build output), not the package dist; correct but easy to misread.
- Each wrapper package also needs its fixture build before `vitest run` (`test` script); running `vitest` alone uses a stale fixture.
