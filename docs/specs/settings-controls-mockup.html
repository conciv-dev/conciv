Controls for extension settings

One control per kind of setting an extension can declare. The page picks the control from the zod type (and .meta() hints), wires it through TanStack Form (createFormHook field components) and builds every control on an Ark UI primitive, so label, description and error are linked for screen readers (Field.Root sets aria-describedby / aria-invalid), keyboard works the Ark way, and focus rings are shared. Each cell shows the zod declaration, the Ark primitive, and the states. Controls respond to clicks.

Shared rules for every control

  • One field shell (Ark Field): label, description under it, error under that with role="alert", a changed dot and "Reset to default" when the value differs from the default, a lock line when the project config sets it. Rows put the control on the right; wide controls (cards, tags, textarea, recorder) go under the label.
  • Saved as you go: TanStack Form validates with the extension's zod schema (Standard Schema). Toggles, choices and sliders save on change; text and numbers save on blur or Enter. An invalid value shows its error and is never sent. The server validates again with the same schema.
  • States: default, focus (accent ring), changed, invalid, locked (read-only, value shown, why it is locked), disabled (dimmed, reason in the description).
  • Keyboard: Tab moves between fields; segmented and radio cards use arrow keys; selects and comboboxes open with Enter/Space and type-ahead; number fields take arrow up/down and Page Up/Down; tags take Enter/comma to add, Backspace to remove; the recorder captures any combo and Esc cancels.
  • Motion: segmented indicator and switch thumb slide with the same spring as the rail; all of it off under reduced motion.
  • Fallback: a zod type with no mapping (objects, unions, records) is not rendered; the extension can pass its own SettingsComponent for it, built from the same field components.
