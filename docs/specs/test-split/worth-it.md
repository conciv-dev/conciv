# Test split: is it worth it

Status: prep for the test rewrite (docs/specs/test-rewrite-after-port.md), written 2026-11-20 over the split files in
this folder (core.md, cli-harness.md, embed-flows.md, app.md, plugin-sdk.md, plugins.md, kits.md).

Question asked of every merge-id (or lone row) whose destination is NODE: does another layer already prove the same
user-facing behaviour? That layer can be a happy-dom journey, a unit or schema table, a story, or another NODE journey
with equal or stricter asserts. If it does, the node body is marked DROP, with a one-line reason that names the covering
test. A DROP never rests on a guess. A DROP never takes the only proof of a token gate, permission ask, deletion,
persistence or other data-loss behaviour.

Targets set for the pass: about one third fewer node bodies, and core's node tests under about 2,500 lines.

## Result: the targets are not met by coverage alone

Why the cut is small: the split already removed the duplicates. Most node bodies left are the only proof of their
behaviour: token, permission, deletion and restart proofs, real-process adapter and bridge proofs, publish contracts,
or engine rules a happy-dom journey cannot see (what the harness receives, argv, index rules, file modes). Dropping
more on coverage would mean guessing.

What would close the gap is rulings and moves, not more evidence. Each item below is a question; none is counted above.

## Questions for the maintainer

- **Q-WORTH-1, product moves out of core.** Core cannot reach ~2,500 lines by drops. These moves follow code
  ownership. Each is a product or ownership call:
  - the pty server to the terminal plugin: 12 bodies, ~500 lines;
  - the follow-up driver and queue wait next to the page plugin: 10 bodies, ~450 lines;
  - the page_eval asks into the page plugin's permission describe: 4 bodies, ~300 lines;
  - session search into its own suite: 14 bodies, ~450 lines.

  With all four, core is about 3,700 lines. Reaching 2,500 also needs either a budget exception, or moving the
  socket and trust block (CT-BROWSER-SOCKET, CT-RECONNECT, CT-SOCKET-POOL) to serve and contract.

- **Q-WORTH-2, type-contract rows.** PL-TYPES (12) and PH-TYPES (2) are checked by tsc only. Typecheck of every plugin
  in packages/plugins/* proves most of them. Typecheck is not one of the five layers. With a ruling, about 8 go.
- **Q-WORTH-3, opencode copies.** shared-events (16), state (24), bus (22), effect-flock (13) are verbatim opencode
  tests; nothing else in the repo proves them. Keep them as opencode does (default), or drop them?
- **Q-WORTH-4, folds.** About 13 bodies in embed-flows and app (for example 849 into U-WATCH, 646 into 626, the mascot
  publish rows into one table) and several in cli-harness (CLI-NEXT 5293 and CLI-WEBPACK 5579 into one it.each) can
  become rows of a neighbouring table with no proof lost. They are not drops, so they are not counted above. Fold them
  in the rewrite (default yes)?
- **Q-WORTH-5, drops that lean on a browser test.** The layer rule says a behaviour lives at the lowest layer that can
  prove it. A few drops below rest on an L3 browser test as cover. That is the wrong way round, so they are held as
  KEEP until ruled:
  - embed B-NATIVE (cover: E-NATIVE, L3);
  - unplugin 2017 (cover: e2e vite-vanilla widget.spec, L3);
  - recorder 1546 (cover: recorder.it 171, L3);
  - the row drops unplugin U-WPPORT 442 and try T-CONNECT 81 (cover: L3).

  With them held, the total is 83 bodies dropped, not 86.

- **Q-WORTH-6, e2e as cover.** cli 5273 and 4469 drop on E2E-INIT, a node suite that runs only in the e2e matrix, not
  in `pnpm test`. If cover must run in the same gate, those 2 stay.
- **Q-WORTH-7, at-risk happy-dom journeys.** Core CA-DRAFT and CA-HLIST drop on app journeys (M-LOCALDRAFT,
  M-HARNESS, M-PICKER) that the split itself lists as at risk in happy-dom. If those journeys move to L3 or are cut,
  the two core bodies come back.
